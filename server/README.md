# Server

FastAPI 기반 백엔드 서버 코드를 관리하는 디렉터리입니다.

프로젝트의 학습, 실시간 대결, 랭킹, 상점/하우징, 고양이 기능과 PostgreSQL 연동 로직을 단계적으로 구성합니다.

## 폴더 구조를 이렇게 나눈 이유

현재 백엔드는 파일 종류별(`models/`, `routers/`)로 한곳에 몰아넣기보다, **기능/도메인별로 폴더를 분리하는 구조**를 사용합니다.

```text
server/
├─ app/
│  ├─ users/       # 사용자, 출석
│  ├─ learning/    # 문제, 개념, 숙련도, 문제 제출 이력
│  ├─ battle/      # 실시간 대결 방, 참가자, 방 문제
│  ├─ ranking/     # 랭킹 그룹, 참가자, 승급전
│  ├─ economy/     # 상점 아이템, 인벤토리, 재화 사용
│  ├─ housing/     # 하우징 가구 배치/이동/삭제
│  ├─ cats/        # 고양이, 보유 고양이, 고양이 기억
│  ├─ sandbox/     # Docker 기반 Python 코드 실행/채점 환경
│  ├─ db/          # DB 연결, SQLAlchemy Base, 전체 모델 수집
│  ├─ core/        # 환경변수와 공통 설정
│  └─ main.py      # 각 도메인의 FastAPI router를 하나의 앱으로 연결
├─ alembic/        # DB 스키마 변경 이력
└─ tests/          # 기능별 검증 코드
```

### 1. 기능별 변경 범위를 분리하기 위해

이 프로젝트는 학습, 채점, 배틀, 랭킹, 상점, 하우징, 고양이처럼 기능의 성격이 뚜렷하게 나뉩니다. 따라서 같은 기능에서 함께 변경될 가능성이 높은 모델과 API를 같은 도메인 폴더에 두었습니다.

예를 들어 학습 문제나 제출 기록을 수정할 때는 `learning/`, 배틀방 로직을 수정할 때는 `battle/`를 중심으로 보면 됩니다. 이렇게 하면 기능을 찾기 쉽고 팀원 여러 명이 동시에 작업할 때 같은 파일을 수정해 충돌할 가능성도 줄어듭니다.

### 2. `learning`과 `sandbox`를 분리한 이유

`learning`은 문제, 제출 기록, 숙련도처럼 **학습 서비스의 규칙**을 담당합니다. 반면 `sandbox`는 사용자가 제출한 Python 코드를 Docker 컨테이너에서 안전하게 실행하는 **기술 인프라 역할**을 담당합니다.

채점 기능은 학습뿐 아니라 향후 배틀이나 승급전에서도 재사용할 수 있으므로 Docker 실행 로직을 특정 도메인 안에 넣지 않고 별도로 분리했습니다.

### 3. `battle`과 `ranking`을 분리한 이유

둘 다 경쟁 기능이지만 저장하는 상태가 다릅니다.

- `battle`: 방 생성, 입장, 준비, 진행, 현재 점수 등 실시간 세션 중심
- `ranking`: 장기간 유지되는 랭크 점수, 랭킹 그룹, 승급전 기록 중심

둘을 하나의 폴더에 합치면 실시간 방 로직과 장기 랭킹 로직이 섞여 파일이 지나치게 커지기 때문에 분리했습니다.

### 4. `economy`, `housing`, `cats`를 나눈 이유

세 기능은 서로 연결되지만 데이터의 책임이 다릅니다.

- `economy`: 아이템 가격, 구매, 재화, 인벤토리
- `housing`: 보유한 아이템을 집의 어느 위치에 배치했는지 관리
- `cats`: 고양이 종류, 유저가 획득한 고양이, 고양이별 기억 관리

따라서 구매 로직과 하우징 좌표, 고양이 데이터를 한 파일에 섞지 않고 각각 독립적으로 관리합니다.

### 5. 테이블 수는 줄이고 코드 책임은 분리하기 위해

ERD는 프로젝트 조건에 맞춰 20개 미만의 테이블로 구성했습니다. 별도의 지갑이나 하우스 테이블을 추가하지 않고 `USERS`에 `balance`, `mileage`, `house_level`, 벽지/바닥 정보를 포함하고, 가구 좌표는 `PLACED_OBJECTS.position_data(JSONB)`에 저장합니다.

하지만 **DB 테이블을 줄였다고 해서 코드의 기능 책임까지 합칠 필요는 없기 때문에**, 애플리케이션 코드는 도메인별로 계속 분리했습니다.

### 6. `db`와 `core`는 공통 기술 영역으로 제한

`db/`는 DB 연결과 전체 모델을 Alembic에서 인식할 수 있도록 모으는 역할만 담당하고, 실제 모델은 각 도메인 폴더에 둡니다.

`core/`에는 환경변수나 공통 설정을 두며, 상점·배틀·가챠 같은 비즈니스 기능을 넣지 않습니다. 공통 폴더가 잡동사니 폴더가 되는 것을 막기 위한 구조입니다.

### 7. Alembic과 tests를 애플리케이션 코드 밖에 둔 이유

`alembic/`은 서비스 기능이 아니라 DB 스키마 변경 이력을 관리하는 영역이고, `tests/`는 구현한 기능의 정상/예외/동시성 조건을 검증하기 위한 영역입니다. 애플리케이션 코드와 역할이 다르기 때문에 `app/` 밖에서 별도로 관리합니다.

## 구조 설계 원칙 요약

> 테이블 기준이나 화면 기준으로 무조건 나눈 것이 아니라, **같은 이유로 함께 변경되는 기능을 하나의 도메인으로 묶는 것**을 기준으로 했습니다.

이 구조를 사용하면 각 팀원이 기능별로 작업 범위를 나누기 쉽고, 학습/채점 같은 핵심 기능과 하우징·고양이 같은 부가 기능이 서로 과도하게 얽히는 것을 줄일 수 있습니다.

## 채점 Sandbox 이미지

채점 전용 이미지는 `sandbox/Dockerfile`에서 빌드합니다.

```powershell
docker build -t cat-game-sandbox:local -f sandbox/Dockerfile sandbox
docker run --rm --network none --read-only cat-game-sandbox:local
```

이미지는 Python 3.12 slim과 비-root `sandbox` 사용자만 포함하며 서버 소스와
추가 패키지를 복사하지 않습니다. 실제 제출 실행 시에는 Backend executor가
네트워크·메모리·CPU·시간·읽기 전용·capability 제한을 추가로 적용합니다.
