이 문서는 **매일 자정 이후 첫 로그인 시 자동 출석 처리**, 100원 보상, 연속 출석, 중복 요청, 자정 경계, transaction 실패를 정리한다.

> 확정 요구사항: **매일 자정 이후 첫 로그인 시 자동으로 출석을 처리하고 100원을 지급한다.**

> 현재 핵심 방어 원칙은 `ATTENDANCES(user_id, check_in_date)` 복합 UNIQUE다.

# H-01. 오늘 첫 로그인 시 자동 출석

## 목적
사용자가 자정 이후 그날 처음 로그인했을 때 별도 출석 버튼 없이 출석 기록을 만들고 100원 보상을 지급한다.

## 사용자 흐름
```text
로그인 성공
→ 서버가 오늘 첫 로그인인지 확인할 수 있는 출석 처리 수행
→ 서버 기준 오늘 날짜 계산
→ ATTENDANCES INSERT 시도
→ 오늘 첫 처리면 100원 지급
→ 이미 오늘 처리됐으면 추가 지급 없음
→ 홈 화면 진입
```

## 중요한 점
최종 사용자 경험은 **출석 버튼을 눌러야 보상을 받는 방식이 아니라 첫 로그인 자동 처리**다.

현재 구현되어 있는 명시적 check-in API가 있다면 최종적으로는 로그인 성공 흐름에서 내부적으로 호출하거나 동일한 출석 서비스 로직을 재사용하는 방향을 검토한다. API 모양을 지금 바로 바꾸는 것은 별도 구현 단계에서 진행한다.

## DB
- `USERS`
- `ATTENDANCES`

## 핵심
먼저 `오늘 출석했나?`를 SELECT해서 믿는 방식보다 실제 INSERT + UNIQUE 제약을 최종 기준으로 사용한다.

## 테스트
- 오늘 기록 없음 + 첫 로그인 → 출석 1행 생성, 100원 증가
- 같은 날 재로그인 → 출석 추가 생성 없음, 추가 보상 없음
- DB에 오늘 날짜가 정확히 저장되는지

# H-02. 연속 출석

## 목적
전날에도 출석했다면 streak_count를 이어간다.

## 처리
```text
오늘 자동 출석 처리
→ 직전 출석 날짜/연속일 확인
→ 마지막 출석일 == 어제
→ streak_count = 이전 streak + 1
→ 오늘 row INSERT
```

## 왜 streak를 row에 저장하나
매번 처음 가입일부터 모든 출석 행을 세지 않고 해당 출석 시점의 연속일 수를 바로 알 수 있다.

## 테스트
- 어제 streak=3 → 오늘 4
- 월말/연말 날짜 경계

---

# H-03. 연속 출석 끊김

## 상황
마지막 출석이 어제가 아니라 이틀 이상 전이다.

## 처리
```text
마지막 출석 날짜 != 어제
→ streak_count = 1
```

과거 기록을 삭제하지 않는다. 이전 streak는 이력으로 남는다.

## 테스트
- 하루 결석 후 로그인
- 여러 달 만에 로그인

# H-04. 같은 날 재로그인/중복 처리

## 상황
사용자가 이미 오늘 자동 출석 처리를 마친 뒤 다시 로그인하거나 같은 출석 로직이 다시 실행된다.

## DB 방어
```text
UNIQUE(user_id, check_in_date)
```

두 번째 INSERT는 DB가 거절한다.

## 서버
`IntegrityError`를 잡아 rollback하고, **이미 오늘 출석 처리된 정상 상태**로 간주한다.

로그인 자체를 실패시키는 오류로 취급할 필요는 없다. 중요한 것은 보상이 다시 지급되지 않는 것이다.

## 왜 이것이 강한가
프론트 표시나 서버의 사전 SELECT만 믿는 것보다 DB 자체가 중복 데이터 생성을 금지하기 때문이다.

---

# H-05. 동시에 여러 번 출석 로직 실행

## 상황
중복 로그인 요청이나 네트워크 재전송 등으로 같은 사용자의 출석 로직이 동시에 여러 번 실행될 수 있다.

## Lock 없는 사전 SELECT의 문제
모든 요청이 거의 동시에 `오늘 기록 없음`을 볼 수 있다.

## UNIQUE 방식
여러 요청이 INSERT를 시도해도 `(user_id,date)`가 같은 행은 최종적으로 한 개만 존재할 수 있다.

## 보상 주의
출석 INSERT와 100원 지급은 같은 transaction 흐름 안에서 묶어야 한다. UNIQUE에 성공한 요청만 보상을 지급하도록 순서를 설계한다.

## 테스트
동시 요청 후:
```text
ATTENDANCES 오늘 row 수 = 1
보상 증가 횟수 = 1
총 증가액 = 100원
```
인지 확인한다.

# H-06. 존재하지 않는 사용자

## 상황
존재하지 않는 사용자로 출석 처리 로직이 실행된다.

## 처리
```text
User 확인
→ 없음
→ 출석 처리 중단
→ Attendance INSERT 없음
```

최종 인증 구조에서는 로그인에 성공한 사용자 ID를 서버가 사용하므로 클라이언트가 임의의 user_id를 출석 보상 대상으로 지정하지 못하게 한다.

## 테스트
없는 UUID, 삭제된 사용자 등을 확인한다.

# H-07. 정상 보상 지급 — 100원

## 확정 규칙
출석 보상은 **100원**이다.

## 처리 순서
```text
BEGIN
→ 오늘 ATTENDANCES INSERT
→ UNIQUE 통과
→ USERS balance = balance + 100
→ COMMIT
```

## 재화 증가
Python에서 기존 값을 읽어 계산해 덮어쓰기보다 DB에서 직접 증가시키는 방식이 동시성에 안전하다.

예:
```sql
UPDATE users
SET balance = balance + 100
WHERE id = :user_id;
```

향후 재화 체계 자체가 사료/금화 등으로 공식 변경되면 이 문서와 ERD/API를 함께 갱신해야 한다. 현재 기준 요구사항의 출석 보상량은 100이다.

## Response/로그인 결과
프론트가 출석 보상 팝업을 보여줄 필요가 있다면 로그인 응답 또는 별도 사용자 상태 조회에서 다음 정보를 전달하는 방식을 검토할 수 있다.

```text
오늘 출석 보상이 새로 지급됐는지
streak_count
지급액 100
변경 후 balance
```

정확한 Response 계약은 인증 API 설계와 함께 확정한다.

# H-08. 보상 처리 실패 시 rollback

## 상황
Attendance INSERT는 성공했지만 balance UPDATE 중 DB 오류가 발생한다.

## 위험
출석 기록은 생겼는데 돈을 못 받으면 다음 로그인에서는 UNIQUE 때문에 다시 받을 수도 없다.

## 해결
Attendance INSERT와 balance UPDATE를 같은 transaction에 둔다.

```text
INSERT attendance
→ balance UPDATE 실패
→ ROLLBACK
→ attendance INSERT도 취소
```

사용자는 정상 복구 후 다시 로그인/출석 처리 시 보상을 받을 수 있어야 한다.

## 테스트
보상 UPDATE 실패를 의도적으로 만들어 attendance row가 남지 않는지 확인한다.

## 목적

```text
출석 달력 열기

→ 날짜순 또는 최신순 정렬
```

## 테스트
- 기록 없음
- 여러 날짜 기록
- 다른 사용자 기록이 섞이지 않는지

# H-10. 자정 경계와 서버 날짜

## 확정된 부분
새 출석 일자는 **자정 이후 첫 로그인**을 기준으로 시작한다.

## 아직 미정인 부분
어느 timezone의 자정을 서비스 기준으로 사용할지는 팀에서 확정해야 한다.

예:
```text
한국 00:01
서버가 UTC 기준이면 전날 15:01
```

서버가 단순 `date.today()`를 쓰면 배포 서버의 timezone에 따라 결과가 달라질 수 있다.

## 해결 방향
서비스 기준 timezone을 하나 정하고 서버가 그 timezone으로 `check_in_date`를 계산한다.

한국 사용자 대상이라면 `Asia/Seoul`을 명시적으로 사용하는 안을 검토할 수 있지만, **timezone 자체는 아직 확정값으로 취급하지 않는다.**

## 중요한 원칙
클라이언트가 `오늘 날짜`를 body로 보내게 하지 않는다. 사용자가 기기 날짜를 바꿔 출석을 조작할 수 있기 때문이다.

## 테스트
- 서비스 기준 23:59 직전 로그인
- 서비스 기준 00:00 직후 로그인
- 같은 날 재로그인
- 서버 OS timezone이 다른 환경

# H 영역에서 팀이 확정/검토해야 할 것

이미 확정:

```text
[x] 매일 자정 이후 첫 로그인 시 자동 출석
[x] 기본 출석 보상 100원
```

남은 결정:

1. 서비스 기준 timezone
2. streak 추가 보상이 있는지
3. streak 최대 보너스가 있는지
4. 로그인 Response에서 출석 보상 정보를 어떻게 전달할지
5. 현재 check-in endpoint를 로그인 내부 서비스로 재사용할지/외부 endpoint를 유지할지
6. 출석 기록 조회 기간/페이지네이션 필요 여부

핵심 구현 원칙은 `복합 UNIQUE + IntegrityError 처리 + 출석/보상 같은 transaction`이다.
