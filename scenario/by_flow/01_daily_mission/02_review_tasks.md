# 02. 오늘의 복습 문제 확인

## 목적
오늘 풀어야 할 복습 문제 목록을 사용자에게 보여주고, 각 문제의 완료 여부와 실제 풀이 가능 여부를 확정하는 단계다.

현재 Backend 기본 선정 규칙은 활성 문제 중 사용자 숙련도가 낮은 개념을
우선해 최대 3개를 선택하는 것이다. 숙련도 기록이 없으면 레벨 0으로 보고,
동률은 `concept_id`, `task_id` 순으로 고정한다. 선정 결과는 출석 row의
`daily_task_ids`에 저장하므로 당일 문제 활성 상태나 숙련도 변화로 목록이
바뀌지 않는다.

## 정상 흐름
1. 서버가 오늘 복습 대상으로 선정된 문제 목록을 조회한다.
2. 각 TASK의 활성 상태와 사용자 완료 여부를 함께 확인한다.
3. 클라이언트는 미완료/완료 문제를 구분해 표시한다.
4. 사용자가 미완료 문제를 선택한다.
5. 선택 시점에 다시 풀이 가능 여부를 확인하고 문제 풀이 화면으로 이동한다.

## 발생 가능한 변수

### A. 배정 후 TASK가 비활성화됨
- **원인**: 잘못된 문제 수정, 관리자 비활성화, 테스트케이스 오류 발견.
- **위험**: 목록에는 있지만 실제 제출은 불가능한 상태가 된다.
- **감지**: 목록 조회 및 문제 진입 시 `TASKS.is_active`를 다시 확인한다.
- **해결**: 비활성 문제를 그대로 풀게 하지 않는다. 배정된 문제를 유지할지 대체 문제로 바꿀지는 `TBD`.
- **UI**: `현재 사용할 수 없는 문제입니다.`

### B. 같은 문제가 목록에 중복 등장
- **원인**: 복습 선정 로직 중복, 생성 API 재시도, 중복 insert.
- **감지**: 동일한 task_id가 한 날짜 목록에 여러 번 존재하는지 확인한다.
- **해결**: 프론트에서만 숨기지 말고 서버/DB에서 중복 원인을 제거한다. 구현 시 유니크 제약 또는 멱등키 도입을 검토한다.

### C. 다른 기기에서 이미 완료됨
- **원인**: PC/모바일 동시 사용.
- **감지**: 문제 선택 직전 또는 목록 새로고침 때 서버 진행 상태 재조회.
- **해결**: 최신 완료 상태로 갱신하고 중복 보상은 허용하지 않는다.

### D. 문제 수가 비정상적으로 많거나 적음
- **원인**: 복습 알고리즘 설정 오류, 숙련도 데이터 이상.
- **해결**: 상한/하한은 아직 비즈니스 룰 `TBD`. 단, 비정상 데이터 탐지를 위한 로그는 남길 수 있다.

### E. 문제 상세 데이터 일부 누락
- **원인**: TASK는 존재하지만 concept/template 등 연관 데이터가 깨짐.
- **감지**: 응답 DTO 생성 중 필수 필드 검증.
- **해결**: 깨진 문제를 정상 문제처럼 반환하지 않는다. 서버 오류 또는 사용 불가 문제로 처리한다.

### F. 완료 상태와 실제 attempt 결과가 어긋남
- **원인**: 보상/진행 상태 갱신 중 서버 장애, 과거 데이터 마이그레이션 문제.
- **해결**: 어느 데이터가 권위 상태인지 구현 전에 명확히 정한다. 단순히 화면 표시값으로 진행 여부를 확정하지 않는다.

## UI
- 문제 제목/개념/난이도
- 완료 여부
- 현재 사용 불가 여부
- 전체 진행률
- `이어 풀기` 또는 `완료` 표시

테스트케이스 원문 등 채점용 민감 데이터는 사용자 응답에 포함하지 않는다.

## DB/API 영향
- TASKS 활성 상태 확인.
- TASK_ATTEMPTS 또는 별도 일일미션 진행 데이터에서 완료 상태를 읽을 수 있어야 한다.
- 전용 미션 스키마는 아직 확정되지 않았으므로 문서에서 임의 추가하지 않는다.

## 동시성/재시도
- 목록 조회는 여러 번 호출되어도 상태를 바꾸지 않는다.
- 같은 문제를 두 탭에서 동시에 열 수는 있지만 제출·보상 단계에서 중복 처리를 막아야 한다.
