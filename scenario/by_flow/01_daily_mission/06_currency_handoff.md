# 06. 재화 획득 및 다음 흐름 연결

## 목적
일일미션 보상이 실제 사용자 재화에 반영된 뒤, 그 결과를 상점·가챠 등 다음 소비 흐름과 연결하는 단계다. 이 단계는 `보상을 계산하는 단계`가 아니라 **지급 결과를 확정하고 다음 화면들이 같은 잔액을 보게 만드는 단계**다.

## 정상 흐름
1. 개별/올클리어 보상 transaction이 성공한다.
2. 서버가 최신 재화 잔액을 확정한다.
3. 응답에 지급 결과와 최신 잔액을 포함한다.
4. 클라이언트는 화면의 재화 표시를 서버 응답 기준으로 갱신한다.
5. 사용자는 홈으로 돌아가거나 상점/가챠로 이동할 수 있다.
6. 상점/가챠 진입 시에도 서버에서 최신 잔액을 다시 확인한다.

## 발생 가능한 변수

### A. 화면 잔액과 서버 잔액이 다름
- **원인**: 다른 탭/기기에서 구매, 다른 보상 수령, 오래된 프론트 상태.
- **해결**: 클라이언트 숫자를 권위값으로 사용하지 않는다. 서버 응답과 재조회 결과를 기준으로 화면을 갱신한다.

### B. 보상 지급 성공 후 클라이언트가 응답을 못 받음
- **원인**: 네트워크 단절, 브라우저 종료.
- **위험**: 사용자는 보상을 못 받은 것으로 생각할 수 있다.
- **해결**: 재접속 시 미션 보상 상태와 사용자 잔액을 다시 조회한다. 이미 지급된 보상을 재지급하지 않는다.

### C. 일일미션 화면에서 잔액을 먼저 올려 보임
- **원인**: 프론트 optimistic update.
- **위험**: 서버 지급 실패 시 존재하지 않는 재화를 보여준다.
- **해결**: 실제 경제 재화는 서버 성공 응답 후 반영한다. 단순 애니메이션은 가능하지만 최종 숫자는 서버 상태를 따른다.

### D. 사용자가 보상 직후 동시에 상점에서 구매
- **상황**: 보상 증가와 구매 차감이 매우 가까운 시점에 발생.
- **해결**: 각각의 DB write가 원자적으로 처리되어야 한다. 상점은 `balance >= price` 조건부 UPDATE 등으로 구매 시점의 실제 서버 잔액을 검사한다.

### E. 사용자가 보상 직후 가챠 시도
- **문제**: 가챠 비용/재화 종류가 아직 확정되지 않았다.
- **해결**: 현재 문서에서는 비용, 확률, 천장을 임의로 확정하지 않는다. 정책 확정 후 가챠 흐름의 차감 transaction과 연결한다.

### F. 재화 종류가 둘 이상으로 확장
- **상황**: 현재 USERS에는 balance, mileage 등이 있으나 최종 경제 구조가 아직 확정되지 않음.
- **해결**: `일일미션이 어느 재화를 지급하는가`를 팀 합의 전 임의 결정하지 않는다. `TBD`로 남긴다.

### G. 재화 지급 기록과 잔액이 맞지 않음
- **원인**: 과거 버그, 수동 관리자 수정, 마이그레이션 오류.
- **해결**: 감사 로그/보상 이벤트 기록 정책이 확정되면 추적 가능하게 한다. 현재 스키마에 없는 로그 테이블을 이 문서에서 임의 확정하지 않는다.

## 서버/DB 원칙
- 보상 지급은 서버에서만 확정한다.
- 잔액 증가와 지급 완료 표시는 원자적으로 처리한다.
- 이후 상점 차감은 `현재 잔액 >= 가격`을 DB에서 다시 검사한다.
- 장시간 외부 작업과 재화 transaction을 묶지 않는다.

## UI
- 지급 성공 시 재화 획득 애니메이션 가능.
- 표시 숫자는 서버의 최종 잔액으로 맞춘다.
- 새로고침 후에도 같은 잔액이 보여야 한다.
- 상점/가챠 버튼은 사용자가 이동할 수 있는 편의 기능일 뿐, 실제 구매/뽑기 가능 여부는 각 서버 API가 다시 검증한다.

## 다른 흐름과 연결

### 상점
`일일미션 보상 → 재화 획득 → 상점 → 가구 구매 → 인벤토리 → 하우징 배치`

### 가챠
`일일미션 보상 → 재화 획득 → 가챠 → 고양이 획득 → USER_CATS 반영 → 하우징 배치`

가챠의 실제 write API와 확률 정책이 확정되지 않은 상태라면 해당 부분은 DEMO/설계 단계와 실제 서버 구현을 구분한다.

- 여러 보상 이벤트 동시 발생
