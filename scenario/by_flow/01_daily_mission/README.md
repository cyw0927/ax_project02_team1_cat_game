# 일일 미션 흐름 시나리오

## 0. 전체 흐름

`일일 미션 진입 → 오늘의 복습 문제 확인 → 문제 풀이 및 제출 → 채점 → 개별 보상 및 올클리어 보상 → 재화 획득`

일일 미션은 단순 출석 보너스가 아니라 **그날 복습해야 할 문제를 제시하고, 풀이 결과에 따라 보상을 주는 별도 학습 흐름**이다. 따라서 날짜 경계, 복습 대상 생성, 제출 중복, 채점 지연, 보상 중복 지급 같은 변수를 단계별로 분리해서 본다.

---

## 1. 일일 미션 진입

### 목적
사용자가 홈에서 오늘 진행할 일일 미션의 존재 여부와 진행 상태를 확인하고, 해당 날짜의 복습 세션으로 진입한다.

### 정상 흐름
1. 사용자가 로그인 후 홈에서 `일일 미션`을 선택한다.
2. 서버는 서버 기준 날짜로 오늘의 일일 미션 상태를 계산한다.
3. 오늘 복습 대상, 완료 개수, 전체 개수, 보상 수령 여부를 반환한다.
4. 클라이언트는 진행률과 시작/이어하기 버튼을 표시한다.

### 발생 가능한 변수와 원인

#### 변수 A. 서버 날짜와 사용자 기기 날짜가 다름
- 원인: 사용자의 PC/휴대폰 시간이 잘못 설정됨, 해외 체류, VPN, 자정 직전/직후 접속.
- 위험: 클라이언트 날짜로 미션을 만들면 하루에 두 번 생성되거나 오늘 미션이 사라질 수 있다.
- 감지: 서버가 현재 날짜를 자체 기준으로 계산하고 클라이언트가 전달한 날짜를 권위 값으로 사용하지 않는다.
- 해결: 서비스 표준 타임존을 팀에서 확정해야 한다. 현재 타임존은 최종 확정 전이면 `TBD`로 둔다.
- UI: `오늘의 미션`이라는 표현만 보여주고 내부 기준 날짜를 필요 시 함께 표시한다.

#### 변수 B. 오늘 복습할 문제가 0개
- 원인 1: 신규 사용자라 과거 학습 데이터가 없다.
- 원인 2: 모든 개념 숙련도가 충분해 복습 대상으로 선정되지 않았다.
- 원인 3: 복습 후보였던 TASK가 비활성화됐다.
- 원인 4: 복습 대상 생성 규칙이 아직 실행되지 않았다.
- 해결: 0개를 오류로 취급하지 않는다. `오늘 복습할 문제가 없습니다` 상태를 별도로 표현한다.
- 비즈니스 결정 필요: 0개일 때 올클리어 보상을 자동 지급할지 여부는 `TBD`. 임의 지급 금지.
- 다음 영향: 문제 풀이 단계로 가지 않고 완료 상태 또는 일반 학습 유도 화면으로 분기한다.

#### 변수 C. 일일 미션 상태 조회 실패
- 원인: DB 연결 실패, 서버 오류, 네트워크 단절.
- 해결: 빈 미션처럼 위장하지 않는다. 조회 실패와 `문제 0개`는 반드시 구분한다.
- UI: `미션 정보를 불러오지 못했습니다. 다시 시도해주세요.` + 재시도 버튼.

#### 변수 D. 사용자가 여러 기기에서 동시에 진입
- 원인: PC와 모바일 동시 접속, 탭 여러 개.
- 해결: 읽기 자체는 허용하되 진행률/보상 상태는 서버 DB를 권위 상태로 한다.
- 다음 영향: 다른 기기에서 이미 완료한 문제는 새로고침 시 완료로 반영한다.

### DB/API 영향
- 오늘의 미션 상태를 계산할 때 사용자 ID + 서버 날짜가 핵심 식별 기준이 된다.
- 현재 ERD에 일일 미션 전용 테이블이 확정되어 있지 않다면, 신규 테이블을 문서에서 임의 확정하지 않는다. 구현 전에 스키마 변경 여부를 결정해야 한다.

### 테스트
- 신규 사용자
- 과거 학습 이력 있는 사용자
- 복습 대상 0개
- 자정 1분 전/후
- 두 탭 동시 진입
- 서버 오류/네트워크 끊김

## 2. 오늘의 복습 문제 확인

### 목적
사용자가 오늘 풀 문제 목록과 현재 완료 상태를 확인한다.

### 정상 흐름
1. 서버가 오늘 복습 문제 목록을 반환한다.
2. 문제별 완료 여부와 풀이 가능 여부를 표시한다.
3. 사용자가 미완료 문제를 선택한다.

### 발생 가능한 변수와 원인

#### 변수 A. 목록에 있던 문제가 중간에 비활성화됨
- 원인: 관리자 오류 수정, 잘못된 문제 비활성화.
- 위험: 사용자 화면에는 있는데 제출하면 TASK가 없거나 inactive가 될 수 있다.
- 해결: 조회 시 활성 상태를 다시 확인한다. 이미 일일 미션에 배정된 문제를 유지할지 대체 문제로 바꿀지는 `TBD` 정책으로 분리한다.
- UI: 문제를 풀 수 없다면 `현재 사용할 수 없는 문제입니다.` 표시.

#### 변수 B. 같은 문제가 중복 포함됨
- 원인: 복습 대상 생성 로직의 중복, 재시도 중 insert 중복.
- 해결: 생성 단계에서 유니크 조건 또는 멱등키로 방지하는 방안을 검토한다.
- UI에서 단순히 중복 제거만 하면 DB 오류를 숨길 수 있으므로 서버 데이터를 정리해야 한다.

#### 변수 C. 사용자가 다른 기기에서 이미 해당 문제를 완료함
- 원인: 동시 사용.
- 해결: 문제 클릭 직전 또는 제출 직후 서버 상태를 다시 확인한다.
- UI: 완료 배지 갱신.

#### 변수 D. 오늘의 문제 수가 매우 많음/적음
- 원인: 복습 선정 알고리즘 설정.
- 해결: 문제 수 상한/하한은 비즈니스 룰이므로 확정 전 `TBD`.

### 다음 단계 조건
- 사용 가능한 미완료 문제를 선택하면 `문제 풀이 및 제출`로 이동.
- 모두 완료면 보상 상태 확인으로 이동.

### 테스트
- 정상 목록
- 비활성 문제 포함
- 중복 문제
- 일부 완료/전체 완료
- 다른 기기에서 완료 상태 변경

## 3. 문제 풀이 및 제출

### 목적
사용자가 코드를 작성하고 서버에 제출한다.

### 정상 흐름
1. 문제 상세를 표시한다.
2. 사용자가 코드 작성.
3. 제출 버튼 클릭.
4. 서버는 사용자/문제/제출 가능 상태를 확인한다.
5. `TASK_ATTEMPTS`에 PENDING 시도를 짧은 트랜잭션으로 저장하고 빠르게 응답한다.
6. 채점 작업은 DB 트랜잭션 밖에서 수행한다.

### 발생 가능한 변수와 원인

#### 변수 A. 제출 버튼 연타
- 원인: 네트워크 지연 때문에 사용자가 응답이 없는 것으로 판단.
- 위험: 같은 코드가 여러 번 채점되고 보상 중복 가능.
- 해결: 클라이언트 버튼 잠금은 UX일 뿐이다. 서버에서 중복 제출 허용 범위/멱등 정책을 결정해야 한다.
- 보상은 동일 문제의 동일 보상 조건에 대해 중복 지급되지 않도록 별도로 보호한다.

#### 변수 B. 제출 직후 인터넷 끊김
- 원인: Wi-Fi 전환, 브라우저 종료.
- 경우 1: 서버가 PENDING 저장 전에 끊김 → 제출 자체가 없을 수 있음.
- 경우 2: 저장 후 응답만 못 받음 → 서버에는 attempt가 존재함.
- 해결: 사용자가 재접속하면 최근 attempt를 조회해 상태를 복원할 수 있어야 한다.

#### 변수 C. 빈 코드/너무 큰 코드/허용되지 않은 입력
- 해결: API 입력 검증으로 거절. Docker 실행까지 보내지 않는다.
- 상세 제한값은 정책 확정 필요.

#### 변수 D. 문제가 제출 순간 비활성화됨
- 해결: 제출 수락 시점에 task active 여부를 서버에서 재검증.

### DB/동시성
- PENDING insert 후 즉시 commit.
- Docker 컨테이너 실행을 기다리면서 DB row lock/transaction을 잡고 있지 않는다.

### UI
- 제출 성공 후 `채점 중` 상태를 명확히 표시.
- 네트워크 오류와 코드 오답을 같은 메시지로 보여주지 않는다.

### 테스트
- 정상 제출
- 더블클릭
- 저장 전/후 네트워크 단절
- 비활성 문제
- 빈 코드
- 여러 사용자 동시 제출

## 4. 채점

### 목적
사용자 코드를 안전한 격리 환경에서 실행하고 결과를 확정한다.

### 정상 흐름
1. Background 작업이 실행 슬롯을 기다린다.
2. 슬롯 확보 후 Docker 컨테이너 실행.
3. CPU/메모리/네트워크/파일시스템 제한 적용.
4. 테스트 결과 수집.
5. 컨테이너 제거.
6. 짧은 DB 트랜잭션으로 attempt 최종 상태 갱신.
7. 클라이언트는 polling 등으로 상태를 확인한다.

### 발생 가능한 변수와 원인

#### 변수 A. 채점 대기열 증가
- 원인: 동시에 많은 제출.
- 해결: 무제한 컨테이너 생성 금지. 애플리케이션 semaphore/queue로 동시 실행 수 제한.
- UI: PENDING과 RUNNING을 구분할 수 있다면 `채점 대기 중`/`채점 중`으로 표현.

#### 변수 B. 코드 무한루프
- 해결: 실행 timeout 후 해당 컨테이너만 종료/제거.
- DB: 실패 상태 기록.
- 다른 사용자의 컨테이너나 DB까지 함께 죽이지 않는다.

#### 변수 C. 메모리 초과
- 해결: 컨테이너 memory limit을 넘긴 해당 작업만 실패 처리.

#### 변수 D. Docker daemon 장애
- 원인: Docker Desktop 종료, daemon 오류.
- 해결: attempt를 영구 PENDING으로 두지 않도록 실패/재시도 정책 필요. 자동 재시도 횟수는 `TBD`.

#### 변수 E. 서버 재시작
- 현재 BackgroundTasks가 비내구성이면 실행 중 작업 유실 가능.
- MVP에서는 한계를 문서화하고, 향후 durable queue 도입 여부 검토.

### 다음 단계 조건
- 최종 채점 결과가 확정되면 보상 판단으로 이동.
- 시스템 오류면 사용자 재시도 가능 상태로 이동하되 오답으로 처리하지 않는다.

### 테스트
- 정답/오답
- timeout
- memory limit
- Docker daemon down
- 동시 30건 이상 제출
- 서버 재시작

## 5. 개별 보상

### 목적
오늘의 복습 문제를 정상적으로 해결한 경우 해당 문제에 대한 보상 자격을 판단한다.

### 정상 흐름
1. 채점 결과가 정답으로 확정.
2. 해당 문제의 일일 미션 보상 지급 여부를 확인.
3. 미지급이면 보상 처리.
4. 지급 완료 상태를 서버 DB에 기록.

### 변수

#### 변수 A. 동일 정답 제출을 여러 번 함
- 원인: 재풀이, 중복 요청.
- 해결: `정답 attempt 수`와 `보상 횟수`는 같은 개념이 아니다. 보상은 해당 미션/문제 기준 1회 등 확정된 정책에 따라 멱등 처리해야 한다.

#### 변수 B. 보상 지급 도중 DB 오류
- 위험: 지급은 됐는데 완료 표시 실패 또는 그 반대.
- 해결: 재화 증가와 보상 지급 기록을 가능한 한 하나의 짧은 원자적 트랜잭션으로 묶는다.

#### 변수 C. 보상 액수 미확정
- 현재 보상 수치를 문서에서 임의로 결정하지 않는다. `TBD`.

### UI
- 새로 지급된 경우만 보상 애니메이션.
- 이미 수령한 문제를 다시 풀었다면 `이미 오늘의 보상을 받았습니다` 등 명확히 표시.

## 6. 올클리어 보상

### 목적
오늘 요구된 모든 복습 문제를 완료했을 때 추가 보상 자격을 판단한다.

### 정상 흐름
1. 마지막 미완료 문제 채점 성공.
2. 서버에서 오늘의 전체 대상 완료 여부를 다시 계산.
3. 올클리어 보상 미지급 상태 확인.
4. 조건 충족 시 1회 지급.

### 발생 가능한 변수

#### 변수 A. 마지막 두 문제가 거의 동시에 정답 처리됨
- 원인: 두 탭/두 기기 동시 제출.
- 위험: 두 요청이 동시에 `아직 올클리어 보상 없음`을 보고 두 번 지급.
- 해결: DB UNIQUE, 조건부 UPDATE, 보상 전용 멱등키 등으로 exactly-once에 가깝게 보호해야 한다. 단순 SELECT 후 INSERT만 하면 race 가능.

#### 변수 B. 오늘 문제 0개
- 0개를 올클리어로 볼지 여부는 `TBD`.

#### 변수 C. 문제 하나가 관리자에 의해 비활성화
- 완료 조건에서 제외할지, 대체 문제를 줄지 정책 필요.

### UI
- 올클리어 성공 시 개별 보상과 구분된 연출.
- 재접속 시 이미 받은 보상을 다시 애니메이션으로 신규 지급처럼 보여주지 않는다.

## 7. 재화 획득 및 다음 흐름 연결

### 목적
획득한 보상이 실제 사용자 잔액에 반영되고 상점/가챠에서 사용할 수 있게 한다.

### 정상 흐름
1. 보상 지급 트랜잭션 완료.
2. 최신 잔액 반환 또는 재조회.
3. 홈/상점/가챠 UI의 잔액 갱신.

### 변수
- 여러 보상이 동시에 지급됨 → lost update 방지를 위해 단순 `read + 계산 + save`보다 DB 원자 연산 권장.
- 응답 유실 → 재접속 시 DB 잔액을 권위 상태로 사용.
- 화면 잔액이 오래됨 → 구매 시 서버가 다시 잔액 확인.

### 다음 단계
- 사용자는 홈으로 돌아가거나 상점/가챠로 이동할 수 있다.
- 하우징으로 직접 이동해 현재 고양이/가구를 확인할 수도 있다.

## 아직 확정이 필요한 항목

- 서비스 기준 타임존
- 오늘 복습 문제 선정 규칙과 문제 수
- 문제 0개일 때 완료/보상 정책
- 개별 보상 수치
- 올클리어 보상 수치
- 일일 미션 전용 DB 구조 및 멱등키 설계
- 채점 실패 자동 재시도 횟수

이 값들은 팀 합의 전까지 구현 상수로 확정하지 않는다.
