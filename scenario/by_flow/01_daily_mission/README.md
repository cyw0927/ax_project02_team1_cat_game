# 일일 미션 흐름 시나리오

## 0. 전체 사용자 흐름

`홈 → 일일 미션 진입 → 오늘의 복습 문제 확인 → 문제 선택 → 코드 작성 → 제출 → 비동기 채점 → 결과 확인 → 개별 보상 → 올클리어 판정/보상 → 최신 재화 반영 → 홈/학습/상점/가챠/하우징`

이 문서는 **사용자가 실제로 보는 화면과 사고 상황(Worst Case)**을 먼저 설명하고, 그 뒤에 서버 감지·방어 로직·DB/API 영향까지 연결한다. 세부 기술 설계는 같은 폴더의 단계별 문서를 함께 본다.

> 확정되지 않은 신규 컬럼/보상 수치/출제 수량/타임존/보상 정책은 임의로 확정하지 않고 `TBD`로 둔다.

---

## 1. 진입 및 오늘의 문제 불러오기

### 사용자 화면/흐름
홈에서 `일일 미션`을 누르면 오늘 풀 복습 문제와 진행률이 보인다. 예: `반복문 복습`, `리스트 복습`, `조건문 복습`, `0/3 완료`. 출석/연속 학습 현황이 함께 보일 수 있다.

### 정상 흐름
1. 서버가 인증된 사용자와 서버 기준 날짜를 확인한다.
2. 오늘의 복습 대상과 완료 상태를 조회한다.
3. 기존 오늘 미션이 있으면 동일한 구성을 반환한다.
4. 없으면 확정된 출제 정책으로 생성한다.
5. 화면은 서버 응답을 기준으로 진행률을 그린다.

### Worst Case A — 신규 사용자라 복습 데이터가 없음
- **왜 발생:** `USER_PROFICIENCY`, 과거 `TASK_ATTEMPTS`가 충분하지 않다.
- **서버 감지:** 유효한 숙련도/과거 시도 데이터가 없음 또는 기준 미달.
- **방어 로직:** 신규 사용자 fallback 정책을 적용한다. `기초 문제`, `신규 사용자 기본 미션`, `일반 학습 유도` 중 최종 방식은 `TBD`.
- **UI:** 오류 화면 대신 `아직 복습할 기록이 충분하지 않아요` 또는 확정된 기본 문제를 표시한다.
- **DB/API 영향:** 일일미션 전용 저장 구조가 신규 ERD에서 필요하면 별도 확정한다. 없는 컬럼을 기존 테이블에 있다고 가정하지 않는다.

### Worst Case B — 복습 후보가 0개
- **왜 발생:** 해당 개념의 활성 TASK 부족, 비활성화, 난이도 조건 불일치, 후보 고갈.
- **서버 감지:** 후보 조회 결과가 0개.
- **방어 로직:** 차순위 취약 개념/난이도 범위 확대/복습 없음 분기 등 fallback chain을 사용하되 정책은 확정 후 적용한다.
- **UI:** `오늘은 복습할 문제가 없습니다`와 `조회 실패`를 구분한다.
- **다음 단계 영향:** 문제가 없으면 풀이로 가지 않고 일반 학습 유도 또는 완료 상태로 분기한다.

### Worst Case C — 23:59에 열고 00:01에 풀이
- **왜 발생:** 열린 화면의 날짜와 서버 날짜가 달라진다.
- **서버 감지:** 요청의 mission_date와 서버 current_date 비교.
- **방어 로직:** 날짜 권위는 서버. 전날 문제를 자정 이후 인정할지는 `TBD`.
- **UI:** 정책상 전날 미션이 만료되면 `날짜가 변경되어 오늘의 미션을 새로 불러옵니다.`

### Worst Case D — PC와 모바일 동시 진행
- **왜 발생:** 한 기기에서 완료했지만 다른 기기 화면이 오래됐다.
- **서버 감지:** 문제 진입/제출/보상 직전에 최신 완료 상태 재조회.
- **방어 로직:** 프론트의 미완료 표시를 권위값으로 사용하지 않는다.
- **UI:** `이미 완료한 미션입니다. 현재 진행 상태를 갱신합니다.`

### 테스트
신규 사용자, 후보 0개, 자정 경계, 두 기기 동시 접속, 서버 조회 실패.

## 2. 코드 풀이 및 제출

### 사용자 화면/흐름
문제에서 `풀기`를 누르면 코드 에디터가 열리고, `제출하기`를 누르면 버튼이 잠기며 `채점 중` 상태가 표시된다.

### 정상 흐름
`POST 제출 → 사용자/문제/미션 유효성 검증 → TASK_ATTEMPTS PENDING 저장 → commit → 202 Accepted → 백그라운드 채점 → 결과 저장 → 클라이언트 결과 조회`

### Worst Case A — 제출 버튼을 0.01초 간격으로 연타
- **왜 발생:** 매크로, 더블클릭, 응답 지연.
- **주의:** `SELECT PENDING 없음 → INSERT`만으로는 동시성 안전하지 않다. 두 요청이 동시에 없음으로 판단할 수 있다.
- **방어 로직:** 제출 중복 정책과 보상 중복 정책을 분리한다. attempt를 여러 개 허용하더라도 최초 정답 보상 등 1회성 이벤트는 멱등하게 보호한다.
- **UI:** 버튼 잠금은 UX 보조 수단일 뿐 서버 방어를 대체하지 않는다.

### Worst Case B — 무한 루프/메모리 폭탄/시스템 접근 코드
- **서버 감지/방어:** Docker sandbox에 memory≈128MB, CPU≈0.5, network none, read-only, timeout 등을 적용한다.
- **주의:** `import os` 자체를 Docker가 차단하는 것이 아니다. 컨테이너 밖 자원 접근을 격리하는 것이 핵심이다.
- **UI:** `시간 초과`, `자원 초과`, `실행 오류`를 가능한 범위에서 구분한다.

### Worst Case C — 동시 30명 이상 제출
- **방어 로직:** PENDING을 먼저 commit하고 빠르게 202를 반환한다. Docker는 무제한 생성하지 않고 semaphore/queue로 동시 실행 수를 제한한다.
- **기술 주석:** FastAPI `BackgroundTasks`는 MVP 단일-worker에서 쓸 수 있지만 내구성 작업 큐가 아니다. 다중 worker, 서버 재시작 복구, 작업 유실 방지가 필요해지면 별도 durable queue 도입을 검토한다.
- **UI:** 일정 시간 이후 `채점이 평소보다 오래 걸리고 있어요.`로 전환한다.

### Worst Case D — 제출 직후 네트워크 단절
- **왜 발생:** 서버는 PENDING 저장/commit했지만 응답이 유실될 수 있다.
- **방어 로직:** 재접속 시 최근 attempt를 조회하여 PENDING/완료 상태를 복구한다.
- **다음 단계 영향:** 중복 attempt를 무조건 새로 만들지 않는다.

### DB/API 원칙
Docker 실행 중 DB transaction/row lock을 유지하지 않는다. PENDING 저장과 최종 결과 갱신은 각각 짧은 트랜잭션으로 분리한다.

### 테스트
더블클릭/매크로, 네트워크 단절, 무한루프, 메모리 초과, Docker daemon 장애, 대량 동시 제출.

## 3. 채점 및 결과 피드백

### 사용자 화면/흐름
정답/오답/실행 오류/시간 초과/자원 초과 등 결과를 확인한다. 시스템 오류는 오답과 구분해야 한다.

### Worst Case — 문제 자체의 test_cases 오류
- **왜 발생:** 잘못된 검증 데이터 때문에 올바른 코드도 실패한다.
- **서버/운영 감지:** 신고/운영 검증, 반복적인 이상 실패 등을 통해 확인한다.
- **방어 로직:** 문제가 잘못됐다고 확인되면 `TASKS.is_active=false`로 비활성화하고 대체 과제를 제공할 수 있다.
- **주의:** 자동 비활성화 임계치는 정해지기 전 `TBD`.
- **UI:** `현재 사용할 수 없는 문제입니다. 다른 문제로 교체합니다.`

## 4. 개별 정답 보상

### 사용자 화면/흐름
정답이면 축하 피드백과 함께 확정된 보상을 보여준다.

### Worst Case — 같은 쉬운 문제를 반복해 재화 파밍
- **왜 발생:** 동일 TASK를 여러 번 정답 처리할 수 있다.
- **핵심:** `TASK_ATTEMPTS`가 여러 개인 것과 보상이 여러 번 지급되는 것은 별개다.
- **방어 로직:** 정책이 `동일 사용자+동일 미션 문제 최초 정답 1회`라면 reward event/unique key/ledger 등으로 DB 수준 멱등성을 보장한다.
- **DB/API 영향:** 현재 ERD에 전용 reward ledger가 없다면 신규 ERD에서 확정한다.

## 5. 올클리어 판정 및 보상

### 사용자 화면/흐름
모든 오늘 문제를 완료하면 `오늘의 미션 완료`와 올클리어 보상 영역이 활성화된다.

### 정상 흐름
서버가 오늘 미션 전체와 완료 상태를 기준으로 올클리어를 판정한다. 프론트의 `3/3` 숫자만으로 확정하지 않는다.

### Worst Case A — 마지막 문제 두 개가 거의 동시에 정답
- **위험:** 두 처리 모두 `이제 전부 완료`라고 판단해 보상을 두 번 지급할 수 있다.
- **방어 로직:** 올클리어를 `사용자+날짜+reward_type` 같은 1회성 이벤트로 멱등 처리한다.

### Worst Case B — 보상 버튼 매크로 연타
- **방어 로직:** 첫 요청만 지급되고 같은 reward event 재요청은 기존 지급 결과를 반환하도록 설계한다.
- **주의:** 현재 존재하지 않는 `ATTENDANCES.daily_quest_completed` 같은 컬럼을 이미 있는 것처럼 사용하지 않는다.

### Worst Case C — 지급 commit 후 응답 유실
- **상황:** 서버에서는 balance 증가와 지급 상태가 commit됐지만 Wi-Fi가 끊긴다.
- **방어 로직:** 재요청 시 재지급하지 않고 서버의 지급 상태와 최신 잔액을 반환한다.
- **UI:** `오늘의 미션 보상은 이미 지급되었습니다. 현재 잔액을 불러왔어요.`
