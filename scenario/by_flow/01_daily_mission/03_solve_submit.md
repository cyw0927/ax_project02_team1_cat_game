# 03. 문제 풀이 및 제출

## 목적
사용자가 오늘의 복습 문제를 풀고 코드를 제출해 채점 가능한 시도를 생성하는 단계다. 이 단계에서는 **제출을 안전하게 기록하고 빠르게 응답하는 것**이 핵심이다.

## 정상 흐름
1. 사용자가 문제 상세를 연다.
2. 코드 작성.
3. 제출 클릭.
4. 서버가 사용자, TASK, 일일미션 대상 여부, TASK 활성 상태를 재검증한다.
5. 입력 검증 통과 시 TASK_ATTEMPTS에 PENDING 시도를 기록한다.
6. 짧은 DB 트랜잭션으로 commit한다.
7. 클라이언트에는 attempt_id와 채점 대기 상태를 반환한다.
8. 실제 Docker 실행은 DB 트랜잭션 밖에서 수행한다.

## 발생 가능한 변수

### A. 제출 버튼 연타
- **원인**: 응답 지연, 사용자가 제출 여부를 모름.
- **위험**: 동일 코드가 여러 attempt로 생성되고 채점 부하 및 보상 중복 가능.
- **감지**: 짧은 시간 내 동일 사용자·동일 task 제출 기록, 멱등키 정책이 있다면 키 중복.
- **해결**: 프론트 버튼 비활성화는 UX 보조일 뿐이다. 보상 단계에서는 같은 미션 문제에 대한 중복 지급을 반드시 차단한다. 제출 자체를 중복 금지할지 재풀이 허용할지는 별도 정책으로 결정한다.

### B. 제출 직후 네트워크 단절
- **경우 1**: 서버 저장 전 끊김 → attempt가 없을 수 있다.
- **경우 2**: DB commit 후 응답만 유실 → attempt는 존재한다.
- **해결**: 재접속 시 최근 attempt 조회로 상태를 복원한다. 사용자가 무조건 다시 제출하게 만들면 중복 attempt가 늘어난다.

### C. 빈 코드 또는 비정상 입력
- **원인**: 실수, 프론트 검증 우회, 악성 요청.
- **해결**: API에서 서버 측 입력 검증 후 Docker로 보내지 않는다.
- **TBD**: 코드 길이 제한, 허용 문자/파일 수 등 구체 수치.

### D. TASK가 제출 직전에 비활성화
- **해결**: 제출 수락 시점에 다시 active 여부를 검사한다. 화면을 오래 열어두었다는 이유로 예전 상태를 신뢰하지 않는다.

### E. 로그인/권한 정보가 만료
- **해결**: 사용자 ID를 body에서 신뢰하지 않고 최종 구현에서는 JWT 등 인증 컨텍스트에서 가져온다. 인증 실패 시 attempt를 생성하지 않는다.

### F. DB insert 실패
- **원인**: DB 장애, FK 불일치, 커넥션 문제.
- **해결**: rollback 후 채점 작업을 시작하지 않는다. 사용자는 재시도 가능 오류를 본다.

### G. 동일 사용자가 두 기기에서 동시에 제출
- **해결**: 각각의 attempt는 별도 기록될 수 있으나, 일일미션 진행/보상은 서버의 권위 상태를 기준으로 1회성 규칙을 적용한다.

## 트랜잭션 경계
- 검증 → attempt INSERT → commit까지 짧게 유지.
- Docker 컨테이너가 끝날 때까지 DB transaction을 열어두지 않는다.
- 오래 걸리는 외부 I/O와 row lock을 결합하지 않는다.

## UI
- 제출 전: `제출`
- 요청 중: 중복 클릭 방지 표시
- 202 수락 후: `채점 대기 중`
- 네트워크 실패: `제출 결과를 확인할 수 없습니다. 최근 제출을 확인해주세요.`가 단순 `제출 실패`보다 안전하다.

## DB/API 영향
- TASK_ATTEMPTS: user_id, task_id, submitted_code, status=PENDING, attempted_at 등.
- 최종 status 값 체계는 기존 미확정 항목이므로 임의 enum을 새로 만들지 않는다.
