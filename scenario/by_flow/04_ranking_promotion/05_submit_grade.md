# 05. 제출 및 채점

## 목적
승급전 문제의 제출을 서버가 수락하고 안전한 채점 흐름을 거쳐 통과 여부를 확정하는 단계다.

## 정상 흐름
1. 사용자가 현재 문제 코드를 제출한다.
2. 서버는 challenge가 IN_PROGRESS인지 확인한다.
3. 서버 현재 시각과 expires_at을 비교한다.
4. 제출 가능한 문제인지 확인한다.
5. 채점 작업을 생성/수행한다.
6. 결과에 따라 해당 RANK_CHALLENGE_TASKS.is_passed를 갱신한다.
7. 모든 필요한 문제 결과가 모이면 최종 판정 단계로 이동한다.

## 발생 가능한 변수
### A. 제출 버튼 연타
- 위험: 같은 문제 채점 중복, 상태 중복 갱신.
- 해결: 프론트 버튼 잠금은 보조 UX로만 사용하고 서버에서 중복 요청 영향을 제한한다.

### B. 제출 직후 네트워크 끊김
- 경우 1: 서버 수락 전 단절.
- 경우 2: 서버 수락 후 응답만 유실.
- 해결: 재접속 시 challenge/task 상태를 조회해 실제 서버 상태를 복원한다.

### C. 제출 순간 제한 시간 경과
- 쟁점: 요청 수락 시각 기준인지 채점 완료 시각 기준인지 정책이 필요하다.
- 정책: `TBD`. 구현 전 팀 합의 필요.

### D. 채점 timeout/메모리 초과/Docker 장애
- 시스템 오류를 곧바로 사용자 오답으로 취급하지 않는다.
- 재시도 정책은 `TBD`.
- 채점 중 DB 장기 transaction/row lock을 유지하지 않는다.

### E. 두 문제가 거의 동시에 채점 완료
- 위험: 최종 성공 판정 함수가 동시에 실행될 수 있음.
- 해결: 개별 결과 저장 후 최종 상태 전이는 별도 짧은 원자 처리로 보호한다.

### F. 이미 is_passed인 문제 재제출
- 허용 여부는 정책 `TBD`. 최소한 기존 통과 상태를 실수로 false로 되돌리지 않는다.
