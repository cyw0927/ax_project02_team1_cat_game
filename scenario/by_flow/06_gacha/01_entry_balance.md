# 가챠 1단계 — 진입 및 재화 확인

## 목적
사용자가 가챠 화면에 진입했을 때 현재 뽑기 가능 상태를 정확히 확인한다. 화면에 보이는 재화와 실제 서버 잔액이 다를 수 있으므로 이 단계에서부터 서버를 권위 상태로 사용한다.

## 정상 흐름
1. 사용자가 홈에서 가챠를 선택한다.
2. 서버에서 최신 사용자 재화와 보유 고양이 목록을 조회한다.
3. 실제 가챠 배너/풀 API가 존재한다면 활성 풀 정보를 조회한다.
4. 클라이언트는 서버가 반환한 상태만으로 뽑기 가능 여부를 표시한다.
5. 실제 가챠 API가 아직 미구현이면 화면은 `DEMO`임을 명확히 표시하고 실제 결제가 일어난 것처럼 표현하지 않는다.

## 발생 가능한 변수
### A. 재화 조회 실패
- 원인: 네트워크 단절, DB 장애, API 오류.
- 감지: 잔액 조회 요청 실패 또는 비정상 응답.
- 처리: 이전 화면에 남아 있던 잔액으로 뽑기를 허용하지 않는다.
- UI: `재화 정보를 불러오지 못했습니다. 다시 시도해주세요.`와 재시도 버튼.

### B. 화면 잔액은 충분하지만 실제 잔액은 부족함
- 원인: 다른 탭/기기에서 상점 구매 또는 다른 재화 사용이 먼저 발생.
- 감지: 실제 뽑기 요청 시 서버의 조건부 차감 실패.
- 처리: 서버 잔액으로 다시 판단한다.
- UI: 최신 잔액으로 갱신하고 `재화가 부족합니다.` 표시.

### C. 가챠 비용이 화면 로딩 이후 변경됨
- 원인: 운영 설정 변경 또는 향후 이벤트 정책.
- 처리: 클라이언트가 비용을 권위 값으로 보내지 않는다. 서버가 가진 최신 비용 기준으로 검증한다.
- 현재 비용/재화 종류/10회 뽑기 여부는 미확정이면 `TBD`.

### D. 보유 고양이 조회 실패
- 위험: 클라이언트가 신규/중복 여부를 잘못 판단할 수 있음.
- 처리: 중복 판단은 서버에서 수행하고, 보유 목록을 못 불러왔다면 결과 미리보기만으로 소유 상태를 단정하지 않는다.

## DB/API 영향
- `USERS.balance` 등 실제 확정된 재화 필드를 서버가 조회한다.
- `USER_CATS`는 결과 처리 시 신규/중복 판정의 참고 상태다.
- 가챠 전용 설정/풀/이력 테이블은 현재 확정되지 않았다면 문서에서 임의 추가하지 않는다.
