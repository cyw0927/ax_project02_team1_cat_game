# 가챠 7단계 — 하우징 연결

## 목적
가챠에서 확정된 보유 고양이가 하우징에 자연스럽게 이어지고, 캐시·asset 누락·동시 상태 변경 때문에 획득한 고양이가 사라진 것처럼 보이지 않게 한다.

## 정상 흐름
1. 가챠 결과 처리 후 사용자의 보유 고양이 상태가 서버에 반영된다.
2. 사용자가 하우징으로 이동한다.
3. 하우징은 `USER_CATS` 기준 최신 보유 목록을 다시 조회한다.
4. 지원되는 asset이 있는 고양이를 선택/배치할 수 있게 표시한다.
5. 실제 배치 위치 저장 정책이 있다면 하우징 도메인의 규칙을 따른다.

## 발생 가능한 변수
### A. 가챠 직후 하우징에 새 고양이가 안 보임
- 원인: 하우징 화면이 이전 보유 목록을 캐시함.
- 감지: 결과 화면에서는 지급 성공인데 하우징 목록에 없음.
- 처리: 하우징 진입 시 서버 최신 목록을 다시 조회하고 로컬 캐시를 권위 상태로 쓰지 않는다.

### B. USER_CATS 반영은 성공했지만 asset이 없음
- 원인: 신규 cat_id에 대응하는 이미지/스프라이트 미배포.
- 처리: 소유권은 정상으로 유지하고 명시적 fallback을 사용한다. 다른 고양이 asset을 그대로 써서 동일한 개체인 것처럼 오인시키지 않는다.
- 운영 대응: asset catalog/매핑 누락을 별도 오류로 기록한다.

### C. 같은 시점에 다른 기기에서 고양이 상태가 변경됨
- 현재 고양이 배치/활성 선택 규칙이 확정되지 않았다면 서버 최신 소유 목록만 동기화하고, 선택 충돌 규칙은 `TBD`.

### D. 중복 보유 허용 정책으로 바뀜
- 동일 cat_id 개체 여러 마리를 하우징에 각각 배치하려면 현 `USER_CATS`와 프론트 asset 식별 방식이 충분한지 검토해야 한다.
- 단순 cat_id 기준 렌더링만으로 개체를 구분할 수 없는 문제가 생길 수 있다.

### E. starter 고양이와 가챠 고양이 혼재
- starter 지급은 로그인/초기 진입 흐름이고 가챠 지급과 별도다.
- 하우징에서는 둘 다 최종적으로 사용자의 `USER_CATS` 목록으로 조회되지만, 획득 원인을 프론트가 임의 추정하지 않는다.

## UI
- 가챠 결과 화면에 `하우징에서 보기` 같은 이동 버튼을 둘 수 있다.
- 하우징 진입 후 새로 획득한 고양이를 강조할지 여부는 UX 정책이며 서버 소유 상태와 분리한다.
- asset 로드 실패 시 `고양이 정보를 불러오지 못함`과 `고양이를 소유하지 않음`을 구분한다.

## DB/API 영향
- 하우징은 최신 `USER_CATS` 조회 결과를 권위 상태로 사용한다.
- 별도 배치 엔티티가 고양이까지 관리할지 현재 스키마가 충분한지는 하우징 시나리오에서 추가 검토한다.

## 다음 흐름
가챠 흐름은 하우징으로 연결되며, 사용자는 홈으로 돌아가 학습/배틀/상점 등 다른 루프를 계속할 수 있다.

## 테스트
- 신규 고양이 뽑기 직후 하우징 진입
- 새로고침 없이 화면 전환
- asset 누락 cat_id
- 여러 기기 동시 조회
- starter + 가챠 고양이 동시 보유
- 향후 중복 보유 허용 시 개체 식별
