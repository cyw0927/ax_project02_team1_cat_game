# 가챠 2단계 — 뽑기 요청

## 목적
사용자가 뽑기 버튼을 눌렀을 때 요청을 한 번의 거래 단위로 식별하고, 버튼 연타·응답 유실·여러 기기 동시 요청 때문에 의도하지 않은 중복 결제가 발생하지 않도록 한다.

## 정상 흐름
1. 사용자가 1회 또는 향후 확정된 단위의 뽑기 버튼을 누른다.
2. 클라이언트는 요청 진행 중 상태를 표시한다.
3. 서버는 인증된 사용자, 활성 가챠 여부, 요청 형식, 최신 비용 정책을 검증한다.
4. 실제 구현에서 멱등 request id 정책이 확정되면 요청 단위를 식별한다.
5. 검증을 통과하면 비용 차감/결과 생성 단계로 이동한다.

## 발생 가능한 변수
### A. 버튼 연타
- 원인: 응답이 늦어 사용자가 버튼이 안 눌렸다고 판단.
- 위험: 의도하지 않은 여러 번의 결제와 여러 결과 생성.
- 감지: 매우 짧은 시간에 같은 사용자의 중복 요청 도착.
- 처리: 프론트 버튼 잠금은 UX 보조이며 서버 보호를 대체하지 않는다. 동일 거래 재전송과 실제 연속 뽑기를 구분할 수 있는 요청 식별 정책이 필요하다.

### B. 서버 처리는 끝났는데 HTTP 응답이 유실됨
- 원인: Wi-Fi 전환, 브라우저 종료, 프록시 timeout.
- 위험: 사용자가 실패한 줄 알고 다시 눌러 재결제.
- 처리: 동일 request id 재조회/재요청 시 이미 완료된 결과를 돌려줄 수 있어야 한다. 정확한 API와 이력 저장 구조는 현재 `TBD`.

### C. 두 기기에서 동시에 뽑기
- 원인: PC와 모바일 동시 사용.
- 위험: 둘 다 같은 이전 잔액을 보고 충분하다고 판단.
- 처리: 이 단계의 사전 조회가 아니라 실제 DB 차감 단계에서 잔액을 원자적으로 재검증한다.

### D. 사용자가 로그인 세션을 잃은 상태
- 감지: 인증 실패.
- 처리: 비용 차감/랜덤 결과 생성 전에 즉시 중단.
- UI: 다시 로그인하도록 안내하고, 실패한 요청을 성공처럼 애니메이션하지 않는다.

### E. 요청한 가챠 종류가 더 이상 유효하지 않음
- 원인: 이벤트 종료, 잘못된 id, 오래 열린 탭.
- 처리: 서버가 활성 상태를 재검증하고 거절한다.

## UI
- 처리 중에는 중복 클릭을 막고 `처리 중` 표시.
- 네트워크 오류와 잔액 부족을 구분.
- 결과 여부를 모르는 timeout 상황에서는 `다시 뽑기`보다 `결과 확인/재시도` 흐름을 우선한다.
