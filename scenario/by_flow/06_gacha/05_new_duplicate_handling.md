# 가챠 5단계 — 신규/중복 고양이 처리

## 목적
확정된 `cat_id`가 신규 획득인지 중복 결과인지 서버에서 판정하고, 확정된 비즈니스 규칙에 맞게 보유 상태를 갱신한다.

## 정상 흐름
1. 서버가 사용자의 현재 `USER_CATS`를 기준으로 결과 고양이 보유 여부를 확인한다.
2. 신규라면 확정된 소유 정책에 따라 `USER_CATS`에 반영한다.
3. 중복이라면 팀에서 확정한 중복 처리 정책을 적용한다.
4. 지급 결과를 거래 결과와 함께 확정한다.

## 발생 가능한 변수
### A. 같은 고양이가 동시에 두 요청에서 신규로 판정됨
- 원인: 두 가챠 요청이 거의 동시에 `USER_CATS`를 조회.
- 위험: 종류별 1마리 정책인데 중복 row가 생길 수 있음.
- 해결: 종류별 1마리만 허용할 경우 `(user_id, cat_id)` DB UNIQUE가 가장 강한 보호 수단이다. 하지만 현재 ERD에 이 UNIQUE가 확정돼 있지 않으므로 스키마 변경 여부를 먼저 결정한다.

### B. 중복 보유를 허용하는 게임 정책
- 이 경우 `(user_id, cat_id)` UNIQUE를 추가하면 안 된다.
- 현재 `USER_CATS` 구조가 개체 단위 고양이를 충분히 표현하는지도 재검토해야 한다.
- 따라서 DB 제약은 중복 정책 확정 이후 결정한다.

### C. 중복 결과를 마일리지로 자동 변환하고 싶음
- `USERS.mileage`가 있다는 사실만으로 이 규칙이 확정된 것은 아니다.
- 변환량, 상한, 사용처까지 팀 합의가 필요하다.
- 확정 전에는 `TBD`.

### D. 신규 지급 중 DB 오류
- 비용은 차감됐는데 소유권 반영이 실패하는 상황을 막아야 한다.
- 가챠 거래 전체의 트랜잭션/복구 전략과 함께 처리한다.

### E. starter 고양이가 가챠 풀에 포함됨
- 기본 주황 starter 지급과 가챠 획득은 별개의 흐름이다.
- starter를 가챠로 다시 뽑을 수 있는지 여부도 별도 정책이며 임의 확정하지 않는다.
