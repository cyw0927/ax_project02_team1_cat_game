# 가챠 흐름 시나리오

## 전체 흐름

`가챠 진입 → 재화 확인 → 뽑기 시도 → 비용 차감 → 결과 생성 → 신규/중복 고양이 처리 → 결과 반영 → 하우징 배치`

가챠는 확률형 보상 기능이므로 **확률·비용·천장·중복 처리 규칙을 프론트가 임의로 결정하면 안 된다.** 현재 서버에 실제 가챠 write API가 확정되어 있지 않다면 화면은 DEMO로 유지하고, 아래 정책 중 미정 항목은 전부 `TBD`로 둔다.

---

## 1. 가챠 진입

### 정상 흐름
1. 홈에서 가챠 선택.
2. 서버에서 사용자 최신 재화와 보유 고양이 목록을 조회.
3. 가챠 배너/풀 정보를 표시.

### 변수
- 재화 조회 실패: 뽑기 가능 상태로 추정하지 않는다.
- 보유 고양이 조회 실패: 결과 중복 여부를 클라이언트에서 임의 판정하지 않는다.
- 가챠 배너 정책 미확정: DEMO 화면에서 실제 확률처럼 오인되는 숫자를 노출하지 않는다.

---

## 2. 재화 확인

### 목적
뽑기 비용을 지불할 수 있는지 확인한다.

### 변수
- 화면에 보이는 잔액은 충분하지만 다른 탭에서 상점 구매가 먼저 발생.
- 비용이 운영 중 변경됨.
- 1회/10회 뽑기 비용 정책 미정.

### 해결
실제 차감 시 서버 DB의 최신 잔액과 서버가 가진 비용을 기준으로 판정한다. 클라이언트 표시 값은 참고용이다.

## 3. 뽑기 요청

### 정상 흐름
1. 사용자가 뽑기 버튼 클릭.
2. 서버가 가챠 가능 상태와 최신 잔액 확인.
3. 비용 차감과 결과 생성 흐름 시작.

### 변수 A. 버튼 연타
- 위험: 사용자가 의도하지 않은 다중 결제.
- 해결: UI 버튼 잠금 + 서버 요청 단위 멱등성 검토.
- 단, 사용자가 실제로 연속 뽑기를 의도할 수 있으므로 멱등키는 요청 단위를 구분해야 한다.

### 변수 B. 응답 타임아웃
- 서버에서는 뽑기가 완료됐는데 클라이언트는 실패로 인식할 수 있다.
- 가챠는 결과가 되돌릴 수 없는 거래이므로 request_id 기반 결과 재조회가 특히 중요하다.

### 변수 C. 두 기기 동시 뽑기
- 둘 다 이전 잔액을 보고 시작할 수 있음.
- 비용 차감은 조건부 원자 UPDATE 등으로 잔액 음수를 방지해야 한다.

---

## 4. 비용 차감

### 원칙
상점과 동일하게 `balance >= cost` 조건이 포함된 원자 차감을 우선 검토한다.

### 변수
- 차감 성공 후 결과 저장 실패.
- 결과는 저장됐지만 고양이 지급 실패.
- HTTP 응답만 유실.

### 해결
비용 차감, 가챠 결과 기록, 보상 지급을 하나의 논리적 거래로 다뤄야 한다. 실제 구현을 위해 별도 gacha history/result 테이블이 필요한지 스키마 검토가 필요하다. 현재 19-table ERD에는 전용 가챠 결과 이력이 없으므로 임의 구현 전에 결정한다.

---

## 5. 결과 생성

### 중요 원칙
- 랜덤 결과는 서버가 권위 상태로 생성.
- 클라이언트 JavaScript가 `Math.random()`으로 실제 보상 cat_id를 결정하지 않는다.
- 확률표는 서버/운영 설정을 기준으로 한다.

### 변수
- 특정 rarity의 후보 고양이가 0마리.
- 비활성/삭제된 고양이가 확률 풀에 남음.
- 확률 합계 오류.
- 서버 재시도 시 결과가 새로 굴러가 사용자가 다른 결과를 받음.

### 해결
하나의 request_id가 생성한 결과는 재시도해도 동일해야 한다. 결과 생성과 저장 순서를 설계해 재굴림을 방지한다.

## 6. 신규 고양이 획득

### 정상 흐름
결과 cat_id를 사용자가 아직 보유하지 않았다면 USER_CATS에 추가한다.

### 변수
- 동일 고양이를 두 가챠 요청이 거의 동시에 신규로 판정.
- 현재 USER_CATS에 `(user_id, cat_id)` DB UNIQUE가 없다면 application-level 사전 체크만으로 race 가능.

### 해결 후보
고양이를 종류별 1마리만 보유하는 정책이라면 `(user_id,cat_id)` unique 제약을 추가하는 것이 안전하다. 그러나 중복 보유 자체를 허용할 계획이면 구조가 달라지므로 먼저 비즈니스 정책 확정 필요.

## 7. 중복 고양이 결과

### 가능한 정책
- 중복 보유 허용
- 마일리지/조각/별도 재화로 변환
- 자동 재뽑기
- 보상 없음

현재 최종 정책이 확정되지 않았다면 전부 `TBD`다. 특히 ERD의 `mileage`가 존재한다고 해서 중복 고양이를 자동 마일리지로 바꾸는 규칙이 확정된 것은 아니다.

### UI
정책이 정해지면 신규 획득과 중복 변환 결과를 명확히 다르게 표시.

---

## 8. 결과 화면

### 정상 흐름
- 획득 고양이의 이름/희귀도/이미지 표시.
- 서버에 기록된 결과를 그대로 렌더링.
- 결과 애니메이션이 실패해도 보상 자체는 이미 서버에 기록된 상태일 수 있음.

### 변수
- 애니메이션 중 새로고침.
- 이미지 asset 로드 실패.
- 응답 유실 후 재접속.

### 해결
가챠 결과 이력 조회가 가능하면 마지막 완료 request를 다시 보여줄 수 있다. asset 오류는 지급 실패로 처리하지 않는다.

---

## 9. 하우징 연결

### 정상 흐름
1. 신규 고양이가 USER_CATS에 반영.
2. 하우징 진입 시 최신 보유 고양이 목록 조회.
3. 선택한 고양이를 하우징에 표시/배치.

### 변수
- 뽑기 직후 하우징 화면의 캐시가 오래됨.
- asset 매핑이 아직 없는 신규 cat_id.

### 해결
하우징 진입 시 서버 목록 재조회. asset 미지원 시 명시적 fallback을 사용하되 다른 고양이인 것처럼 오인시키지 않는다.

---

## 10. 기본 주황 고양이와 가챠의 관계

게임 시작 시 주황 starter 고양이(cat_id=1)를 기본 제공하는 규칙과 가챠는 분리한다. starter 지급을 가챠 결과처럼 처리하지 않는다. 신규 사용자는 가챠를 하지 않아도 최소 한 마리로 게임을 시작할 수 있어야 한다.
