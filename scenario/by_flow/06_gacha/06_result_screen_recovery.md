# 가챠 6단계 — 결과 화면과 복구

## 목적
서버에서 이미 확정된 가챠 결과를 사용자에게 보여주고, 애니메이션 실패·새로고침·응답 유실이 발생해도 실제 지급 결과를 잃지 않도록 한다.

## 정상 흐름
1. 서버가 확정된 가챠 결과를 반환한다.
2. 클라이언트는 해당 `cat_id`, 이름, 희귀도, 이미지 등 서버 결과에 대응하는 정보를 표시한다.
3. 신규/중복 여부와 처리 결과를 구분해 보여준다.
4. 애니메이션 종료 후 보유 고양이/재화 상태를 최신 서버 값으로 동기화한다.

## 발생 가능한 변수
### A. 결과 애니메이션 도중 새로고침
- 실제 거래가 완료됐다면 결과를 다시 생성하면 안 된다.
- 거래 이력/마지막 완료 결과 조회가 가능하면 동일 결과를 복원한다.
- 이력 API/테이블은 현재 `TBD`.

### B. 서버는 성공했지만 HTTP 응답이 유실됨
- 사용자는 실패로 오인할 수 있다.
- 동일 request id를 이용한 상태 조회 또는 재요청 시 기존 결과를 반환하는 구조가 필요하다.
- 다시 랜덤을 굴리거나 다시 차감해서는 안 된다.

### C. 이미지 asset 로드 실패
- 원인: 신규 고양이 asset 미배포, 경로 오류, 네트워크 문제.
- 실제 보상 지급과 UI asset 로드는 분리한다.
- fallback 이미지를 쓰더라도 다른 고양이로 오인되지 않게 이름/cat_id 기반 정보는 정확히 표시한다.

### D. 결과 화면을 닫은 직후 보유 목록이 예전 상태
- 원인: 클라이언트 캐시.
- 처리: 결과 완료 후 또는 다음 화면 진입 시 서버 최신 보유 목록을 다시 조회한다.

### E. 중복 변환 결과와 재화 잔액이 화면에서 어긋남
- 서버가 반환한 최종 잔액을 우선한다.
- 프론트에서 `기존 잔액 - 비용 + 중복보상`을 따로 계산해 권위 값으로 사용하지 않는다.

## UI 원칙
- 연출 실패를 거래 실패로 표시하지 않는다.
- `획득 완료`, `중복 처리`, `결과 확인 불가` 상태를 구분한다.
- 결과 확인 불가 상황에서는 추가 결제를 유도하기보다 복구/조회 버튼을 우선한다.

## DB/API 영향
- 이상적인 복구를 위해서는 거래 식별자와 확정 결과를 조회할 수 있어야 한다.
- 현재 전용 가챠 이력 스키마가 확정되지 않았으므로 구현 전 결정 필요.
