# 가챠 3단계 — 비용 차감과 거래 경계

## 목적
가챠 비용을 최신 서버 잔액 기준으로 한 번만 차감하고, 결과 생성/보상 지급과의 정합성을 유지한다.

## 정상 흐름
1. 서버가 최신 비용을 결정한다.
2. 사용자 잔액이 충분한지 DB에서 다시 확인한다.
3. 조건부 원자 UPDATE 등으로 `balance >= cost`일 때만 차감한다.
4. 차감 실패 시 결과 생성 단계로 가지 않는다.
5. 차감 이후 결과 생성/지급과의 거래 경계를 확정된 설계에 따라 처리한다.

## 권장 원칙
상점과 동일하게 단순 읽기 후 차감하지 말고 조건이 포함된 원자 UPDATE를 우선 검토한다.

```sql
UPDATE USERS
SET balance = balance - :cost
WHERE id = :user_id
  AND balance >= :cost;
```

영향 행이 0이면 잔액 부족 또는 사용자 상태 이상으로 판단하고 실패 처리한다.

## 발생 가능한 변수
### A. 동시에 두 번 차감 시도
- 원인: 두 기기 또는 요청 연타.
- 처리: 각각의 UPDATE가 DB 최신 잔액을 기준으로 판정하므로 잔액 음수를 방지한다.

### B. 차감 성공 후 결과 생성 전에 서버 오류
- 위험: 돈만 빠지고 결과가 없음.
- 해결: 가챠 거래를 어디까지 하나의 DB 트랜잭션으로 묶을지, 또는 거래/결과 이력을 어떤 순서로 영속화할지 구현 전에 결정해야 한다.
- 현재 19-table ERD에는 가챠 전용 거래 이력 테이블이 확정돼 있지 않으므로 임의로 추가하지 않는다.

### C. 결과 저장 성공 후 HTTP 응답 유실
- 처리: 거래가 성공했다면 재요청으로 다시 차감하지 말고 기존 결과를 복원해야 한다. 이를 위해 request id/결과 이력 정책이 필요하다.

### D. 비용 설정이 잘못되어 음수/0원
- 처리: 서버 설정 검증 단계에서 차단. 0원 가챠를 의도할 경우 별도 정책으로 명시한다.

### E. 실제 사용 재화가 여러 종류가 됨
- 현재 `balance`, `mileage`가 존재한다고 해서 가챠 통화가 확정된 것은 아니다.
- 어떤 재화를 차감할지는 `TBD`이며 프론트가 임의 선택하지 않는다.

## DB 잠금 원칙
- 긴 외부 작업을 위해 USERS row lock을 오래 유지하지 않는다.
- 가챠 결과 생성이 DB 내부의 짧은 계산이라면 거래와 함께 처리할 수 있지만, 외부 서비스 호출이 생긴다면 트랜잭션 경계를 다시 설계한다.

## UI
- 차감 성공이 확정되기 전까지 결과 확정 애니메이션을 시작하지 않는다.
- 잔액 부족 시 최신 잔액으로 갱신한다.
