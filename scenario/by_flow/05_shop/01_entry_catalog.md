# 01. 상점 진입 및 상품 목록 확인

## 목적
사용자가 상점에 들어왔을 때 실제 구매 가능한 상품과 최신 재화 상태를 서버 기준으로 확인하는 단계다.

## 정상 흐름
1. 사용자가 홈 또는 보상 완료 화면에서 상점을 선택한다.
2. 서버가 사용자 존재 여부와 최신 재화 잔액을 확인한다.
3. 서버가 현재 제공 가능한 ITEMS 목록을 조회한다.
4. 필요하면 사용자 INVENTORIES를 함께 읽어 보유 여부/수량을 표시한다.
5. 클라이언트는 카테고리, 상품명, 가격, 보유 상태를 렌더링한다.

## 발생 가능한 변수
### A. 상품 목록 조회 실패
- 원인: DB 연결 오류, API 오류.
- 해결: 빈 상점으로 위장하지 않는다.
- UI: `상품 정보를 불러오지 못했습니다.` + 재시도.

### B. 잔액 조회 실패
- 위험: 화면에 이전 잔액이 남아 구매 가능처럼 보일 수 있다.
- 해결: 잔액을 권위 있게 확인하지 못하면 거래 확정 버튼을 제한하고 재조회한다.

### C. 오래 열린 탭
- 원인: 다른 기기/탭에서 구매 또는 보상 발생.
- 해결: 목록 화면 숫자는 참고값으로 취급하고 실제 구매 시 서버가 다시 잔액을 검증한다.

### D. 상품 정보가 중간에 변경됨
- 원인: 운영 중 가격/카테고리/판매 여부 변경.
- 해결: 화면에 보이던 값이 아니라 구매 시점의 서버 데이터를 최종 기준으로 사용한다.

### E. 존재하지만 현재 판매 정책이 불명확한 아이템
- 현재 ITEMS 스키마에는 판매 기간/재고량 같은 필드가 확정되지 않았다.
- 해당 개념을 문서에서 임의로 추가하지 않고 필요 시 `TBD`로 둔다.

## UI
- 현재 서버 기준 잔액
- 카테고리별 상품 목록
- 가격
- 보유 여부/수량
- 조회 실패와 상품 0개 상태를 구분

## DB/API 영향
- USERS.balance 조회
- ITEMS 조회
- INVENTORIES 조회
- 조회 API는 상태를 변경하지 않아야 한다.

## 동시성/재시도
목록 조회는 여러 번 실행돼도 구매 상태를 바꾸지 않는다. 다른 기기에서 상태가 바뀌면 다음 조회에 최신값이 반영되어야 한다.
