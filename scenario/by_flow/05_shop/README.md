# 상점 흐름 시나리오

## 전체 흐름

`상점 진입 → 재화 확인 → 아이템 탐색 → 구매 시도 → 잔액/아이템/동시성 검증 → 구매 완료 → 인벤토리 반영 → 하우징 적용`

상점은 화면에서 가격을 보여주는 기능보다 **실제 잔액 차감과 인벤토리 증가를 원자적으로 처리하는 것**이 핵심이다.

---

## 1. 상점 진입

### 정상 흐름
1. 홈 또는 재화 획득 화면에서 상점 선택.
2. 서버에서 활성 아이템 목록 조회.
3. 사용자 최신 balance 및 인벤토리 조회.
4. 카테고리/가격/보유 여부 표시.

### 변수
- 아이템 목록 조회 실패: 빈 상점으로 위장 금지.
- 사용자 잔액 조회 실패: 구매 버튼을 임의로 활성화하지 않는다.
- 클라이언트에 표시된 잔액이 오래됨: 구매 시 서버에서 재검증.
- 아이템 가격이 화면을 연 뒤 변경됨: 서버 현재 price가 최종 기준.

---

## 2. 아이템 탐색

### 목적
사용자가 구매 가능한 가구/장식 등을 확인한다.

### 변수
- 삭제/비활성 아이템을 오래된 탭에서 클릭.
- 이미 보유한 단일성 아이템을 다시 구매.
- 수량형 아이템의 최대 보유량 정책.
- wallpaper/floor처럼 동일 카테고리에서 하나만 적용 가능한 아이템.

보유 제한 정책이 확정되지 않았다면 UI에서 임의 제한하지 않고 `TBD`로 둔다.

---

## 3. 구매 시도

### 정상 흐름
1. 사용자가 구매 버튼 클릭.
2. 서버는 user와 item 존재 여부 확인.
3. 서버 현재 가격 기준으로 잔액 차감 시도.
4. 성공하면 INVENTORIES 수량 증가.
5. 한 트랜잭션에서 commit.
6. 최신 balance/보유 상태 반환.

### 재화 차감 원칙
명시적 `SELECT ... FOR UPDATE`보다 가능한 경우 다음과 같은 조건부 원자 UPDATE를 우선한다.

```sql
UPDATE users
SET balance = balance - :price
WHERE id = :user_id
  AND balance >= :price;
```

영향 row가 0이면 잔액 부족으로 처리한다.

### 변수 A. 구매 버튼 연타
- 원인: 더블클릭, 네트워크 지연.
- 위험: 사용자가 의도하지 않게 여러 개 구매.
- 해결: 수량형 상품에서 중복 구매 자체가 정상일 수 있으므로 무조건 멱등 처리할 수는 없다. 주문 단위 idempotency key를 도입할지 정책 검토.
- UI 버튼 잠금은 보조 수단.

### 변수 B. 잔액 100, 가격 80인 상태에서 두 구매 동시 요청
- 단순 read(balance=100) 후 각각 80 차감하면 음수/정합성 오류 가능.
- 조건부 UPDATE를 쓰면 하나가 성공한 뒤 다른 하나는 조건 실패.

### 변수 C. 잔액 차감 성공 후 인벤토리 증가 실패
- 해결: 같은 DB 트랜잭션에서 처리하여 rollback.
- 사용자는 돈만 빠지고 아이템이 없는 상태가 되면 안 된다.

### 변수 D. 인벤토리 row가 이미 존재
- 해결: `(user_id,item_id)` unique + UPSERT 증가 방식 활용 가능.

### 변수 E. 가격 조작
- 클라이언트가 price를 보내더라도 신뢰하지 않는다. item_id로 DB price 조회.

---

## 4. 구매 완료 응답

### 정상 흐름
- 최신 잔액
- 구매 item
- 최신 quantity 또는 inventory 상태
을 반환.

### 변수
- DB commit은 성공했지만 HTTP 응답 유실.
- 사용자가 재시도해 두 번째 구매가 발생할 수 있음.

### 해결 후보
- 구매 요청 idempotency key를 둘지 결정.
- 도입 전에는 UI에서 네트워크 실패 시 `구매 여부 확인 중` 후 inventory/balance 재조회하는 방식이 안전.

---

## 5. 인벤토리 반영

### 정상 흐름
구매 성공 후 인벤토리에서 해당 가구를 확인할 수 있다.

### 변수
- 화면 캐시가 오래됨.
- 다른 기기에서 구매/배치.
- quantity와 실제 배치 수량 불일치.

### 해결
하우징 진입 시 서버 인벤토리/배치 정보를 다시 조회한다.

---

## 6. 하우징 적용

### 정상 흐름
1. 상점에서 구매한 아이템이 인벤토리에 존재.
2. 하우징에서 배치 요청.
3. 서버는 해당 아이템 보유 여부/수량을 확인.
4. PLACED_OBJECTS에 위치 저장.

### 변수
- 보유 수량보다 더 많은 배치 요청.
- 상점 구매 직후 다른 탭에서 동시 배치.
- wallpaper/floor 교체.

배치 수량 경쟁은 현재 housing 정책과 함께 결정해야 한다.

---

## 7. 품절/재고 개념

현재 ITEMS 스키마에는 전역 재고량이 명시되어 있지 않다. 따라서 `품절`을 문서에서 임의로 구현하지 않는다. 향후 한정 수량 상점이 필요하면 별도 스키마/정책이 필요하다.

---

## 8. 환불/판매

현재 기본 흐름에 환불/되팔기 기능은 없다. 필요 시 별도 정책으로 정의해야 하며 현재 구매 API의 역연산을 임의로 만들지 않는다.

---

## 테스트 체크리스트

- 정상 구매
- 잔액 정확히 가격과 동일
- 잔액 부족
- 존재하지 않는 item
- 두 동시 구매
- 버튼 연타
- 인벤토리 기존 row UPSERT
- 차감 후 DB 오류 rollback
- 응답 유실 후 재조회
- 가격 변경 후 오래된 화면에서 구매
- 보유 수량보다 많은 하우징 배치
