# 07. 구매 완료 및 화면 상태 갱신

## 목적
DB에서 구매가 성공한 뒤 사용자의 화면을 서버 최신 상태와 일치시키고, 재화·보유 수량·다음 행동을 명확히 보여준다.

## 정상 흐름
1. 구매 transaction commit 성공.
2. 서버가 최신 balance와 해당 inventory quantity를 반환한다.
3. 클라이언트는 응답 기준으로 재화 표시를 갱신한다.
4. 구매한 상품의 보유 수량/보유 상태를 갱신한다.
5. 사용자는 계속 쇼핑하거나 하우징으로 이동한다.

## 발생 가능한 변수

### A. 성공 응답이 늦게 도착
- 원인: 네트워크 지연.
- 위험: 이후 요청의 최신 상태를 과거 응답이 덮어쓸 수 있음.
- 해결: 거래 응답 순서 관리 또는 중요 상태 재조회. 화면 숫자만으로 서버 상태를 역산하지 않는다.

### B. 연속 구매
- 원인: 여러 상품을 빠르게 구매.
- 해결: 매 요청마다 서버 최신 balance 기준으로 구매 가능 여부를 다시 판정한다.
- UI: 첫 구매 성공 후 남은 재화를 즉시 갱신하되 다음 구매의 최종 판정은 서버.

### C. 다른 기기에서 동시에 구매
- 화면의 balance/quantity는 쉽게 오래될 수 있다.
- 해결: 현재 거래 성공 응답 또는 서버 재조회 결과가 권위 상태.

### D. 구매 완료 애니메이션 중 페이지 이동
- DB 상태에는 영향 없음.
- 복귀 시 최신 inventory/balance를 재조회하면 된다.

### E. 이미 보유한 단일성 아이템
- 일부 아이템이 여러 개 보유 가능한지, 한 번만 구매 가능한지는 카테고리별 정책 `TBD`.
- 정책 확정 전 프론트가 임의로 재구매를 막지 않는다.

## UI
- `구매 완료` 메시지.
- 실제 서버가 반환한 차감 후 balance 표시.
- 보유 수량 또는 보유 상태 갱신.
- `계속 쇼핑`, `하우징에서 배치` 같은 다음 행동 제공 가능.

## DB/API 영향
이 단계에서는 새 거래를 만들기보다 직전 transaction 결과를 사용자에게 전달한다.

필요하면 다음을 재조회한다.
- USERS.balance
- INVENTORIES
- ITEMS 최신 정보

## 중복 요청 주의
결과 화면 재렌더링이나 새로고침 자체가 구매 API를 다시 호출하면 안 된다. `구매 실행`과 `구매 결과 표시`를 분리한다.
