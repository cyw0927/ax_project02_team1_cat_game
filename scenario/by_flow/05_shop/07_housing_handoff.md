# 07. 인벤토리 확인 및 하우징 연결

## 목적
상점 구매 결과를 하우징에서 실제 사용할 수 있는 보유 상태로 연결하고, 구매 성공과 배치 성공을 서로 다른 단계로 관리한다.

## 정상 흐름
1. 상점 구매가 commit되어 INVENTORIES에 반영된다.
2. 사용자가 하우징으로 이동한다.
3. 하우징 진입 시 서버에서 최신 inventory와 현재 PLACED_OBJECTS를 조회한다.
4. 사용자가 보유 아이템을 선택해 배치 요청을 보낸다.
5. 서버가 실제 보유 여부/수량을 확인한다.
6. 유효하면 PLACED_OBJECTS에 위치 정보를 저장한다.
7. wallpaper/floor처럼 적용 방식이 다른 카테고리는 해당 하우징 API 정책을 따른다.

## 발생 가능한 변수
### A. 구매 직후 아이템이 하우징에 안 보임
- 원인: 오래된 inventory 캐시, 화면 상태 갱신 누락.
- 해결: 하우징 진입/새로고침 시 서버 inventory 재조회.
- UI: 단순히 구매를 다시 유도하지 말고 보유 상태부터 확인한다.

### B. 보유 수량보다 많이 배치
- 원인: 여러 탭에서 동시 배치, 클라이언트 조작.
- 해결: 배치 시 서버가 실제 보유 수량과 이미 배치된 수량을 다시 검증해야 한다.
- 정확한 다중 배치 허용 규칙은 housing 정책과 함께 `TBD`.

### C. 다른 기기에서 배치/삭제
- 현재 화면의 배치 상태가 오래될 수 있다.
- 서버 상태를 권위값으로 사용하고 재진입 시 다시 읽는다.

### D. wallpaper/floor 교체
- 아이템 보유와 현재 적용 상태를 분리한다.
- 새 항목 적용 시 기존 적용값을 어떻게 처리할지는 기존 housing 규칙을 따른다.

### E. 구매 성공했지만 하우징 배치 실패
- 구매 transaction을 되돌리지 않는다.
- 아이템은 inventory에 남고 배치만 실패한 상태가 정상적으로 표현되어야 한다.

### F. 위치 데이터 오류
- position_data 형식/범위 검증이 필요하다.
- 상세 충돌 규칙이 확정되지 않은 경우 임의로 고급 물리 규칙을 문서에서 확정하지 않는다.

## DB/API 영향
- INVENTORIES: 구매 보유량의 권위 상태
- PLACED_OBJECTS: 실제 배치된 객체
- USERS.wallpaper_item_id / floor_item_id: 해당 카테고리 적용 상태

## UI
- `구매 완료`와 `배치 완료`를 구분
- 보유 아이템 목록
- 배치 가능/이미 배치 상태
- 실패 시 inventory를 잃은 것처럼 보이지 않게 최신 상태 표시

## 다음 흐름
`상점 구매 → 인벤토리 → 하우징 배치 → 저장 → 재접속 시 복원`

사용자는 배치하지 않고 다시 상점/홈으로 돌아갈 수도 있다.

## 테스트
- 구매 후 즉시 하우징 이동
- inventory 캐시 오래됨
- 동시 배치
- 보유 수량 초과 배치
- wallpaper/floor 교체
- 배치 실패 후 inventory 유지
- 재접속 후 배치 복원
- 다른 기기에서 배치 변경
