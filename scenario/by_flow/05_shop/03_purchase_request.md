# 03. 구매 요청 및 서버 재검증

## 목적
사용자의 구매 의사를 서버에 전달하고, 화면 값이 아니라 서버의 최신 사용자/상품/가격/잔액을 기준으로 거래 가능 여부를 다시 판정한다.

## 정상 흐름
1. 클라이언트가 user와 item_id를 포함한 구매 요청을 보낸다.
2. 서버가 사용자 존재 여부를 확인한다.
3. 서버가 item_id로 현재 상품과 가격을 조회한다.
4. 구매 제한이 확정된 경우 해당 조건을 검사한다.
5. 최신 잔액으로 구매 가능 여부를 판단한다.
6. 조건을 만족하면 `04_atomic_purchase.md`의 원자적 거래 단계로 넘어간다.

## 발생 가능한 변수
### A. 존재하지 않는 사용자/아이템
- 해결: 거래 시작 전 실패. balance나 inventory를 변경하지 않는다.

### B. 가격 변경
- 원인: 사용자가 상점 화면을 연 뒤 운영 데이터 변경.
- 해결: 서버 최신 price를 기준으로 처리한다.
- UI: 필요하면 `가격이 변경되었습니다`와 최신 가격을 보여준다.

### C. 잔액 부족
- 클라이언트 화면에 충분해 보여도 다른 탭에서 이미 사용했을 수 있다.
- 서버 최신 balance가 권위 상태다.

### D. 버튼 연타/네트워크 재시도
- 수량형 상품에서는 두 번 구매가 실제 의도인지 재시도인지 구분하기 어렵다.
- 주문 단위 idempotency key 도입 여부는 `TBD`.
- 프론트 버튼 잠금은 보조 수단일 뿐 서버 정합성 보장이 아니다.

### E. 악의적 요청
- 클라이언트가 price, quantity, balance를 조작해 보내도 서버가 신뢰하지 않는다.

## API/DB 영향
이 단계의 검증만으로 balance를 먼저 차감하지 않는다. 실제 변경은 하나의 짧은 transaction에서 처리한다.
