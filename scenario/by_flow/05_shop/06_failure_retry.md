# 06. 구매 실패, 재시도, 중복 요청 처리

## 목적
구매가 실패하거나 결과가 불명확할 때 사용자가 재화를 잃지 않고, 재시도가 중복 구매로 이어지지 않도록 처리한다.

## 실패 유형
### A. 검증 단계 실패
- 사용자 없음
- 아이템 없음
- 잔액 부족
- 확정된 구매 제한 위반

이 경우 DB 변경 없이 실패해야 한다.

### B. transaction 중 실패
- 잔액 차감 이후 inventory 반영 실패
- DB 예외/제약 위반

같은 transaction에서 rollback해 일부 상태만 남지 않도록 한다.

### C. commit 후 응답 유실
- 서버에는 구매 완료, 클라이언트는 결과를 모름.
- 단순히 같은 구매 요청을 바로 재전송하면 두 번째 정상 구매가 될 수 있다.
- 우선 최신 balance/inventory를 재조회해 상태를 확인한다.

### D. 버튼 연타
- 클라이언트 버튼 비활성화는 UX 보조 수단이다.
- 서버는 각 요청의 거래 정합성을 독립적으로 보장해야 한다.
- 동일 의도 재시도와 실제 2개 구매를 구분하려면 idempotency key가 필요할 수 있으며 현재 `TBD`다.

### E. 네트워크 timeout
- timeout 자체가 DB rollback을 의미하지 않는다.
- 서버 처리 완료 여부를 재조회해야 한다.

## UI 원칙
- `잔액 부족`, `상품 없음`, `서버 오류`, `결과 확인 필요`를 같은 오류 메시지로 합치지 않는다.
- 결과 불명확 시 `다시 구매`보다 `구매 상태 확인`을 우선한다.
- 실패한 거래를 프론트에서 임의 성공 처리하거나 잔액을 수동 보정하지 않는다.

## 장애 문의 시 확인 정보
1. user_id
2. item_id
3. 요청 시각
4. 서버 응답/오류
5. transaction commit 여부
6. 현재 balance
7. 현재 inventory quantity
8. idempotency/request id가 있다면 해당 값
