# 06. 구매 실패와 rollback

## 목적
구매 과정 중 어느 단계에서 실패하더라도 잔액과 인벤토리가 서로 어긋나지 않도록 하고, 사용자가 실패 원인을 명확히 이해할 수 있게 한다.

## 주요 실패 유형

### A. 잔액 부족
- 원인: 실제 서버 balance가 가격보다 적음.
- 발생 상황: 화면에는 충분해 보였지만 다른 탭/기기에서 이미 사용했을 수 있음.
- 감지: 조건부 UPDATE 영향 row 0건.
- 해결: 어떤 변경도 commit하지 않고 실패 응답.
- UI: `재화가 부족합니다.` + 최신 잔액 표시.

### B. 상품이 존재하지 않음
- 원인: 잘못된 item_id, 삭제/비활성화된 상품, 오래된 화면.
- 해결: 서버의 최신 ITEMS 상태를 기준으로 구매 거절.
- UI: `현재 구매할 수 없는 상품입니다.`

### C. 화면 가격과 서버 가격 불일치
- 원인: 오래 열린 상점 화면, 운영 중 가격 변경.
- 해결: 서버 가격을 권위 값으로 사용. 차이가 있으면 최신 가격을 반환하고 사용자가 다시 확인하도록 할 수 있다.
- 정책: 자동으로 새 가격 구매를 진행할지 재확인을 요구할지는 `TBD`.

### D. 잔액 차감 후 inventory 갱신 실패
- 위험: 돈만 빠짐.
- 해결: 같은 DB 트랜잭션이면 전체 rollback.

### E. inventory 증가 성공 후 commit 실패
- 해결: commit 자체가 실패하면 transaction 전체가 반영되지 않은 것으로 취급하고 서버 상태 재조회.

### F. commit 성공 후 응답 유실
- 위험: 실제 구매 성공인데 사용자는 실패로 인식.
- 해결: 재접속/재조회 시 balance와 inventory를 권위 상태로 확인. 동일 구매 요청 재처리 정책은 멱등키 도입 여부 `TBD`.

### G. DB deadlock/일시 오류
- 원인: 동시 트랜잭션 충돌 가능.
- 해결: 트랜잭션을 짧게 유지. 안전한 경우 제한된 재시도 가능하나 횟수/정책은 `TBD`.

## 금지되는 처리
- 먼저 balance를 commit하고 별도 transaction에서 inventory 증가.
- 프론트에서 balance를 임의 차감한 뒤 서버 실패를 무시.
- 실패했는데 성공 애니메이션 먼저 확정.
- 단순 SELECT balance 후 Python에서 계산하고 별도 save하여 동시 구매를 허용.

## 오류 분류
- 4xx 성격: 상품 없음, 잔액 부족, 구매 불가 상태 등 사용자 요청 조건 불충족.
- 5xx 성격: DB 장애, 예기치 않은 서버 오류.
- 네트워크 오류: 서버 처리 여부를 클라이언트가 모르는 상태일 수 있으므로 `실패 확정`과 구분.

## 사용자 재시도
- 잔액 부족 → 최신 잔액 확인 후 종료.
- 상품 상태 변경 → 카탈로그 재조회.
- 네트워크 유실 → 서버 상태 재조회 후 실제 구매 여부 판단.
- 서버 오류 → 재시도 가능하되 중복 구매 방지 정책 필요.
