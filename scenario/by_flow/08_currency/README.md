# 재화 흐름 시나리오

## 전체 흐름

재화는 독립된 하나의 화면이라기보다 여러 기능을 연결하는 공통 축이다.

`일일 미션 / 학습 / 배틀 / 승급전 성공 → 재화 획득 → 잔액 반영 → 상점 또는 가챠 사용 → 하우징 결과로 연결`

재화에서 가장 중요한 것은 **중복 지급 방지, 잔액 음수 방지, 동시 요청 정합성, 실패 시 rollback, 서버 권위 상태 유지**다.

---

## 1. 재화 획득원

현재 흐름에서 재화 획득 후보는 다음과 같다.

- 일일 미션 개별 정답 보상
- 일일 미션 올클리어 보상
- 일반 학습 정답 보상
- 배틀 결과 보상
- 승급전 성공 보상
- 로그인/출석 보상(기존 출석 정책과 연결)

각 보상 액수는 별도 비즈니스 결정이다. 확정되지 않은 값을 이 문서에서 임의로 지정하지 않는다.

---

## 2. 보상 자격 판정

### 정상 흐름
1. 원인이 되는 이벤트가 서버에서 확정된다.
2. 해당 이벤트가 보상 조건을 만족하는지 확인한다.
3. 이전에 같은 보상을 지급했는지 확인한다.
4. 미지급이면 재화 증가.
5. 지급 사실과 잔액 변경을 commit.

### 핵심 원칙
`정답/승리/성공 이벤트가 여러 번 조회되는 것`과 `재화를 여러 번 지급하는 것`을 분리한다.

---

## 3. 중복 지급

### 발생 원인
- 사용자가 제출 버튼을 여러 번 누름.
- 클라이언트가 응답을 못 받고 재요청.
- Background 작업이 재실행.
- 두 서버 요청이 동시에 같은 보상 자격을 확인.
- 결과 화면을 다시 열 때 보상 함수가 다시 호출.

### 해결 원칙
1회 지급이어야 하는 보상은 **고유한 지급 식별자**가 필요하다.

예:
- attendance: `(user_id, check_in_date)` UNIQUE
- 일일 미션 문제 보상: `user + date + mission_task + reward_type` 형태의 멱등 식별 필요
- battle 보상: `room + user + reward_type`
- promotion 보상: `challenge + user + reward_type`

현재 19-table ERD에 모든 reward ledger가 존재하는 것은 아니므로 실제 구현 전 스키마 추가 여부를 결정해야 한다.

### 피해야 할 방식
```text
SELECT 지급 여부
→ 없음 확인
→ 재화 증가
→ 지급 기록
```
만 하고 동시성 보호가 없으면 두 요청이 모두 `없음`을 볼 수 있다.

---

## 4. 재화 증가

### 원칙
가능하면 DB에서 원자적으로 증가시킨다.

```sql
UPDATE users
SET balance = balance + :reward
WHERE id = :user_id;
```

Python에서 기존 balance를 읽고 `balance + reward`를 계산한 뒤 저장하는 방식은 동시 보상에서 lost update가 생길 수 있다.

### 변수
- 동시에 학습 보상과 배틀 보상이 들어옴.
- 일부 보상 지급 기록 저장 실패.

### 해결
재화 증가와 해당 지급 기록을 하나의 짧은 트랜잭션으로 묶는 방향을 우선한다.

---

## 5. 재화 사용 — 상점

### 정상 흐름
1. 서버가 최신 item price 확인.
2. 조건부 차감.
3. 인벤토리 증가.
4. commit.

```sql
UPDATE users
SET balance = balance - :price
WHERE id = :user_id
  AND balance >= :price;
```

영향 row가 0이면 잔액 부족.

### 왜 이 방식인가
불필요한 `FOR UPDATE`를 줄이면서 잔액 음수를 방지할 수 있다.

---

## 6. 재화 사용 — 가챠

가챠도 최신 서버 비용 기준으로 원자 차감해야 한다.

### 추가 위험
가챠는 비용 차감 후 결과가 만들어지는 거래라서, 응답 유실 후 사용자가 재시도할 때 **비용만 두 번 차감되고 결과도 두 번 생성**되는 문제가 특히 중요하다.

### 해결 후보
- request_id/idempotency key
- 결과 이력 저장
- 같은 request_id 재요청 시 기존 결과 반환

실제 가챠 API/이력 테이블은 아직 확정되지 않았다면 TBD.

---

## 7. 잔액 부족

### 발생 상황
- 상점 구매
- 가챠
- 두 기기 동시 사용

### 정상 처리
- HTTP 요청 시 서버가 최신 잔액으로 판단.
- 잔액 부족이면 변경 없이 실패.
- 클라이언트는 서버가 반환한 최신 잔액으로 UI 갱신.

### 잘못된 처리
프론트에서 `현재 화면 balance >= price`만 검사하고 구매를 확정하면 안 된다.

---

## 8. 화면 잔액과 DB 잔액 불일치

### 원인
- 다른 탭/기기에서 구매.
- Background reward가 방금 지급.
- 오래 열린 화면.
- 네트워크 응답 순서 역전.

### 해결
- DB가 권위 상태.
- 중요한 거래 전 서버 재검증.
- 거래 성공 응답의 최신 잔액으로 화면 갱신.
- 화면 간 이동 시 필요하면 profile/balance 재조회.

---

## 9. 거래 실패와 rollback

### 사례 A. 상점
`차감 성공 → inventory 증가 실패`

같은 트랜잭션이라면 전체 rollback.

### 사례 B. 보상
`보상 지급 기록 성공 → balance 증가 실패`

동일 트랜잭션으로 처리해 불일치 방지.

### 사례 C. Docker 채점
채점이 오래 걸리는 동안 재화 transaction을 열어두지 않는다. 채점 확정 후 별도 짧은 보상 transaction 시작.

---

## 10. 재화 종류

현재 USERS에는 `balance`, `mileage`가 존재하지만 이것만으로 최종 경제 구조가 확정된 것은 아니다.

### 결정 전 금지
- `balance = 골드`, `mileage = 가챠 전용`이라고 임의 확정
- 중복 고양이를 mileage로 자동 변환
- 1골드=1가챠 같은 숫자 확정

팀 합의 전에는 각각의 사용처/획득처를 `TBD`로 표시한다.

---

## 11. 출석과 재화

기존 요구에는 `매일 자정 이후 첫 로그인 시 100원 지급` 규칙이 있다.

### 변수
- 같은 날 로그인 두 번.
- 두 기기 동시 첫 로그인.
- 자정 경계.
- 기기 날짜 조작.

### 해결
- 서버 날짜 기준.
- ATTENDANCES `(user_id, check_in_date)` UNIQUE로 중복 기록 방지.
- 출석 row 생성과 100 지급을 짧은 transaction에서 일관되게 처리.
- 로그인 통합 전 수동 check-in API만으로 최종 요구가 완성된 것은 아님.

---

## 12. 감사/거래 이력

현재 단순 USERS.balance만 있으면 `왜 이 잔액이 되었는지` 완전히 복원하기 어렵다.

향후 필요 시 currency ledger/reward history 도입을 검토할 수 있다. 다만 현재 ERD 19개 제한/설계와 충돌할 수 있으므로 새 테이블을 임의 추가하지 않고 팀 합의 후 migration 계획을 세운다.
