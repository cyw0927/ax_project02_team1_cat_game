# 02. 지급 자격 및 중복 지급 방지

## 목적
같은 정답, 같은 배틀 결과, 같은 승급 성공, 같은 출석 보상이 여러 번 처리되어도 재화는 한 번만 지급되게 한다.

## 정상 흐름
1. 보상 원천 식별자를 확인한다.
2. 같은 사용자와 같은 보상 원천에 대해 이미 지급됐는지 확인한다.
3. 미지급이면 지급 가능 상태로 진행한다.
4. 이미 지급됐다면 새 지급 없이 기존 결과와 최신 잔액을 반환한다.

## 발생 가능한 변수
### A. 제출 버튼 연타
- 같은 attempt 또는 같은 미션 문제에 대한 요청이 중복된다.
- 해결: 프론트 버튼 잠금은 UX일 뿐이며 서버 멱등성이 필요하다.

### B. commit 후 응답 유실
- 실제 지급은 성공했지만 사용자는 실패로 인식하고 재요청할 수 있다.
- 해결: 같은 식별자로 재요청하면 기존 지급 상태를 반환한다.

### C. 두 서버 요청이 동시에 미지급 상태를 읽음
- 단순 `SELECT 없음 → INSERT/UPDATE`만 사용하면 둘 다 지급할 수 있다.
- 해결: UNIQUE 제약, 조건부 INSERT/UPDATE, 멱등 키 등 스키마에 맞는 DB 보호가 필요하다.

### D. 출석 보상
- 현재 확정 규칙은 ATTENDANCES `(user_id, check_in_date)` UNIQUE를 활용할 수 있다.
- 서버 날짜 기준으로 하루 1회만 성공한다.

### E. 일일 미션/배틀/승급전
- 현재 19-table ERD에 범용 지급 이력 테이블이 없다.
- 실제 멱등 식별 저장 구조는 `TBD`이며 임의 테이블을 추가하지 않는다.

## 보상 식별 후보
- 일일 미션: `user + date + mission_task + reward_type`
- 배틀: `room + user + reward_type`
- 승급전: `challenge + user + reward_type`
- 출석: `user + check_in_date`

## UI
- 이미 받은 보상에 대해 신규 획득 애니메이션을 반복하지 않는다.
- 서버가 기존 지급으로 판단한 경우 최신 잔액만 동기화한다.
