# 01. 재화 획득 이벤트 발생

## 목적
일일 미션, 학습, 배틀, 승급전 성공, 출석 등 각 기능에서 보상 조건이 확정된 뒤 재화 흐름을 시작한다.

## 정상 흐름
1. 원인이 되는 기능에서 결과가 서버 기준으로 확정된다.
2. 서버가 해당 결과가 보상 대상인지 판단한다.
3. 보상 종류와 원천 식별자를 만든다.
4. 다음 단계인 중복 지급 검증으로 전달한다.

## 발생 가능한 변수
### A. 결과는 확정됐지만 보상 정책이 아직 미정
- 예: 배틀 승패별 지급액, 승급전 성공 보상 수치.
- 해결: 지급 액수는 임의 생성하지 않고 정책값이 확정될 때까지 `TBD`로 둔다.

### B. 클라이언트가 직접 보상 이벤트를 요청
- 원인: 프론트에서 정답/승리 여부를 판단해 보상을 호출.
- 위험: 요청 조작으로 임의 획득 가능.
- 해결: 보상 이벤트의 원인은 서버가 이미 확정한 결과여야 한다.

### C. Background 채점 결과 도착이 늦음
- 해결: Docker 실행 동안 재화 transaction을 열어두지 않는다. 채점 완료 후 별도의 짧은 보상 transaction을 시작한다.

### D. 같은 결과가 여러 번 조회됨
- 결과 조회 횟수와 보상 횟수를 분리한다. 결과를 다시 조회했다고 다시 보상 이벤트를 새로 만들지 않는다.

## DB/API 영향
- USERS.balance 등 실제 재화 필드 변경 전 단계다.
- 원천 객체 예: TASK_ATTEMPTS, ROOMS, RANK_CHALLENGES, ATTENDANCES.
- 범용 reward ledger는 현재 확정 스키마에 없으므로 추가 여부는 `TBD`.

## UI
- 아직 보상 commit 전이면 화면에서 잔액을 먼저 증가시키지 않는다.
- 채점/결과 확정 중이면 `보상 계산 중` 등 결과와 지급 상태를 구분한다.
