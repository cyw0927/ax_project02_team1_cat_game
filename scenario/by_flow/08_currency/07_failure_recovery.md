# 07. 실패·롤백·응답 유실 복구

## 목적
재화 거래 도중 일부 단계가 실패하거나 commit 이후 응답이 유실돼도 잔액과 실제 지급/소비 결과가 서로 어긋나지 않게 한다.

## 대표 실패 유형
### A. 상점 차감 성공 → inventory 반영 실패
- 같은 transaction이면 전체 rollback.
- 사용자는 재화를 잃지 않아야 한다.

### B. 보상 지급 기록 성공 → balance 증가 실패
- 같은 transaction으로 묶어 둘 다 rollback.

### C. commit 성공 → HTTP 응답 유실
- 가장 위험한 유형 중 하나.
- 사용자는 실패로 생각하고 같은 요청을 재시도할 수 있다.
- 해결: 지급/사용 요청에 멱등 식별이 필요하며 재요청 시 기존 결과를 반환한다.

### D. 가챠 비용 차감 후 결과 응답 유실
- 같은 draw가 다시 실행되어 비용과 결과가 중복될 수 있다.
- request_id/idempotency key 및 결과 이력 저장 후보를 검토한다.
- 실제 구조는 `TBD`.

### E. DB timeout/일시 장애
- commit 여부가 불명확할 수 있다.
- 클라이언트에서 임의로 성공/실패를 추정하지 않고 서버 상태 재조회 경로가 필요하다.

## 장애 복구 원칙
1. DB 상태가 권위값이다.
2. 화면 로컬 잔액만으로 복구하지 않는다.
3. 동일 요청을 재실행할 때는 멱등성을 먼저 확인한다.
4. 부분 성공을 허용하지 않는 거래는 짧은 transaction으로 묶는다.
5. Docker 채점 등 장기 작업과 재화 transaction은 분리한다.

## UI
- 결과 불명확: `처리 상태를 확인 중입니다.`
- 재조회 후 성공 확인: 기존 성공 결과 표시.
- 재조회 후 미처리 확인: 안전하게 재시도 가능.
- 잔액을 클라이언트 추정값으로 보정하지 않는다.

## 추적 정보
- user_id
- 원천 이벤트/room/challenge/attempt 식별자
- request_id가 있다면 해당 값
- transaction 결과
- 현재 서버 balance
- 지급/소비 결과 존재 여부
