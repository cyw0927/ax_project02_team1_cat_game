# 배틀 9단계 — 재화 획득 연결

## 목적
배틀 결과 보상으로 확정된 재화를 사용자 잔액에 반영하고, 이후 상점/가챠 소비 흐름으로 안전하게 넘긴다.

## 정상 흐름
1. 배틀 결과가 FINISHED로 확정된다.
2. 사용자별 보상 자격과 지급량을 계산한다.
3. 아직 지급되지 않은 보상만 재화에 반영한다.
4. 서버가 최신 잔액을 반환한다.
5. UI는 획득 재화와 총 잔액을 표시한다.
6. 사용자는 홈, 상점 또는 가챠로 이동할 수 있다.

## 발생 가능한 변수

### 변수 A. 결과 화면 재조회로 동일 보상 재지급 시도
- 원인: 새로고침, 재접속, API 재시도.
- 해결: `결과를 본 횟수`와 `보상 지급 횟수`를 분리한다. 이미 지급된 보상은 다시 잔액에 더하지 않는다.

### 변수 B. 잔액 증가 직후 응답 유실
- 원인: DB commit 이후 네트워크 단절.
- 위험: 사용자가 보상을 못 받았다고 생각해 재시도.
- 해결: 재요청 시 지급 여부를 먼저 확인하고 최신 서버 잔액을 반환한다.

### 변수 C. 배틀 보상 지급과 상점 구매가 동시에 발생
- 원인: 여러 탭/기기에서 동시 작업.
- 해결: 각 재화 쓰기를 짧은 원자 트랜잭션으로 처리하고 상점은 조건부 잔액 차감으로 최종 검증한다.

### 변수 D. 화면에 표시된 잔액과 DB 잔액이 다름
- 원인: 다른 탭에서 구매/보상, 오래된 클라이언트 상태.
- 해결: 서버 잔액을 권위 값으로 사용하고 성공 응답 시 UI를 다시 동기화한다.

### 변수 E. 보상 액수/종류가 아직 미확정
- 원인: 등수별 보상, 참가 보상, 승리 보상 정책 미결정.
- 해결: 수치와 통화 종류는 `TBD`. 문서나 프론트에서 임의 확정하지 않는다.

### 변수 F. 일부 보상 구성요소만 반영됨
- 원인: 하나의 배틀 결과에서 여러 보상 타입을 줄 경우 트랜잭션 경계 오류.
- 해결: 팀이 보상 구성 단위를 확정한 후 같은 지급 이벤트에 속한 항목의 원자성 범위를 정의한다.

## DB/동시성 원칙
- 재화 증가는 지급 여부 확인과 함께 서버에서 처리한다.
- 긴 외부 작업은 없다. 짧은 DB 쓰기로 끝낸다.
- 중복 지급 방지는 프론트 버튼 비활성화가 아니라 DB/서버 멱등성으로 보장한다.
