# 배틀 8단계 — 종료 및 결과 보상

## 목적
배틀을 한 번만 `FINISHED`로 확정하고, 최종 점수/순위를 기준으로 사용자별 보상 자격을 계산하되 중복 지급을 막는다.

## 정상 흐름
1. 종료 조건이 충족된다.
2. 서버는 room.status가 아직 IN_PROGRESS인지 확인한다.
3. 최종 점수 반영 범위를 확정한다.
4. ROOM을 FINISHED로 전환한다.
5. 최종 개인/팀 결과와 순위를 계산한다.
6. 사용자별 보상 자격을 계산한다.
7. 아직 지급되지 않은 보상만 지급한다.
8. 결과 화면에 순위, 점수, 지급 결과를 표시한다.

## 발생 가능한 변수

### 변수 A. 종료 요청이 두 번 이상 실행
- 원인: 버튼 연타, timeout 처리와 수동 종료 경쟁, 재시도.
- 해결: FINISHED 전환을 멱등하게 처리한다. 이미 FINISHED면 종료 로직을 새로 시작하지 않고 기존 결과를 반환한다.

### 변수 B. 마지막 채점 결과와 종료가 동시에 도착
- 원인: 제한 시간 직전 제출의 채점 완료.
- 핵심 결정: 제출 시각 기준인지 채점 완료 시각 기준인지에 따라 점수 인정 여부가 달라진다.
- 해결: 정책 확정 전 `TBD`. 임의로 점수를 넣거나 버리지 않는다.

### 변수 C. PENDING/RUNNING 채점이 남은 상태에서 종료 조건 도달
- 해결: 종료 즉시 결과를 확정할지, 인정 가능한 제출의 채점을 기다릴지 정책 필요. 장시간 DB lock으로 기다리지 않는다.

### 변수 D. 결과 화면을 새로고침할 때 보상 지급 로직이 다시 실행
- 위험: 중복 재화 지급.
- 해결: 결과 조회와 보상 쓰기를 분리하고, 동일 room/user/reward 종류의 중복 지급을 서버/DB에서 차단해야 한다.

### 변수 E. 여러 서버 요청이 같은 사용자 보상을 동시에 지급
- 원인: background 처리와 결과 조회 트리거 경쟁.
- 해결: 보상 이벤트에 대한 멱등 식별 또는 DB unique 전략이 필요하다. 현재 ERD에 전용 battle reward 테이블이 없다면 구현 전 스키마 결정을 해야 한다.

### 변수 F. 일부 사용자 지급 후 중간 오류
- 원인: DB 오류, 트랜잭션 경계 문제.
- 해결: 한 사용자 단위 보상 반영은 원자적으로 처리하고, 재시도 시 이미 지급된 사용자는 건너뛴다.

### 변수 G. 팀전 결과 동률
- 원인: 동일 점수.
- 해결: 동률 처리/순위 결정 규칙은 `TBD`.

### 변수 H. 참가 중 이탈한 사용자 보상
- 원인: 중도 연결 끊김, 이탈 정책.
- 해결: 참가 보상/승리 보상 자격 조건은 비즈니스 룰 `TBD`.

## DB/트랜잭션 원칙
- FINISHED 상태 전이는 짧게 처리한다.
- Docker/PENDING 채점을 기다리며 ROOM lock을 유지하지 않는다.
- 재화 지급과 지급 완료 표시는 같은 사용자 보상 단위에서 원자적으로 처리해야 한다.

## UI
- 최종 점수와 순위는 서버 결과 사용.
- `보상 처리 중`과 `보상 없음`을 구분한다.
- 재접속/새로고침 후에도 동일 결과가 다시 표시되어야 한다.
