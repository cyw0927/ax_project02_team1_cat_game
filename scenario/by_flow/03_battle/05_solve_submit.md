# 배틀 5단계 — 문제 풀이 및 제출

## 목적
IN_PROGRESS 상태에서 참가자가 ROOM_TASKS 순서에 따라 문제를 풀고 제출하며, 제출 결과가 이후 점수 계산의 근거가 되도록 한다.

## 정상 흐름
1. 서버가 현재 방의 문제 순서와 사용 가능한 문제를 제공한다.
2. 참가자가 코드를 작성한다.
3. 제출 요청을 보낸다.
4. 서버는 사용자가 해당 방 참가자인지, 방이 IN_PROGRESS인지, 해당 TASK가 방 문제인지 재검증한다.
5. 제출 기록을 PENDING으로 짧게 저장/commit한다.
6. Docker 채점은 DB 트랜잭션 밖에서 실행한다.
7. 최종 채점 결과가 확정되면 점수 반영 단계로 넘긴다.

## 발생 가능한 변수

### 변수 A. 여러 참가자가 동시에 제출
- 원인: 정상적인 경쟁 상황.
- 해결: 각 제출은 독립 attempt로 처리한다. Docker 동시 실행 수는 semaphore/queue로 제한하되 DB row lock으로 대기시키지 않는다.

### 변수 B. 같은 사용자가 같은 문제를 반복 제출
- 원인: 오답 후 재시도 또는 버튼 연타.
- 해결: 반복 풀이 허용 여부와 점수 인정 횟수는 분리한다. attempt가 여러 개 생겨도 점수는 확정된 규칙에 따라 멱등하게 반영한다.

### 변수 C. 제출 직전 또는 직후 게임 종료
- 원인: 제한 시간, 모든 문제 완료, 관리자/방장 종료 등.
- 핵심 쟁점: `제출 요청 도착 시각` 기준으로 인정할지 `채점 완료 시각` 기준으로 인정할지 미정.
- 해결: 팀이 기준을 확정하기 전까지 `TBD`. 구현에서 임의 판단하지 않는다.

### 변수 D. 제출 저장 후 네트워크 끊김
- 원인: Wi-Fi 단절, 브라우저 종료.
- 해결: attempt 조회 또는 방 재접속 시 제출 상태를 복원한다. 동일 코드를 자동 재제출해 중복 attempt를 만드는 동작은 피한다.

### 변수 E. Docker 대기열이 길어짐
- 원인: 동시 제출 폭증.
- 해결: 무제한 컨테이너 생성 금지. PENDING 저장 후 빠르게 응답하고 제한된 실행 슬롯에서 순차 처리한다.
- UI: 가능하면 `제출됨/채점 대기/채점 중`을 구분한다.

### 변수 F. 무한루프, 메모리 초과, 과도한 출력
- 해결: 해당 컨테이너만 timeout/메모리/output limit으로 종료한다. 다른 배틀 참가자나 DB를 함께 실패시키지 않는다.

### 변수 G. TASK가 중간에 비활성화됨
- 해결: 게임 시작 후 문제 유지 여부는 정책이 필요하다. 최소한 제출 시 서버가 room-task 관계와 유효 상태를 확인한다.

## DB/동시성 원칙
- 제출 기록 저장과 Docker 실행을 같은 트랜잭션으로 묶지 않는다.
- ROOM row lock을 Docker 실행 동안 유지하지 않는다.
- 점수 반영은 채점 결과 확정 후 별도 짧은 쓰기로 처리한다.
