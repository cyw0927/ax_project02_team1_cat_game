# 배틀 1단계 — 진입 및 방 목록 확인

## 목적
사용자가 홈에서 배틀로 진입한 뒤 현재 참가 가능한 방의 최신 상태를 확인한다. 이 단계의 핵심은 화면에 보이는 정보가 실제 참가 가능 여부의 최종 판단값이 아니라는 점이다.

## 정상 흐름
1. 사용자가 홈에서 `배틀`을 선택한다.
2. 클라이언트가 방 목록을 요청한다.
3. 서버는 ROOM의 상태와 현재 참가자 수를 조회한다.
4. 클라이언트는 방 제목, 상태, 현재 인원, 최대 인원 등을 표시한다.
5. 사용자가 참가할 방을 선택하면 `방 참가` 단계로 이동한다.

## 발생 가능한 변수

### 변수 A. 방 목록 조회 실패
- 원인: 네트워크 단절, 서버 오류, DB 연결 오류.
- 감지: 요청 자체가 실패하거나 정상 응답을 받지 못한다.
- 해결: 빈 배열로 위장하지 않는다. `방이 없음`과 `조회 실패`를 분리한다.
- UI: `방 목록을 불러오지 못했습니다. 다시 시도해주세요.`와 재시도 버튼.
- 다음 영향: 최신 상태를 확인할 수 없으므로 참가 단계로 진행시키지 않는다.

### 변수 B. 방 목록이 비어 있음
- 원인: 실제 WAITING 방이 없음, 모든 방이 종료됨, 운영 초기 상태.
- 감지: 서버 조회는 성공했지만 표시 가능한 방이 0개.
- 해결: 오류가 아니라 정상 상태로 취급한다.
- UI: `참가 가능한 방이 없습니다.`를 표시하고 방 생성 기능이 있다면 진입점을 제공한다.

### 변수 C. 목록에는 WAITING인데 클릭 순간 게임이 시작됨
- 원인: 다른 사용자가 목록 조회 이후 방을 시작함.
- 감지: 참가 API에서 최신 room.status를 다시 확인한다.
- 해결: 목록 데이터를 믿고 참가시키지 않는다. 서버 참가 검증을 권위 상태로 둔다.
- UI: `이미 시작된 방입니다.` 후 목록 최신화.

### 변수 D. 인원수가 남아 보이지만 실제 마지막 자리를 다른 사용자가 먼저 차지함
- 원인: 여러 사용자가 동시에 동일 방을 보고 참가 요청.
- 감지: 방 참가 트랜잭션 안에서 현재 참가자 수를 다시 확인한다.
- 해결: 참가 단계의 짧은 직렬화로 정원 초과를 방지한다.
- UI: `정원이 찼습니다.` 후 인원수 갱신.

### 변수 E. FINISHED 방이나 잘못된 상태의 방이 캐시되어 표시됨
- 원인: 오래 열린 탭, 느린 polling, 클라이언트 캐시.
- 감지: 서버 최신 room.status와 화면 상태가 다름.
- 해결: 참가 시 서버 상태 재검증, 결과에 따라 UI를 최신 상태로 교체.

## API/DB 영향
- 읽기 단계에서는 긴 트랜잭션이나 row lock이 필요하지 않다.
- 참가 가능 여부를 목록 응답만으로 확정하지 않는다.
- 실제 상태 전이는 다음 `방 참가` 단계에서 처리한다.

## 동시성/재시도
- 동일 사용자가 목록 조회를 여러 번 하는 것은 문제없다.
- polling/WebSocket 방식은 팀 결정에 따라 선택하되, 재연결 후에는 서버 최신 상태를 전체 동기화할 수 있어야 한다.
