# 배틀 7단계 — 연결 끊김 및 재접속

## 목적
브라우저 새로고침, Wi-Fi 단절, 탭 종료 등으로 클라이언트 연결이 끊겨도 서버의 배틀 상태를 기준으로 사용자가 다시 현재 위치를 복원할 수 있게 한다.

## 정상 복구 흐름
1. 사용자가 다시 배틀 화면에 진입한다.
2. 서버에서 사용자의 현재 ROOM_PARTICIPANTS 상태를 조회한다.
3. ROOM.status, current_score, is_ready, 참가자 목록, 현재 문제 진행 상태를 다시 불러온다.
4. WAITING이면 대기실, IN_PROGRESS면 게임 화면, FINISHED면 결과 화면으로 복원한다.
5. 클라이언트의 오래된 로컬 상태는 서버 상태로 덮어쓴다.

## 발생 가능한 변수

### 변수 A. Ready=true인 상태에서 연결 끊김
- 원인: Ready 후 브라우저 종료/네트워크 단절.
- 해결: 연결 여부와 Ready 상태를 동일 개념으로 취급하지 않는다. 연결 끊김 사용자의 Ready를 유지/해제할지는 비즈니스 정책 `TBD`.

### 변수 B. 게임 도중 연결 끊김
- 원인: Wi-Fi 전환, 모바일 네트워크 변경, 브라우저 종료.
- 해결: participant와 점수는 서버에 남긴다. 자동 패배/퇴장 여부는 정책 미정이면 `TBD`.
- UI: 재접속 시 `게임 상태를 복원하는 중입니다.` 후 최신 상태 반영.

### 변수 C. 연결 끊긴 사이 게임이 종료됨
- 해결: 재접속 후 IN_PROGRESS 화면으로 되돌리지 않고 FINISHED 결과 화면으로 이동한다.

### 변수 D. 연결 끊긴 사이 점수가 변경됨
- 원인: 이미 제출한 채점 결과가 뒤늦게 확정됨.
- 해결: 로컬 점수가 아니라 서버 current_score를 다시 읽는다.

### 변수 E. WebSocket 재연결은 됐지만 일부 이벤트를 놓침
- 위험: 이벤트만 이어받으면 중간 상태가 누락될 수 있다.
- 해결: reconnect 시 전체 room snapshot을 한 번 다시 조회한 뒤 실시간 이벤트를 이어받는다.

### 변수 F. 여러 탭/기기에서 동시에 같은 배틀 재접속
- 원인: PC와 모바일 동시 접속.
- 해결: 서버 상태는 하나의 권위 상태로 유지한다. 입력 충돌을 어떻게 제한할지는 별도 정책 `TBD`.

### 변수 G. 서버 프로세스 재시작
- 원인: 배포, 장애.
- 해결: ROOM/ROOM_PARTICIPANTS/점수처럼 DB에 저장된 상태는 복원 가능해야 한다. 메모리에서만 유지한 실시간 상태가 있다면 재구성 전략이 필요하다.

## API/DB 영향
- 재접속은 먼저 읽기/동기화 문제로 본다.
- 복원을 위해 새 participant를 중복 생성하지 않는다.
- 기존 room_id/user_id 참가 상태를 조회해 이어간다.
