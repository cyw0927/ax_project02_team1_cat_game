# 배틀 2단계 — 방 참가

## 목적
선택한 방에 사용자를 참가시키되 정원, 방 상태, 중복 참가를 서버에서 최종 검증한다.

## 정상 흐름
1. 사용자가 참가 버튼을 누른다.
2. 서버는 해당 ROOM row를 짧게 `FOR UPDATE`로 잠근다.
3. room 존재 여부, `WAITING` 상태, 현재 인원 < 최대 인원, 기존 참가 여부를 확인한다.
4. 조건을 모두 만족하면 ROOM_PARTICIPANTS를 생성한다.
5. 즉시 commit 후 lock을 해제한다.
6. 참가 성공 응답 후 대기실/Ready 단계로 이동한다.

## 발생 가능한 변수

### 변수 A. 마지막 1자리에 두 명이 동시에 참가
- 원인: 두 요청이 거의 동시에 같은 현재 인원을 보고 들어옴.
- 위험: 단순 count 후 insert라면 정원을 초과할 수 있다.
- 감지/해결: ROOM row를 짧게 잠근 뒤 상태와 정원을 같은 트랜잭션에서 재검증한다. 먼저 lock을 얻은 요청만 마지막 자리를 차지한다.
- UI: 실패한 사용자는 `정원이 찼습니다.`를 본다.

### 변수 B. 이미 참가한 사용자가 같은 요청을 다시 보냄
- 원인: 버튼 연타, 응답 유실 후 재시도, 여러 탭.
- 감지: `(room_id, user_id)` 기존 참가 레코드를 조회하거나 DB unique 제약으로 막는다.
- 해결: 중복 participant를 만들지 않는다. 이미 참가 중이면 기존 참가 상태를 반환하는 방식도 검토 가능하다.
- UI: `이미 참가 중입니다.` 또는 기존 대기실로 복원.

### 변수 C. 참가 요청 도중 방이 시작됨
- 원인: 방장 시작 요청과 참가 요청 경쟁.
- 감지: lock 획득 후 room.status 재확인.
- 해결: `WAITING`이 아니면 참가 거절.

### 변수 D. 네트워크가 끊겨 성공 응답을 못 받음
- 원인: insert/commit은 성공했으나 응답 전달 실패.
- 위험: 사용자는 실패했다고 생각하고 다시 참가할 수 있다.
- 해결: 재요청 시 기존 참가 레코드를 확인하여 상태를 복원한다.

### 변수 E. 존재하지 않는 방
- 원인: 오래된 링크, 삭제/정리된 room_id, URL 직접 조작.
- 해결: 404 계열 오류로 구분하고 목록으로 돌아가게 한다.

### 변수 F. 팀전 team_name 값 이상
- 원인: 클라이언트 조작, 팀 배정 로직 미완성.
- 해결: 허용 팀 값과 배정 정책이 확정되면 서버에서 검증한다. 현재 미정이면 `TBD`로 유지한다.

## DB/트랜잭션 원칙
- 이 단계는 여러 조건을 한 순간에 판정해야 해서 `FOR UPDATE`가 정당화되는 예외다.
- lock은 참가 조건 확인과 insert/commit까지만 유지한다.
- 이후 Ready 대기나 네트워크 통신 동안 lock을 유지하지 않는다.
