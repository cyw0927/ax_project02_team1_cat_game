# 배틀 흐름 시나리오

## 전체 흐름

`배틀 진입 → 방 참가 → Ready → 게임 시작 → 문제 풀이 → 점수 경쟁 → 배틀 종료 → 결과 보상 → 재화 획득`

배틀은 여러 사용자가 같은 ROOM 상태를 공유한다. 따라서 단순 CRUD보다 **동시 참가, 정원 초과, 준비 상태 경쟁, 시작 시점, 연결 끊김, 점수 중복 반영, 종료 중복 실행**을 중점적으로 본다.

---

## 1. 배틀 진입 및 방 목록 확인

### 목적
사용자가 참가 가능한 방을 확인한다.

### 정상 흐름
1. 홈에서 배틀 선택.
2. 서버에서 방 목록 조회.
3. WAITING 등 참가 가능한 상태를 UI에 표시.
4. 방 제목, 현재 인원, 최대 인원, 상태를 보여준다.

### 변수
- 방 목록 조회 실패: 빈 목록과 구분.
- 이미 종료된 방이 캐시에 보임: 참가 시 서버가 최신 상태 재검증.
- 방장이 방을 닫음: 클릭 순간 상태가 바뀔 수 있음.
- 현재 인원이 max처럼 보여도 실제로는 동시 참가 요청이 들어오는 중일 수 있음.

### UI
프론트의 `참가 가능` 표시는 참고용이다. 실제 참가 가능 여부는 서버 응답으로 확정한다.

---

## 2. 방 참가

### 정상 흐름
1. 사용자 참가 요청.
2. 서버는 Room row를 짧게 `FOR UPDATE`로 잠금.
3. room 존재, WAITING 상태, 정원, 기존 참가 여부를 확인.
4. ROOM_PARTICIPANTS 생성.
5. 즉시 commit 후 lock 해제.

### 왜 여기서는 FOR UPDATE가 필요한가
정원과 상태처럼 여러 조건을 같은 순간에 일관되게 판정해야 한다. 두 요청이 동시에 마지막 한 자리를 보고 둘 다 입장하는 문제를 막기 위한 짧은 직렬화다.

### 변수
- 마지막 1자리에 두 명 동시 참가: lock 후 먼저 들어온 요청만 성공.
- 이미 참가한 사용자가 재요청: unique(room_id,user_id) 또는 사전 검사로 중복 방지.
- 방이 WAITING에서 IN_PROGRESS로 바뀌는 순간 참가: lock 후 최신 상태로 거절.
- 네트워크 오류로 응답을 못 받음: 재요청 시 이미 참가 상태인지 조회하고 복구 가능.
- 팀전일 때 team_name 누락/잘못된 값: 팀 구성 정책에 따라 검증 필요, 현재 미정이면 TBD.

### UI
`정원이 찼습니다`, `이미 시작된 방입니다`, `이미 참가 중입니다`를 구분해 표시.

---

## 3. Ready

### 목적
참가자가 게임 시작 준비가 됐음을 서버에 기록한다.

### 정상 흐름
- 참가자 is_ready = true.
- 방 참가자 목록에 실시간 또는 주기적 갱신.

### 변수
- Ready 직후 취소: 취소 허용 여부 정책 필요.
- 방장이 Ready 하지 않음.
- 참가자가 연결 끊김 상태인데 Ready=true로 남음.
- 이미 IN_PROGRESS인데 Ready 요청 도착.

### 해결
상태 전이마다 room.status를 서버에서 재검증한다. UI 버튼 비활성화만 믿지 않는다.

---

## 4. 게임 시작

### 목적
방을 WAITING에서 IN_PROGRESS로 전환하고 문제 풀이를 시작한다.

### 시작 조건 후보
- 방장만 시작 가능 여부
- 최소 참가 인원
- 전원 Ready 필요 여부
- ROOM_TASKS 최소 개수

위 조건은 확정된 규칙만 사용하고 미정은 `TBD`로 둔다.

### 변수
- 시작 버튼 연타: 두 번 시작되지 않아야 함.
- 시작 순간 참가/퇴장 요청과 경쟁.
- 준비 안 된 유저 존재.
- 문제 목록이 비어 있음 또는 비활성화됨.

### 해결
시작은 짧은 상태 전이 트랜잭션으로 처리하고, 성공한 한 요청만 WAITING→IN_PROGRESS를 수행한다.

---

## 5. 문제 풀이 및 제출

### 정상 흐름
- ROOM_TASKS 순서에 따라 문제 제시.
- 참가자가 코드를 제출.
- 학습과 동일한 Docker 채점 인프라 사용 가능.

### 변수
- 여러 참가자가 동시에 제출.
- 같은 사용자가 같은 문제를 반복 제출.
- 게임 종료 직후 늦게 도착한 제출.
- 채점 대기 중 게임이 종료됨.

### 핵심 정책 필요
`제출 시각 기준으로 인정할지`, `채점 완료 시각 기준으로 인정할지`를 확정해야 한다. 경쟁 게임에서는 이 차이가 점수에 직접 영향.

### DB 원칙
Docker 실행 동안 ROOM row lock을 잡지 않는다. 제출 기록과 점수 반영은 분리한다.

---

## 6. 점수 경쟁

### 목적
채점 결과를 게임 점수로 반영하고 참가자 간 순위를 갱신한다.

### 변수
- 동일 attempt 결과가 두 번 처리됨 → 중복 점수 위험.
- 동시에 여러 문제 정답 처리 → lost update 위험.
- 재접속한 클라이언트의 오래된 점수 표시.
- 팀전일 경우 개인 점수와 팀 점수 집계 방식 미정.

### 해결 원칙
- 점수는 클라이언트가 계산해 보내는 값을 그대로 신뢰하지 않는다.
- 서버의 채점 결과를 기준으로 원자적으로 증가.
- attempt 또는 room+user+task 단위 멱등성 필요.
- 점수 규칙은 `정답=몇 점`, 속도 보너스 여부 등 팀 합의 전 TBD.

### UI
실시간 갱신이 없더라도 서버 최신 점수를 재조회해 복원 가능해야 한다.

---

## 7. 연결 끊김 / 재접속

### 발생 원인
브라우저 새로고침, Wi-Fi 끊김, 탭 종료, 프로세스 재시작.

### 처리
- 사용자가 room participant로 남아 있다면 재접속 후 방 상태와 current_score를 서버에서 복원.
- 게임이 이미 FINISHED라면 진행 화면이 아니라 결과 화면으로 이동.
- 연결 끊김을 자동 패배/퇴장으로 처리할지는 비즈니스 정책 TBD.

---

## 8. 배틀 종료

### 종료 조건 후보
- 모든 문제가 끝남
- 제한 시간 종료
- 방장이 종료
- 참가자 수 부족

현재 확정되지 않은 조건은 TBD.

### 변수
- 종료 요청 두 번.
- 마지막 점수 반영과 종료가 동시에 발생.
- 채점 중인 PENDING attempt 존재.

### 해결
FINISHED 전환은 멱등하게 처리. 종료 후 늦게 도착한 점수를 인정할지 정책 확정 필요.

---

## 9. 결과 보상

### 정상 흐름
1. 최종 순위/팀 결과 확정.
2. 사용자별 보상 자격 계산.
3. 미지급 보상만 지급.
4. 재화 잔액 갱신.

### 변수
- 결과 화면 재조회 때 보상 함수 재실행.
- 두 서버 요청이 동시에 같은 배틀 보상 지급.
- 일부 참가자만 지급되고 중간 실패.

### 해결
room_id + user_id + reward_type에 해당하는 멱등 식별이 필요. 현재 ERD에 전용 보상 테이블이 없다면 구현 전 스키마 결정 필요.

### 보상 수치
등수별/참가/승리 보상은 미정이면 `TBD`.
