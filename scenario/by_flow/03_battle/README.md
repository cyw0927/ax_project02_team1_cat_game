# 배틀 흐름 시나리오

## 0. 전체 사용자 흐름

`홈 → 배틀 로비 → 방 생성/검색/참가 → 대기실 → Ready → 게임 시작 → 문제 풀이/제출 → 점수 경쟁 → 재접속 처리 → 종료 → 결과/보상 → 재화 반영`

배틀은 여러 사용자가 같은 ROOM 상태를 공유하므로 **마지막 자리 동시 입장, Ready 경쟁, 시작 시점, 제출/채점 지연, 점수 중복, 연결 끊김, 종료/보상 중복**이 핵심이다.

> 시작 조건, 최소 인원, 팀전 규칙, 실시간 통신 방식, 점수 공식, AFK/보상 제한은 확정 전 `TBD`다.

---

## 1. 방장 — 방 생성 및 설정

### 사용자 화면/흐름
로비에서 `방 만들기`를 누르면 제목, 모드, 정원 등 확정된 설정 항목을 입력하고 대기실로 이동한다. 방장은 별도 표시가 가능하다.

### Worst Case A — 생성 버튼 매크로 연타
- **왜 발생:** 응답 지연/매크로로 여러 생성 요청을 보낸다.
- **서버 감지:** 사용자가 이미 WAITING/IN_PROGRESS 방의 host인지 확인한다.
- **방어 로직:** 한 사용자의 활성 호스트 방 제한 정책이 확정됐다면 서버 트랜잭션/DB 제약으로 중복 생성을 막는다. 프론트 버튼 잠금만으로 해결하지 않는다.
- **UI:** `이미 진행 중인 방이 있습니다.`

### Worst Case B — 비정상 정원/설정값 직접 전송
- **방어 로직:** Pydantic/API 검증으로 허용 범위만 저장한다. 최대 정원 수치는 정책 확정 전 TBD.

### Worst Case C — 방 설정 변경과 Ready 충돌
- **위험:** 참가자는 이전 규칙에 Ready했는데 방 규칙이 바뀔 수 있다.
- **방어 로직:** 설정 변경 시 Ready 초기화 여부와 변경 가능 시점을 정책으로 확정한다. 필요하면 room row를 짧게 잠그고 상태를 일관되게 전이한다.

## 2. 참가자 — 방 검색 및 입장

### 사용자 화면/흐름
로비에서 `3/4` 같은 현재 인원과 방 상태를 보고 참가한다. 화면 표시는 참고용이고 최종 입장 가능 여부는 서버가 결정한다.

### Worst Case — 마지막 한 자리에 두 명이 동시에 입장
- **상황:** 두 요청이 거의 동시에 현재 인원 3명을 본다.
- **왜 발생:** `정원 확인 → INSERT`가 분리되면 둘 다 입장 가능하다고 판단할 수 있다.
- **방어 로직:** `ROOMS` row를 짧게 `SELECT ... FOR UPDATE` → WAITING/정원/기존 참가 여부 재확인 → 한 명 `ROOM_PARTICIPANTS` INSERT → 즉시 commit.
- **UI:** 한 명은 입장 성공, 다른 한 명은 `방이 가득 찼습니다.`
- **DB 영향:** `(room_id,user_id)` unique를 통해 동일 사용자의 중복 참가도 막는다.

### Worst Case — 입장 응답 유실
- **방어 로직:** 재요청 시 기존 participant 여부를 확인해 실제 입장 상태를 복구한다.

---

## 3. Ready 및 게임 시작

### 사용자 화면/흐름
대기실에서 참가자는 Ready를 누르고, 시작 조건을 만족하면 게임이 시작된다.

### Worst Case A — 방장이 시작을 누르는 순간 참가자 이탈/네트워크 단절
- **서버 감지:** 시작 transaction 안에서 최신 room.status, 참가 인원, Ready 상태를 다시 확인한다.
- **방어 로직:** 확정된 시작 조건을 모두 만족하는 경우에만 `WAITING → IN_PROGRESS` 전이한다.
- **UI:** 조건이 깨졌으면 `참가자 상태가 변경되어 시작할 수 없습니다.`

### Worst Case B — 시작 버튼 연타
- **방어 로직:** 조건부 상태 전이로 한 요청만 WAITING→IN_PROGRESS에 성공하게 한다.

### 문제 스냅샷
공정성을 위해 배틀 문제는 `ROOM_TASKS`에 `task_order`와 함께 방 단위로 고정한다. 게임 중 문제 pool 변경이 양 팀에 다른 문제를 만들지 않게 한다.

---

## 4. 문제 풀이, 샌드박스, 점수 경쟁

### 사용자 화면/흐름
모든 참가자가 같은 방의 문제를 풀고 제출한다. 채점 결과에 따라 개인/팀 점수가 갱신되고 점수판이 보인다.

### Worst Case A — 참가자 전원이 동시에 제출
- **방어 로직:** `TASK_ATTEMPTS` PENDING 저장 후 202 반환, Docker는 제한된 동시 실행 수로 처리한다.
- **기술 주석:** BackgroundTasks+semaphore는 MVP 한계가 있으며 다중 worker/내구성 요구가 커지면 별도 작업 큐가 필요하다.

### Worst Case B — 종료 직전 제출
- **핵심 정책:** 제출 수락 시각 기준인지 채점 완료 시각 기준인지 결과에 영향을 준다. 확정 전 `TBD`.
- **DB 원칙:** Docker 실행 중 ROOM lock을 잡지 않는다.

### Worst Case C — 동일 채점 결과가 두 번 점수 반영
- **왜 발생:** background retry/중복 callback/응답 재처리.
- **방어 로직:** attempt 또는 room+user+task 단위 멱등 식별로 점수 이벤트를 한 번만 반영한다.
- **점수 증가:** Python에서 과거 점수를 읽어 덮지 말고 DB 원자 증가를 우선한다.

### 실시간 점수판
WebSocket은 적합한 후보지만 현재 확정된 요구가 아니라면 `설계 제안`으로 둔다. 어떤 통신 방식을 쓰든 서버 DB의 최신 점수가 권위 상태다.

## 5. 연결 끊김 및 재접속

### Worst Case — Wi-Fi 끊김/새로고침
- **서버 감지:** 사용자의 ROOM_PARTICIPANTS 존재, room.status, current_score 확인.
- **방어 로직:** IN_PROGRESS면 현재 방/점수/문제 상태를 복원하고, FINISHED면 결과 화면으로 이동한다.
- **UI:** `연결이 복구되었습니다.`와 최신 점수를 표시한다.
- **TBD:** 연결 끊김을 자동 패배/퇴장으로 볼지 여부.

## 6. 종료 및 결과 보상

### 사용자 화면/흐름
게임 종료 후 최종 점수, 승패/순위, 보상 결과가 표시된다.

### Worst Case A — 종료 요청과 마지막 점수 반영이 경쟁
- **방어 로직:** FINISHED 전환을 멱등하게 하고, 종료 시점 이후 늦게 완료된 채점을 인정할지 정책을 명시한다.

### Worst Case B — 결과 화면 새로고침으로 보상 함수 재실행
- **방어 로직:** `room_id + user_id + reward_type` 같은 보상 이벤트를 1회성으로 처리한다. 전용 ledger/unique 구조는 신규 ERD에서 확정한다.

### Worst Case C — 다중 계정/AFK 파밍
- **아이디어:** 최소 기여도, 일일 횟수 제한 등은 어뷰징 방지 후보로 유효하지만 아직 확정되지 않았다면 `TBD`로 둔다.
- **금지:** `0점이면 무조건 보상 없음`처럼 합의되지 않은 규칙을 확정 문장으로 쓰지 않는다.

### 보상 동시 지급
여러 참가자에게 동시에 지급해도 `UPDATE USERS SET balance = balance + :reward` 같은 원자 증가를 사용해 lost update를 막는다. 지급 식별과 잔액 증가는 짧은 transaction으로 묶는다.
