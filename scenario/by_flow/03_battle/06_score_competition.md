# 배틀 6단계 — 점수 경쟁

## 목적
채점이 끝난 제출 결과를 서버 기준으로 점수에 반영하고, 개인전/팀전의 현재 순위를 최신 상태로 유지한다.

## 정상 흐름
1. 제출 attempt의 채점 결과가 확정된다.
2. 서버가 해당 attempt가 어느 room/user/task에 속하는지 확인한다.
3. 점수 인정 조건을 검증한다.
4. 인정되는 경우 ROOM_PARTICIPANTS.current_score를 원자적으로 증가시킨다.
5. 참가자 화면은 polling/WebSocket 등을 통해 최신 점수를 갱신한다.

## 발생 가능한 변수

### 변수 A. 같은 attempt 결과 처리 함수가 두 번 실행됨
- 원인: 재시도, background 작업 중복 실행, 응답 유실 후 재처리.
- 위험: 같은 정답으로 점수가 두 번 증가.
- 해결: attempt 또는 `room+user+task+점수 이벤트`를 기준으로 멱등 식별이 필요하다. 현재 ERD에 전용 score event 테이블이 없다면 구현 전 스키마/제약을 결정한다.

### 변수 B. 한 사용자의 정답 여러 건이 동시에 확정됨
- 원인: 여러 문제 채점이 거의 동시에 끝남.
- 위험: `읽기→더하기→쓰기` 방식이면 lost update가 발생할 수 있다.
- 해결: DB에서 `current_score = current_score + :delta` 형태의 원자 UPDATE를 사용한다.

### 변수 C. 클라이언트가 높은 점수를 직접 전송
- 원인: 요청 조작, 버그.
- 해결: 클라이언트가 계산한 최종 점수를 신뢰하지 않는다. 서버가 검증된 채점 결과로 delta를 계산한다.

### 변수 D. 점수 산식 미확정
- 후보: 정답 고정점수, 난이도별 가중치, 속도 보너스, 최초 정답만 인정 등.
- 해결: 팀 결정 전 `TBD`. 문서에서 임의 수치 확정 금지.

### 변수 E. 팀전에서 개인 점수와 팀 점수 계산 방식 충돌
- 원인: 합산/최고점/평균 등 정책 미정.
- 해결: `team_name`은 존재하지만 팀 점수 산식은 별도 `TBD`로 유지한다.

### 변수 F. 재접속 화면에 오래된 점수 표시
- 원인: 클라이언트 캐시, WebSocket 이벤트 유실.
- 해결: 재접속 시 서버의 ROOM_PARTICIPANTS.current_score를 전체 재조회해 복원한다.

### 변수 G. 마지막 점수 반영과 배틀 종료가 동시에 발생
- 원인: 종료 조건 도달 시점과 채점 완료 시점 경쟁.
- 해결: 늦은 결과 인정 기준을 명확히 정해야 한다. 제출 시각/채점 완료 시각 중 어떤 것을 기준으로 할지는 `TBD`.

## DB/동시성 원칙
- 점수 증가는 원자 UPDATE를 우선한다.
- 단순 점수 증가를 위해 ROOM 전체를 오래 잠그지 않는다.
- 중복 점수 차단은 UI가 아니라 서버/DB에서 보장한다.

## UI
- 서버 최신 점수를 권위 값으로 표시한다.
- 실시간 이벤트가 빠져도 전체 상태 재조회로 복원 가능해야 한다.
- 순위 변동 애니메이션은 UX일 뿐 실제 순위 계산은 서버 데이터를 따른다.
