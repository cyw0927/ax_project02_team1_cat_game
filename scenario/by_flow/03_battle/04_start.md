# 배틀 4단계 — 게임 시작

## 목적
방을 `WAITING`에서 `IN_PROGRESS`로 한 번만 전환하고, 참가자 모두가 같은 게임 시작 상태와 문제 순서를 보도록 만든다.

## 정상 흐름
1. 시작 권한을 가진 사용자가 시작 요청을 보낸다.
2. 서버는 room.status가 `WAITING`인지 확인한다.
3. 확정된 시작 조건(권한, 최소 인원, Ready 조건, ROOM_TASKS 존재)을 검증한다.
4. 조건을 만족하면 `WAITING → IN_PROGRESS`로 전환한다.
5. 시작 시각/문제 순서 등 필요한 상태를 확정한다.
6. 참가자 화면은 최신 방 상태를 받아 문제 풀이 화면으로 이동한다.

## 발생 가능한 변수

### 변수 A. 시작 버튼 연타
- 원인: 응답 지연, 더블클릭.
- 위험: 시작 로직이나 초기화가 두 번 실행될 수 있다.
- 해결: `WAITING`인 한 요청만 상태 전이에 성공하도록 하고, 이후 요청은 이미 시작된 상태를 반환한다.

### 변수 B. 시작 순간 마지막 참가 요청이 들어옴
- 원인: 참가와 시작이 동시에 처리됨.
- 해결: 참가 단계와 시작 단계 모두 room.status를 서버에서 재검증한다. 어떤 요청이 먼저 유효한 상태 전이를 확정했는지에 따라 결과가 결정되어야 한다.

### 변수 C. Ready하지 않은 참가자가 존재
- 원인: 전원 Ready 전에 시작 클릭.
- 해결: 전원 Ready가 필수인지 여부는 정책 `TBD`. 필수로 확정되면 서버에서 참가자 전체 상태를 검증한다.

### 변수 D. ROOM_TASKS가 0개
- 원인: 문제 배정 누락, 운영 오류.
- 해결: 문제 없이 게임을 시작하지 않는다. 시작 요청을 실패시키고 관리자가 문제 구성을 수정하도록 한다.
- UI: `게임 문제 구성이 준비되지 않았습니다.`

### 변수 E. 배정된 문제 일부가 비활성화됨
- 원인: 방 생성 후 관리자가 TASK 비활성화.
- 해결: 시작 시점에 실제 사용 가능 여부를 재검증한다. 대체 문제 자동 삽입 여부는 `TBD`.

### 변수 F. 시작 응답 유실
- 원인: 상태 전이는 성공했지만 클라이언트가 응답을 못 받음.
- 해결: 재조회 시 room.status가 IN_PROGRESS면 게임 화면으로 복원한다. 시작 요청을 단순 재실행하지 않는다.

## DB/동시성
- 상태 전이는 짧은 트랜잭션으로 처리한다.
- 이후 실제 문제 풀이/채점 동안 ROOM row lock을 유지하지 않는다.
- 시작 시각이나 시작 버전이 필요하다면 구현 전에 스키마 반영 여부를 결정한다.
