# 배틀 3단계 — Ready

## 목적
방 참가자가 실제 게임 시작 준비가 되었음을 서버 상태로 기록하고, 시작 조건 판정에 사용할 최신 준비 상태를 유지한다.

## 정상 흐름
1. 참가자가 Ready 버튼을 누른다.
2. 서버는 해당 사용자가 ROOM_PARTICIPANTS에 존재하는지 확인한다.
3. room.status가 아직 `WAITING`인지 확인한다.
4. participant.is_ready를 true로 변경한다.
5. 다른 참가자 화면도 polling/WebSocket 등을 통해 준비 상태를 갱신한다.

## 발생 가능한 변수

### 변수 A. Ready 버튼 연타
- 원인: 지연된 응답, 더블클릭.
- 해결: true를 다시 true로 쓰는 요청은 멱등하게 처리한다.
- UI: 첫 클릭 직후 버튼 상태를 바꾸되 서버 응답을 최종 기준으로 한다.

### 변수 B. Ready 직후 취소
- 원인: 사용자가 아직 준비가 안 됐거나 실수로 누름.
- 해결: Ready 취소 허용 여부는 비즈니스 정책이다. 허용한다면 WAITING에서만 false 전환 가능하게 한다. 미확정이면 `TBD`.

### 변수 C. 이미 게임이 시작된 뒤 Ready 요청 도착
- 원인: 오래 열린 탭, 네트워크 지연, 요청 순서 뒤바뀜.
- 감지: 요청 처리 시 room.status 재검증.
- 해결: IN_PROGRESS/FINISHED에서는 상태 변경을 거절하고 최신 방 상태를 반환한다.

### 변수 D. 연결 끊긴 사용자가 Ready=true로 남음
- 원인: Ready 후 브라우저 종료 또는 Wi-Fi 단절.
- 위험: 전원 Ready 조건을 사용할 경우 실제 부재 사용자까지 준비 완료로 판정될 수 있다.
- 해결: 연결 상태를 Ready와 같은 값으로 취급하지 않는다. 연결 끊김을 시작 조건에 반영할지는 별도 정책 `TBD`.

### 변수 E. 참가자 레코드가 없음
- 원인: 참가 성공 전 Ready 호출, 잘못된 사용자/room_id, 데이터 정리.
- 해결: 참가자가 아니면 Ready를 허용하지 않는다.

### 변수 F. 여러 기기에서 같은 사용자가 Ready/취소를 교차 호출
- 원인: 다중 탭/기기 사용.
- 해결: 서버 DB의 마지막 유효 상태를 권위 값으로 하고 모든 화면은 재조회 후 동기화한다.

## DB/API 영향
- ROOM_PARTICIPANTS.is_ready 변경.
- 단순 단일 row 상태 변경은 필요 이상으로 긴 lock을 잡지 않는다.
- 게임 시작 조건을 판정할 때는 Ready 값과 room.status를 서버에서 다시 조회한다.
