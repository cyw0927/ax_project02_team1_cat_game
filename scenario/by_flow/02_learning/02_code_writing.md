# 02. 코드 작성

## 목적
선택한 문제를 확인하고 사용자가 코드를 작성하는 단계다. 아직 서버 채점이 시작되지 않았으므로, 에디터 상태와 실제 제출 상태를 구분한다.

## 정상 흐름
1. 문제 상세를 표시한다.
2. starter/template 코드가 있으면 에디터에 로드한다.
3. 사용자가 코드를 작성/수정한다.
4. 필요하면 힌트를 확인한다.
5. 사용자가 제출을 누르면 제출 단계로 이동한다.

## 변수 A. 문제 상세 로드 실패
- 원인: 네트워크 단절, TASK 비활성화, 연관 데이터 오류.
- 해결: 빈 문제 화면으로 열지 않는다. 재조회 또는 목록 복귀.
- UI: `문제를 불러오지 못했습니다.`

## 변수 B. 작성 중 TASK 비활성화
- 원인: 관리자 수정.
- 해결: 작성 자체를 즉시 막을 필요는 없지만 제출 시 서버 재검증 필수.
- UI: 제출 시 `현재 사용할 수 없는 문제입니다.`

## 변수 C. 브라우저 새로고침/탭 종료로 코드 유실
- 해결 후보: 로컬 임시 저장, 서버 draft 저장.
- 현재 draft 저장 정책은 `TBD`.
- 원칙: 저장 기능이 없다면 있는 것처럼 표현하지 않는다.

## 변수 D. 여러 탭에서 같은 문제를 서로 다른 코드로 작성
- 위험: 어느 코드가 최신인지 사용자가 혼동.
- 해결: 서버 제출은 각 attempt 기준으로 독립 저장. draft 동기화 정책은 별도 결정.

## 변수 E. starter/template 코드가 깨짐
- 원인: TASK.template_code 오류.
- 해결: 문제 데이터 오류로 로그. 사용자가 정상 템플릿이라고 오해하지 않게 한다.

## 변수 F. 입력 크기가 비정상적으로 큼
- 위험: 요청 크기/로그/DB 저장 부담.
- 해결: 제출 API에서 최대 코드 크기 검증. 정확한 제한은 `TBD`.

## 변수 G. 허용되지 않는 언어/문법 모드
- 현재 프로젝트는 Python 학습을 기준으로 한다.
- 프론트 언어 선택 UI가 생긴다면 서버 채점 언어와 반드시 일치해야 한다.

## 변수 H. 힌트 사용
- `used_hint`가 보상/숙련도에 영향을 주는지 최종 비즈니스 규칙 확인 필요.
- 힌트를 눌렀다는 사실을 클라이언트만 신뢰하지 않고 제출/attempt 데이터와 연결하는 방안을 검토한다.

## 변수 I. 클라이언트 에디터 문법 표시와 실제 Python 실행 결과 차이
- 에디터 lint는 편의 기능일 뿐 채점 결과가 아니다.
- UI에서 lint 통과를 `정답`처럼 표현하지 않는다.

## DB/API 영향
코드 작성만으로 DB write가 반드시 필요한 것은 아니다. draft 저장 정책이 확정되기 전에는 TASK_ATTEMPTS를 작성 중 상태로 남발하지 않는다.

## 보안
문제 상세 응답에 `test_cases`나 정답 코드가 포함되지 않아야 한다.
