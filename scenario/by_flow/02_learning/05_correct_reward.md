# 05. 정답 보상

## 목적
일반 학습 문제의 채점 결과가 정답으로 확정된 뒤, 사용자가 해당 풀이에 대해 보상을 받을 자격이 있는지 판단하고 중복 없이 지급하는 단계다.

## 정상 흐름
1. attempt가 정답으로 최종 확정된다.
2. 서버가 해당 문제/사용자에 대한 보상 자격을 확인한다.
3. 이미 지급된 동일 보상인지 확인한다.
4. 지급 가능하면 재화 증가와 지급 사실을 짧은 트랜잭션으로 반영한다.
5. commit 후 최신 잔액과 지급 결과를 반환한다.

## 변수 A. 같은 문제를 여러 번 정답 처리
- 원인: 반복 학습, 재제출, 여러 기기.
- 핵심 질문: 동일 문제를 다시 맞힐 때마다 보상을 줄지, 최초 1회만 줄지, 기간별로 줄지.
- 현재 정책이 확정되지 않았다면 `TBD`.
- 원칙: attempt 개수와 보상 횟수는 분리한다.

## 변수 B. 응답 유실 후 보상 재요청
- DB commit은 성공했지만 클라이언트가 응답을 못 받을 수 있다.
- 재요청 시 같은 보상을 다시 지급하지 않도록 멱등성 필요.

## 변수 C. 두 정답 attempt가 거의 동시에 확정
- 둘 다 미지급 상태를 읽으면 이중 지급 가능.
- 단순 `SELECT → 없음 → UPDATE balance`만으로 보호하지 않는다.
- UNIQUE, 원자적 조건부 UPDATE, 멱등키 등 스키마에 맞는 DB 보호가 필요하다.

## 변수 D. 잔액 증가는 성공했는데 보상 기록 실패
- 사용자 잔액과 보상 이력이 불일치.
- 해결: 가능하면 같은 짧은 transaction으로 묶어 전체 rollback 가능하게 한다.

## 변수 E. 보상 기록은 성공했는데 잔액 증가 실패
- 이후 재시도 때 `이미 지급됨`으로 오판할 수 있다.
- 보상 이벤트와 잔액 반영을 원자적으로 처리하는 이유다.

## 변수 F. 힌트 사용 문제
- `used_hint=true`일 때 보상 감소/제외 여부는 아직 최종 규칙 확인 필요.
- 정책이 없다면 임의 차감 금지.

## 변수 G. 보상 수치 변경
- 서버 배포 중 정책이 바뀌었을 수 있다.
- 어떤 시점의 보상값을 적용할지 규칙이 필요.
- 현재 숫자는 문서에서 임의 확정하지 않는다.

## 변수 H. TASK가 정답 처리 후 비활성화
- 이미 정상적으로 확정/지급된 과거 보상을 자동 회수하지 않는다.
- 미지급 attempt의 처리 기준은 정책 결정 필요.

## 변수 I. 숙련도 업데이트와 보상 업데이트 중 하나만 실패
- 학습 결과는 숙련도에도 영향을 줄 수 있다.
- 숙련도 계산 정책과 보상 정책은 별도지만, 불일치 복구가 가능해야 한다.
- 정확한 proficiency 갱신 규칙은 기존 설계/팀 합의에 따른다.

## DB/트랜잭션 원칙
- Docker 채점과 보상 transaction을 하나로 묶지 않는다.
- 채점이 정답으로 확정된 후 짧은 보상 transaction 시작.
- 재화 증가가 단순 합산이라면 DB 원자 UPDATE를 우선 검토.

예:
```sql
UPDATE users
SET balance = balance + :reward
WHERE id = :user_id;
```

하지만 중복 지급 방지에는 별도의 보상 식별 근거가 필요하다.

## UI
- 실제 신규 지급: `정답입니다! 보상을 획득했습니다.`
- 정답이지만 기지급: `정답입니다.` + 보상 상태 별도 표시
- 지급 실패: 화면에서 임의로 balance를 증가시키지 않고 서버 상태 재조회
