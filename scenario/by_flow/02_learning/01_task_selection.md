# 01. 문제 선택

## 목적
사용자가 일반 학습 화면에 진입해 현재 풀 수 있는 문제를 탐색하고 하나를 선택하는 단계다. 문제 목록만 보여주는 것이 아니라 문제 활성 상태, 개념, 난이도, 사용자 숙련도와 최근 풀이 상태가 이후 단계에 어떤 영향을 주는지 함께 본다.

## 정상 흐름
1. 사용자가 홈에서 `학습`을 선택한다.
2. 서버가 활성 개념/문제 목록을 조회한다.
3. 필요하면 사용자 개념별 숙련도와 최근 풀이 이력을 함께 조회한다.
4. 클라이언트는 허용된 문제 정보만 표시한다.
5. 사용자가 문제를 선택한다.
6. 문제 상세 진입 시 해당 TASK가 여전히 활성 상태인지 다시 확인한다.
7. 정상이라면 코드 작성 화면으로 이동한다.

## 변수 A. 활성 문제 목록이 0개
- 원인: 초기 데이터 미등록, 전체 비활성화, 필터 결과 없음.
- 감지: 활성 TASK 조회 결과 0개.
- 해결: 서버 오류와 구분하고 정상 빈 상태로 표시한다.
- UI: `현재 풀 수 있는 문제가 없습니다.`
- 다음 단계: 문제 선택 불가, 홈 복귀 또는 필터 해제.

## 변수 B. 목록에 보이던 문제가 선택 직전에 비활성화
- 원인: 문제 오류 발견, 테스트케이스 수정, 관리자 조치.
- 위험: 오래된 목록을 믿고 비활성 문제로 attempt를 만들 수 있음.
- 해결: 상세 진입/제출 시 서버에서 `TASKS.is_active` 재검증.
- UI: `현재 사용할 수 없는 문제입니다.` 후 목록 재조회.

## 변수 C. 사용자 숙련도 데이터가 없음
- 원인: 신규 사용자, 해당 개념 첫 학습, 과거 데이터 누락.
- 해결: 신규 상태와 데이터 손상을 구분한다.
- 정책: 초기 숙련도 기본값은 팀 결정 전 `TBD`.

## 변수 D. 숙련도와 문제 난이도가 맞지 않음
- 예: 초보 사용자가 최고 난이도 문제 선택.
- 결정 필요: 자유 선택, 추천만 제공, 난이도 잠금 중 어떤 정책을 쓸지 `TBD`.
- 원칙: 프론트만 임의로 접근을 막지 않고 서버 정책과 일치시킨다.

## 변수 E. 같은 문제가 중복 노출
- 원인: API join 오류, 프론트 병합 오류, 중복 데이터.
- 감지: 동일 task_id 중복.
- 해결: 화면에서만 숨기지 말고 데이터/API 원인을 제거한다.

## 변수 F. test_cases가 클라이언트에 노출
- 위험: 채점 기준 유출.
- 해결: 목록/상세 DTO에서 서버 전용 `test_cases` 제외.
- 테스트: Network 응답 JSON에 테스트케이스 원문이 없는지 확인.

## 변수 G. 목록 조회 중 네트워크 끊김
- 해결: 빈 목록으로 위장하지 않고 오류/재시도 상태로 표시.
- UI: `문제 목록을 불러오지 못했습니다.`

## 변수 H. 여러 탭/기기에서 동시에 학습
- 목록 조회 자체는 읽기이므로 허용 가능.
- 이후 attempt와 보상 상태는 서버 DB를 권위 상태로 사용한다.

## 변수 I. 개념 연관 데이터 손상
- 상황: TASK는 존재하지만 concept_id가 유효하지 않음.
- 해결: 정상 문제처럼 반환하지 않고 task_id/concept_id를 로그로 남긴다.

## 변수 J. 잘못된 필터/정렬 요청
- 예: 존재하지 않는 난이도, 지나치게 큰 page size.
- 해결: API 입력 검증. 허용 범위는 계약에서 확정.

## DB/API 영향
주요 읽기 대상은 `CONCEPTS`, `TASKS`, `USER_PROFICIENCY`, 필요 시 최근 `TASK_ATTEMPTS`다. 목록 조회는 상태를 바꾸지 않는 읽기 요청이어야 한다.
