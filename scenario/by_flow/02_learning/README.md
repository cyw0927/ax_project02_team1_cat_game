# 학습 흐름 시나리오

## 0. 전체 사용자 흐름

`홈 → 학습 진입 → 단원/난이도 탐색 → 문제 선택 → 코드 작성/힌트 사용 → 제출 → 비동기 채점 → 결과 피드백 → 정답 보상 → 최신 재화/숙련도 반영 → 다음 문제 또는 다른 기능`

학습은 사용자가 원하는 문제를 직접 선택해 반복하는 기본 루프다. 이 문서는 실제 화면과 Worst Case를 먼저 설명하고 서버 방어·DB/API 영향으로 연결한다. 세부 기술 내용은 같은 폴더의 단계별 문서를 함께 본다.

> 보상 수치, 난이도 잠금 규칙, 힌트 효과, proficiency 산식, 코드 임시저장 정책은 확정 전 `TBD`다.

## 1. 진입 및 문제 선택

### 사용자 화면/흐름
학습 화면에는 개념/단원 탭과 문제 리스트가 보인다. 난이도, 문제 유형, 완료 여부 등을 확인하고 원하는 문제를 선택한다. 시스템 추천이 있어도 사용자의 직접 선택권을 막지 않는 방향을 우선한다.

### 정상 흐름
1. 서버가 활성 `CONCEPTS`, `TASKS`와 사용자 `USER_PROFICIENCY`를 조회한다.
2. 프론트가 단원/난이도별 문제를 표시한다.
3. 사용자가 task를 고른다.
4. 상세 조회 시 서버가 task 존재/활성 여부를 다시 검증한다.

### Worst Case A — 신규 사용자라 proficiency가 없음
- **왜 발생:** 아직 학습 이력이 없다.
- **서버 감지:** 해당 사용자/개념 row가 없음.
- **방어 로직:** 기본값/추천 규칙은 확정된 정책만 사용한다. 임의 점수를 만들어 저장하지 않는다.
- **UI:** `처음 학습하는 단원입니다`처럼 정상 상태로 표시한다.

### Worst Case B — 잠긴 문제 URL/API 직접 접근
- **왜 발생:** 프론트 자물쇠는 보안 경계가 아니다.
- **서버 감지:** 사용자 숙련도/선행 조건/활성 상태를 서버에서 재검증한다.
- **방어 로직:** 잠금 규칙이 확정된 범위에서만 거절한다. 잠금 기준 자체가 미정이면 문서에서 임의 확정하지 않는다.
- **UI:** `아직 도전할 수 없는 문제입니다.`

### Worst Case C — 화면을 연 사이 문제 비활성화
- **왜 발생:** 운영자가 오류 문제를 수정/비활성화할 수 있다.
- **서버 감지:** 상세 조회/제출 시 `is_active` 재확인.
- **방어 로직:** 비활성 task 제출을 채점하지 않는다.
- **UI:** `현재 이용할 수 없는 문제입니다. 다른 문제를 선택해주세요.`

## 2. 코드 작성 및 힌트

### 사용자 화면/흐름
문제 설명과 템플릿 코드를 보고 코드를 작성한다. 힌트 기능이 있으면 사용 여부를 기록할 수 있다.

### Worst Case A — 고정 템플릿 변조
- **왜 발생:** 개발자 도구/직접 API 호출로 함수명·매개변수를 바꿀 수 있다.
- **서버 감지:** 서버의 `TASKS.template_code`와 제출 구조를 기준으로 검증한다.
- **방어 로직:** 프론트에서 넘어온 전체 템플릿을 무조건 신뢰하지 않는다. 최종 조립 방식은 `test_cases/template_code` 형식 확정과 함께 정한다.
- **UI:** 형식이 맞지 않으면 채점 전에 `문제의 기본 코드 형식이 변경되었습니다.` 등으로 안내한다.

### Worst Case B — 힌트를 처음부터 모두 열기
- **왜 발생:** 사용자는 힌트를 학습 도구 또는 정답 우회 수단으로 사용할 수 있다.
- **방어 로직:** `used_hint`는 기록하되 보상/숙련도에 미치는 영향은 확정된 정책만 사용한다.
- **금지:** `힌트 사용 시 무조건 보상 감소`, `5회 오답 후 강제 힌트` 등을 합의 없이 추가하지 않는다.

### Worst Case C — 새로고침/브라우저 종료로 코드 유실
- **방어 로직:** 임시저장 기능 도입 여부는 `TBD`. 없다면 유실 가능성을 명확히 하고, 도입 시 서버/로컬 저장의 권위와 버전을 정의한다.

## 3. 제출 및 비동기 채점

### 사용자 화면/흐름
`제출하기`를 누르면 즉시 버튼이 비활성화되고 `채점 대기/채점 중` 상태로 바뀐다.

### 정상 흐름
`제출 → 유효성 검증 → TASK_ATTEMPTS PENDING 저장/commit → 202 Accepted → 제한된 백그라운드 실행 → Docker 채점 → 최종 결과 저장 → 화면 조회`

### Worst Case A — 30명 이상 동시 제출
- **왜 발생:** 수업 종료 직후 같은 시각에 제출이 몰릴 수 있다.
- **방어 로직:** PENDING을 먼저 저장하고 무제한 컨테이너를 만들지 않는다. MVP에서는 BackgroundTasks + semaphore로 동시 Docker 실행 수를 제한한다.
- **중요:** BackgroundTasks는 내구성 있는 분산 작업 큐가 아니다. 다중 worker/재시작 복구/작업 유실 방지가 필요하면 별도 durable queue가 필요하다.

### Worst Case B — 무한루프/메모리 폭탄/과도한 출력
- **방어 로직:** Docker memory≈128MB, CPU≈0.5, network none, read-only, timeout, output cap 등을 적용한다.
- **주의:** 특정 Python import 자체를 차단한다고 표현하지 않는다. 핵심은 컨테이너 바깥 피해를 막는 격리다.

### Worst Case C — 제출 연타/응답 유실
- **방어 로직:** attempt 생성 정책과 정답 보상 멱등성을 분리한다. commit 후 응답이 유실되면 최근 attempt를 재조회한다.

### DB/API 원칙
Docker 대기/실행 중 DB transaction이나 row lock을 유지하지 않는다.

## 4. 결과 피드백 및 정답 보상

### 사용자 화면/흐름
정답/오답/실행 오류/시간 초과/시스템 오류를 구분해 보여준다. 오답이면 다시 풀 수 있고, 정답이면 확정된 보상과 숙련도 변화를 표시한다.

### Worst Case A — 쉬운 문제 무한 반복 파밍
- **왜 발생:** 동일 task를 계속 다시 제출할 수 있다.
- **서버 감지:** 과거 정답/보상 이력을 서버에서 조회한다.
- **방어 로직:** `최초 정답 1회`, `일일 1회`, `매 정답` 중 실제 정책을 확정하고, 1회성이라면 DB 멱등키/unique/ledger로 보호한다.
- **UI:** 재풀이 자체는 허용하더라도 `이 문제의 기본 보상은 이미 획득했습니다.`처럼 구분 가능하다.

### Worst Case B — test_cases 오류
- **왜 발생:** 문제 은행 데이터가 잘못되면 올바른 코드도 실패한다.
- **방어 로직:** 운영 검증 후 해당 `TASKS.is_active=false` 처리 및 대체 문제 제공이 가능해야 한다.
- **UI:** 시스템 오류/문제 오류를 단순 오답으로 확정하지 않는다.

### Worst Case C — 정답 처리와 보상 처리 사이 오류
- **위험:** 정답은 기록됐는데 보상이 안 됐거나 반대 상태가 될 수 있다.
- **방어 로직:** 정답 결과 확정 후 별도의 짧은 보상 트랜잭션을 사용하고 지급 이벤트를 멱등 처리한다. 장시간 Docker 작업과 같은 transaction으로 묶지 않는다.
