# 학습 흐름 시나리오

## 전체 흐름

`학습 진입 → 문제 선택 → 코드 작성 → 제출 → 채점 → 정답 보상 → 재화 획득`

학습은 일일 미션과 달리 사용자가 원하는 문제를 선택해 반복 학습하는 기본 루프다. 같은 채점 인프라를 사용하더라도 문제 선택 자유도, 반복 풀이, 보상 중복 정책이 다를 수 있으므로 별도 흐름으로 본다.

---

## 1. 학습 진입

### 목적
사용 가능한 학습 문제와 사용자의 현재 숙련도/진행 상태를 불러온다.

### 정상 흐름
1. 홈에서 `학습` 선택.
2. 서버가 활성 CONCEPT/TASK 목록과 사용자 숙련도 정보를 반환.
3. 클라이언트가 개념/난이도/문제 유형별 탐색 UI를 표시.

### 변수와 원인
- 문제 목록 조회 실패: DB/네트워크 오류. 빈 목록으로 위장하지 않고 재시도 UI 표시.
- 활성 문제가 0개: 운영 데이터 부족 또는 관리자 비활성화. `문제가 없습니다`와 서버 오류를 구분.
- proficiency 데이터 없음: 신규 사용자. 기본 숙련도 처리 규칙은 기존 정책을 따르며 임의 숫자 부여 금지.
- 다른 기기에서 숙련도 변경: 진입 시 서버 최신값 사용.

### 다음 단계
사용자가 실제로 풀 수 있는 활성 문제를 선택하면 문제 선택 단계로 이동한다.

---

## 2. 문제 선택

### 목적
풀이할 TASK 하나를 확정한다.

### 정상 흐름
1. 사용자가 문제 카드 선택.
2. 문제 상세, 템플릿 코드, 난이도, 관련 개념 표시.
3. `test_cases`는 정답 판별 내부 정보이므로 사용자 응답에 그대로 노출하지 않는다.

### 변수
- 클릭 직후 문제 비활성화: 상세 조회/제출 시 서버 재검증.
- 존재하지 않는 task_id: 404 처리.
- URL 직접 조작: 권한/활성 여부 서버 검증.
- 문제 내용 갱신: 풀이 중 변경될 수 있으므로 제출 시 어떤 버전을 기준으로 채점할지 정책 필요. 버전 관리가 없다면 운영 중 문제 수정 시 주의.

### UI
문제 선택 실패 시 목록으로 강제 초기화하기보다 이유를 보여주고 다시 선택 가능하게 한다.

---

## 3. 코드 작성

### 목적
사용자가 문제 해결 코드를 작성하고 제출 준비를 한다.

### 정상 흐름
- 템플릿 코드 로드.
- 사용자가 편집.
- 필요 시 힌트 사용 여부 기록.

### 변수
- 브라우저 새로고침/탭 닫기: 작성 중 코드 유실 가능. 임시 저장 기능은 별도 정책.
- 매우 긴 코드: API/body 제한 필요.
- 빈 코드: 제출 전 UI 검증 가능하지만 서버에서도 검증.
- 힌트 사용: 보상/숙련도에 영향을 줄지 비즈니스 규칙 필요. 현재 스키마에는 `used_hint`가 있으나 효과 수치는 별도 확정 필요.

---

## 4. 제출

### 정상 흐름
1. 제출 요청.
2. 서버는 사용자와 TASK 유효성 검증.
3. TASK_ATTEMPTS에 PENDING 저장 후 commit.
4. 202 응답으로 attempt_id 반환.
5. 백그라운드 채점 예약.

### 변수
- 더블클릭/재전송: 여러 attempt가 생성될 수 있음. 풀이 기록 자체는 복수 허용 가능하지만 보상 중복과 분리해서 판단.
- 응답 유실: 서버 저장 여부를 최근 attempt 조회로 복구.
- DB 저장 실패: Docker 실행 시작 금지.
- 서버가 제출을 받았으나 BackgroundTasks 등록 전 장애: 비내구성 한계 문서화 필요.

### DB 원칙
PENDING 저장 트랜잭션은 짧게 끝내고 Docker 대기/실행 동안 DB lock을 잡지 않는다.

---

## 5. 채점

### 정상 흐름
- 실행 슬롯 대기.
- 제한된 Docker 컨테이너에서 실행.
- 결과 수집 및 컨테이너 제거.
- 별도 짧은 트랜잭션으로 attempt 최종 상태 기록.

### 변수
- 대기열 과다: 무제한 컨테이너 생성 금지.
- timeout/무한루프: 해당 컨테이너만 종료.
- memory 초과: 해당 실행만 실패.
- stdout 과다: 출력 크기 제한 필요.
- Docker daemon down: 시스템 오류와 오답 구분.
- 서버 재시작: BackgroundTasks 유실 가능.

### UI
`채점 대기`, `채점 중`, `정답`, `오답`, `시스템 오류`를 가능한 범위에서 구분한다.

---

## 6. 정답 보상

### 목적
정답 결과에 따라 학습 보상을 지급할지 판단한다.

### 핵심 변수
- 같은 문제를 하루에 10번 맞힘.
- 이미 이전에 정답 처리한 문제를 다시 맞힘.
- 힌트를 사용한 정답.
- 같은 attempt에 대한 보상 처리 요청이 두 번 실행됨.

### 해결 원칙
- `정답 기록`과 `재화 지급`을 분리한다.
- 학습 보상이 최초 정답 1회인지, 일일 1회인지, 매 정답인지 현재 미확정이면 `TBD`.
- 보상 정책 확정 전 프론트에서 임의로 재화를 증가시키지 않는다.
- 지급이 1회성이라면 DB unique/멱등키/조건부 update 중 하나로 중복 지급을 서버에서 차단.
- 재화 증가와 지급 기록은 짧은 원자 트랜잭션으로 처리.

### 숙련도 영향
정답/오답, 힌트 사용, 난이도에 따라 USER_PROFICIENCY를 어떻게 변화시킬지는 별도 비즈니스 규칙이다. 현재 문서에서는 임의 산식 확정 금지.

---

## 7. 재화 획득 및 반복

### 정상 흐름
- 보상 지급 시 최신 잔액 반영.
- 사용자는 같은 개념의 다른 문제를 선택하거나 홈으로 복귀.
- 획득 재화는 상점/가챠 흐름으로 연결.

### 변수
- 화면 잔액과 서버 잔액 불일치: 서버 잔액 우선.
- 동시에 상점 구매 중: 구매 API가 조건부 잔액 차감으로 다시 검증.

---

## 테스트 체크리스트

- 활성/비활성 문제 선택
- 신규 사용자 proficiency 없음
- 정답/오답/힌트 사용
- 제출 연타
- 응답 유실 후 attempt 조회
- Docker timeout/memory 초과
- 동시 다수 제출
- 동일 문제 반복 정답
- 보상 중복 실행
- 숙련도 업데이트 실패 시 정답 기록과 정합성
