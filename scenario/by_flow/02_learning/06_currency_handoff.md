# 06. 재화 반영 및 다음 흐름 연결

## 목적
정답 보상 처리 결과를 서버의 최신 재화 잔액에 반영하고, 사용자가 다음 문제/홈/상점/가챠/하우징으로 이동할 때 오래된 화면 상태 때문에 잘못된 판단을 하지 않도록 연결하는 단계다.

## 정상 흐름
1. `05_correct_reward.md`에서 신규 지급 또는 기지급 상태가 확정된다.
2. 서버 commit 후 최신 balance를 확정한다.
3. 클라이언트가 서버가 반환한 최신 잔액으로 UI를 갱신한다.
4. 문제 완료/최근 풀이 상태를 갱신한다.
5. 사용자는 다음 문제를 선택하거나 다른 메뉴로 이동한다.

## 변수 A. commit 성공 후 응답 유실
- 서버에는 지급 완료, 화면에는 실패처럼 보일 수 있다.
- 재요청 시 보상 멱등성으로 이중 지급을 막는다.
- 재접속 후 서버 balance와 지급 상태를 다시 읽는다.

## 변수 B. 다른 기능의 보상과 동시에 balance 증가
- 예: 학습 보상과 배틀 보상 동시 확정.
- 위험: Python에서 `read → +reward → save`를 각각 수행하면 lost update 가능.
- 해결: 가능한 한 DB 원자 증가 연산 사용.

## 변수 C. 화면 balance가 오래됨
- 다른 탭/기기에서 상점 구매 또는 가챠 사용.
- 다음 거래는 항상 서버가 최신 잔액으로 재검증한다.
- 화면 숫자는 참고 표시이지 결제 권위 상태가 아니다.

## 변수 D. 오래된 API 응답이 최신 잔액을 덮어씀
- 동시에 여러 요청이 있으면 응답 순서가 뒤집힐 수 있다.
- 중요한 거래 후에는 해당 거래 응답 또는 서버 재조회 결과를 기준으로 갱신한다.

## 변수 E. 정답 결과는 보이는데 보상 상태가 불명확
- attempt 정답과 보상 지급은 서로 다른 개념이다.
- UI에서 `정답`과 `보상 지급 완료/기지급/실패`를 필요에 따라 구분한다.

## 변수 F. 숙련도 화면이 오래됨
- 정답 후 proficiency 갱신 정책이 있다면 다음 문제 추천에 반영돼야 한다.
- 즉시 반영 시점/계산 방식은 `TBD`.

## 다음 문제로 이동
흐름:
`정답/보상 결과 → 최신 상태 반영 → 문제 목록 → 다른 문제 선택`

이때 기존 목록이 오래됐다면 TASK 활성 상태/추천 상태를 재조회할 수 있다.

## 상점으로 이동
흐름:
`학습 보상 → 최신 balance → 상점 → 서버 가격/잔액 검증 → 구매`

학습 화면에서 보이던 잔액만으로 구매를 확정하지 않는다.

## 가챠로 이동
흐름:
`학습 보상 → 최신 재화 → 가챠 → 서버 비용/정책 검증`

가챠 비용/확률/천장 등 미확정 정책은 `TBD`이며 학습 문서에서 임의 숫자를 만들지 않는다.

## 하우징으로 이동
학습 정답 자체가 하우징 배치를 자동 변경하지는 않는다. 재화로 상점/가챠를 거친 결과가 이후 하우징에 반영된다.

## DB/API 영향
- 최신 USERS.balance 조회/응답.
- 필요 시 USER_PROFICIENCY 최신 상태.
- 최근 TASK_ATTEMPTS 조회.
- 보상 지급 이력의 권위 상태.

## 장애 문의 시 추적 정보
1. user_id
2. task_id
3. attempt_id
4. 채점 최종 상태
5. 보상 자격/지급 상태
6. transaction 결과
7. 현재 서버 balance
8. 관련 proficiency 상태

## 테스트 케이스
- 정상 신규 지급 후 잔액 갱신
- 기지급 정답 후 잔액 변화 없음
- commit 후 응답 유실
- 다른 기능 보상 동시 발생
- 다른 기기 구매 후 학습 화면 복귀
- 오래된 응답 순서 역전
- 상점 바로 이동
- 가챠 바로 이동
- 다음 문제 바로 선택
- 재접속 후 상태 복원
