# 04. 채점

## 목적
제출된 Python 코드를 격리된 실행 환경에서 채점하고, 정답/오답/실행 오류/시스템 오류를 구분해 최종 attempt 상태를 확정한다.

## 정상 흐름
1. PENDING attempt가 채점 대기열에 존재한다.
2. 실행 슬롯을 확보한다.
3. Docker 컨테이너를 제한된 자원으로 실행한다.
4. 테스트케이스를 적용한다.
5. 결과/종료코드/timeout 등을 수집한다.
6. 컨테이너를 제거한다.
7. 별도 짧은 DB 트랜잭션으로 attempt 최종 상태를 업데이트한다.
8. 클라이언트가 결과를 조회한다.

## 변수 A. 대기열 증가
- 원인: 수업 직후 동시 제출.
- 해결: 무제한 컨테이너 생성 금지. semaphore/queue로 동시 실행 수 제한.
- UI: 가능하면 `대기 중`과 `채점 중` 구분.

## 변수 B. 무한루프/timeout
- 해당 컨테이너만 종료/제거.
- 사용자 코드 실행 실패와 서버 장애를 구분.
- 정답 보상 지급 금지.

## 변수 C. 메모리 초과
- 컨테이너 memory limit 적용.
- 한 작업의 초과가 다른 사용자/호스트 전체에 영향을 주지 않도록 격리.

## 변수 D. 출력 폭주
- stdout/stderr 수집 상한 필요.
- 최대 크기는 `TBD`.

## 변수 E. Docker daemon 장애
- 사용자 오답으로 처리하지 않는다.
- 영구 PENDING 방지/재시도 정책 필요.
- 자동 재시도 횟수는 `TBD`.

## 변수 F. 서버 재시작
- MVP BackgroundTasks는 비내구성이므로 작업 유실 가능.
- 오래된 PENDING 탐지/복구 정책 또는 durable queue 도입 검토.

## 변수 G. 컨테이너는 끝났지만 DB 결과 update 실패
- Docker를 다시 무조건 실행하면 중복/불일치 가능.
- 결과 업데이트 실패 로그 및 재시도 전략 필요.
- Docker 동안 DB lock을 유지하는 방식으로 해결하지 않는다.

## 변수 H. 클라이언트 결과 조회 실패
- 채점 실패와 조회 실패를 구분.
- 재접속 후 attempt 상태 재조회.

## 변수 I. 테스트케이스 자체 오류
- 사용자 코드가 정상이어도 서버 테스트 데이터가 잘못될 수 있음.
- 시스템/콘텐츠 오류를 사용자 오답으로 확정하지 않도록 운영 검토 경로 필요.

## 변수 J. 여러 attempt가 순서 뒤바뀌어 완료
- 먼저 제출한 것이 나중에 끝날 수 있다.
- 최신 화면이 오래된 attempt 결과로 덮이지 않도록 attempt_id 기준으로 표시.
- 보상 자격은 정책과 서버 기록을 기준으로 판정.

## 보안 원칙
- network disabled
- read-only filesystem
- CPU limit
- memory limit
- timeout
- 최소 실행 권한

## DB 원칙
Docker/대기열 실행 중 DB transaction을 유지하지 않는다.

```text
짧은 TX: PENDING 저장
→ DB 밖 채점
→ 짧은 TX: 최종 결과 저장
```
