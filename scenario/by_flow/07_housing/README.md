# 하우징 흐름 시나리오

## 전체 흐름

`하우징 진입 → 보유 가구/고양이 로드 → 현재 배치 상태 복원 → 가구 배치/이동/삭제 → 벽지·바닥 변경 → 고양이 배치 → 고양이 상호작용 → 저장 → 재접속 복원 → 공개 방 방문 → 타인 고양이 쓰다듬기·상호작용 → 방문 보상`

하우징은 상점과 가챠의 결과가 모이는 최종 공간이자 다른 사용자의 공개 방을 방문하는 공간이다. 따라서 **보유권 검증, 배치 수량, 위치 데이터, 여러 기기 동시 수정, 저장 실패, asset 누락, 방문자 read-only 권한 격리, 방문 보상 멱등성**을 중심으로 본다.

공개 방 방문, 타인 고양이 쓰다듬기·상호작용, 방문 보상은 정식 기능이다. 이를 지원하는 신규 ERD가 작성될 예정이며, 구체적인 방문 횟수와 보상 수치는 확정 전 `TBD`다.

---

## 1. 하우징 진입

### 정상 흐름
1. 홈에서 하우징 선택.
2. 서버에서 사용자 house 정보 조회.
3. wallpaper/floor, PLACED_OBJECTS, 보유 고양이 USER_CATS를 함께 또는 순차 조회.
4. 클라이언트가 방 배경과 배치 오브젝트/고양이를 렌더링.

### 변수
- house 데이터 조회 실패: 빈 방으로 덮어쓰지 않는다.
- placed object 일부의 item master가 삭제/비활성.
- USER_CATS는 있으나 cat master/asset이 누락.
- 신규 사용자의 배치 데이터가 0개.
- 다른 기기에서 이미 배치를 수정.

### UI
조회 실패와 `아무것도 배치하지 않은 빈 방`을 구분. 일부 asset만 실패하면 전체 하우징을 막기보다 fallback/누락 안내를 사용.

---

## 2. 보유 가구/인벤토리 확인

### 정상 흐름
- INVENTORIES에서 사용자가 보유한 item과 quantity 조회.
- 현재 PLACED_OBJECTS 수량과 비교해 추가 배치 가능 여부 계산.

### 변수
- inventory quantity보다 placed object 수가 많음: 과거 버그/동시성 오류/데이터 마이그레이션 문제.
- inventory row는 있는데 item master 없음.
- 구매 직후 화면 캐시가 갱신되지 않음.

### 해결
서버 DB를 권위 상태로 재조회. 잘못된 데이터는 클라이언트에서 조용히 수정하지 말고 운영/복구 경로가 필요.

---

## 3. 가구 배치

### 정상 흐름
1. 사용자가 인벤토리에서 가구 선택.
2. 화면에서 위치 선택.
3. 배치 요청 전송.
4. 서버는 user/item 보유 여부와 배치 가능한 수량 검증.
5. PLACED_OBJECTS 생성 및 position_data 저장.
6. 응답 후 화면 확정.

### 변수 A. 보유하지 않은 item_id를 직접 전송
- 해결: 서버가 INVENTORIES를 확인하고 거절.

### 변수 B. quantity=1인데 두 탭에서 동시에 각각 배치
- 위험: 둘 다 `현재 배치 0`을 읽고 두 개 생성 가능.
- 해결: 배치 수량 규칙이 필요하다면 짧은 트랜잭션 안에서 원자적으로 검증/생성하도록 설계. 정확한 구현은 스키마에 맞춰 검토.

### 변수 C. 가구가 방 밖/벽/다른 가구 위
- `position_data`가 현재 jsonb이므로 서버가 어느 수준까지 공간 충돌을 검증할지 정책 필요.
- 고급 충돌 검사는 P2로 미룰 수 있으나 최소 좌표 범위 검증은 필요.

### 변수 D. position_data 형식이 이상함
- 누락된 x/y, 문자열 좌표, 지나치게 큰 payload.
- 해결: Pydantic schema로 허용 필드/타입 검증. 현재 arbitrary dict라면 최종 규격 결정 필요.

---

## 4. 가구 이동/수정

### 정상 흐름
- placed_object_id 기준으로 본인 소유 여부 확인.
- 새 position_data 검증 후 UPDATE.

### 변수
- 다른 사용자의 placed_object_id 조작 → 403/404 정책에 따라 거절.
- 두 기기에서 같은 오브젝트를 동시에 이동 → 마지막 write가 앞선 변경을 덮을 수 있음.
- 삭제된 object를 이동 요청 → not found.

### 해결 후보
MVP는 last-write-wins를 허용할 수 있으나, 필요하면 version/updated_at optimistic concurrency 도입 검토. 정책 없이 조용히 합치지 않는다.

---

## 5. 가구 삭제/회수

### 정상 흐름
PLACED_OBJECTS row를 삭제하되 INVENTORIES의 보유 quantity 자체는 감소시키지 않는다. `배치 해제`와 `아이템 삭제`를 구분한다.

### 변수
- 삭제 버튼 연타 → 두 번째는 이미 없음.
- 삭제 응답 유실 → 재조회로 상태 확인.
- 상점 환불과 혼동 → 현재 환불 기능과 별개.

---

## 6. 벽지/바닥 변경

### 정상 흐름
1. 사용자 보유 item인지 확인.
2. category가 wallpaper/floor인지 검증.
3. USERS.wallpaper_item_id 또는 floor_item_id 갱신.

### 변수
- 가구 item을 wallpaper로 적용하려는 조작.
- 보유하지 않은 벽지 적용.
- 삭제된 item이 현재 적용된 상태.

### 해결
서버가 item category와 ownership을 둘 다 확인.

---

## 7. 보유 고양이 로드

### 정상 흐름
- USER_CATS + CATS 조회.
- starter 포함 보유 고양이를 하우징에 표시.

### 변수
- 신규 사용자에게 starter가 아직 없음.
- starter 생성 요청이 동시에 두 번 들어옴.
- cat_id에 대응하는 프론트 asset이 없음.

### 해결
- 로그인/가입 흐름에서 starter 보장을 재사용.
- `(user_id,cat_id)` 중복 정책 확정 후 DB unique 여부 검토.
- asset 누락은 명시적 fallback.

---

## 8. 고양이 배치 및 이동

### 현재 프로토타입 방향
- UUID 없는 DEMO에서도 주황 고양이 1마리 즉시 표시.
- 선택된 고양이를 바닥 클릭 위치로 이동.
- 자동 산책은 클릭 명령보다 우선하지 않음.
- 자동 산책 간격은 느긋하게 유지.

### 서버 저장과의 구분
화면에서 순간적으로 움직이는 모든 좌표를 매 프레임 DB에 저장하면 과도한 write가 발생한다. `생활 애니메이션 좌표`와 `영구 배치/선호 위치`를 구분해야 한다.

### 변수
- 브라우저 크기 변화로 percentage 좌표 의미 변화.
- 공용 PixiJS 프론트의 논리 격자 좌표와 개인 prototype 좌표계가 다름.
- 가구 충돌 영역과 실제 배경 이미지가 불일치.

### 해결
좌표 변환 책임을 별도 계층으로 두고 서버 position_data 규격을 팀에서 합의한다.

---

## 9. 고양이 상호작용

### 후보
- 클릭/쓰다듬기
- 대화
- 가구 사용
- 잠/앉기/공부 등 상태

현재 실제 sprite asset은 walk 중심이며 SIT/SLEEP/STUDY 전용 sprite가 확정된 상태가 아니므로 문서에서 구현 완료로 가정하지 않는다.

### CAT_MEMORIES
AI 대화/기억을 쓸 경우 user_cat_id의 context_summary를 저장할 수 있으나, 어떤 시점에 요약하고 얼마나 보존할지는 별도 정책.

---

## 10. 저장 실패와 재접속

### 변수
- 드래그 중 네트워크 끊김.
- 서버 저장 성공 후 응답 유실.
- 브라우저 종료.

### 해결
- UI가 먼저 움직였더라도 서버 저장 실패 시 `저장되지 않음`을 표시하거나 이전 상태로 복원.
- 재접속 시 항상 서버의 마지막 성공 저장 상태를 기준으로 재구성.

---

## 11. 상점/가챠와의 연결

- 상점 구매 완료 → 인벤토리 → 하우징 가구 배치.
- 가챠 고양이 획득 → USER_CATS → 하우징 고양이 표시.
- 화면 전환 직후 오래된 캐시 때문에 신규 자산이 안 보일 수 있으므로 하우징 진입 시 최신 서버 상태를 확인.

---

## 12. 공개 방 방문과 방문 보상

- 방문자는 공개된 방의 허용 데이터만 조회한다.
- 타인의 가구/고양이 소유권·배치·영구 상태·기억은 수정할 수 없으며 위조 요청은 403 처리한다.
- 쓰다듬기/상호작용 기록, 보상 멱등성, 일일 제한을 서버에서 판정한다.
- 버튼 매크로, 여러 기기 동시 요청, commit 후 응답 유실에도 보상을 중복 지급하지 않는다.
- 상세 단계는 [`09_public_room_visit.md`](./09_public_room_visit.md)를 따른다.

## 13. AI 고양이 대화

- 특정 공급자를 확정 전제로 쓰지 않는다.
- 입력 검증, 역할/권한 분리, 출력 검증, 최소 권한, 방문자 read-only context, `CAT_MEMORIES` 쓰기 제한, 로깅/모니터링을 함께 적용한다.
- 외부 AI 호출 중 DB lock/transaction을 유지하지 않는다.
- 상세 단계는 [`10_ai_cat_dialogue_security.md`](./10_ai_cat_dialogue_security.md)를 따른다.

- asset 없는 cat_id

- 쓰다듬기 매크로 연타, 두 기기 동시 요청, 보상 응답 유실
- 프롬프트 인젝션과 방문자 read-only AI context
