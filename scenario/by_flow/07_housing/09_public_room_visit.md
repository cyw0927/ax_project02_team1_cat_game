# 09. 공개 방 방문 및 상호작용

## 사용자 화면 / 흐름
`하우징 → 공개 방 목록/프로필 → 타인 방 입장 → 가구·고양이 조회 → 고양이 쓰다듬기·상호작용 → 방문 보상 결과 → 내 하우징으로 복귀`

공개 방 방문, 타인 고양이 쓰다듬기·상호작용, 방문 보상은 확정 기능이다. 구체적인 노출 범위, 일일 횟수와 보상 수치는 `TBD`이며 이를 지원하는 신규 ERD가 작성될 예정이다.

## 정상 흐름
1. 사용자가 공개된 다른 사용자의 방을 선택한다.
2. 서버는 대상 방의 공개 여부와 방문자의 접근 권한을 확인한다.
3. 서버는 방문용 read-only DTO로 방 배경, 배치 가구, 공개 가능한 고양이 상태만 반환한다.
4. 방문자가 고양이의 쓰다듬기 또는 허용된 상호작용을 요청한다.
5. 서버는 방문 세션, 대상 고양이, 상호작용 종류, 제한 상태를 재검증한다.
6. 상호작용 기록과 지급 자격을 멱등하게 확정하고, 자격이 있으면 방문 보상을 짧은 트랜잭션에서 반영한다.
7. 화면은 서버가 확정한 상호작용 결과와 최신 보상 상태를 표시한다.

## 대표 Worst Case

### A. 방문자가 소유자용 수정 API를 직접 호출
- **왜 발생하는가:** 개발자 도구로 `placed_object_id`, `user_cat_id`, 좌표 또는 기억 쓰기 요청을 위조한다.
- **서버 감지:** 인증 사용자와 자원 소유자를 비교하고, 방문 컨텍스트에서는 수정 권한을 부여하지 않는다.
- **방어 로직:** 타인의 가구·고양이 소유권·배치·영구 상태·`CAT_MEMORIES`를 수정하는 요청은 403으로 거절한다. 방문 조회 DTO에 내부 수정용 필드와 비공개 기억을 포함하지 않는다.
- **사용자 UI:** `이 방에서는 변경할 수 없습니다.`를 표시하고 로컬에서 보이던 임시 변화는 서버 상태로 복원한다.

### B. 쓰다듬기/보상 버튼을 매크로로 연타
- **왜 발생하는가:** 응답 지연, 더블클릭, 자동화 요청으로 같은 상호작용과 보상 지급이 반복된다.
- **서버 감지:** 방문자·대상 방/고양이·상호작용 종류·정책상 기간을 묶은 멱등 식별자와 일일 제한 상태를 확인한다.
- **방어 로직:** 동일 이벤트는 기존 결과를 반환하고 보상을 다시 지급하지 않는다. rate limit은 보조 방어로 사용하며 멱등성을 대신하지 않는다.
- **사용자 UI:** 처리 중 버튼을 잠그고, 재시도 시 신규 보상 애니메이션을 반복하지 않는다.

### C. 보상 commit 뒤 네트워크 단절 또는 앱 크래시
- **왜 발생하는가:** 서버 처리는 성공했지만 응답을 받기 전에 연결이나 앱이 종료된다.
- **서버 감지:** 재접속 후 동일 멱등 식별자와 방문 기록을 조회한다.
- **방어 로직:** 이미 완료된 결과와 최신 잔액을 반환한다. 새 방문으로 간주해 중복 지급하지 않는다.
- **사용자 UI:** `결과 확인 중` 뒤 서버 확정 상태를 복원한다.

### D. 방이 비공개로 바뀌거나 대상 고양이가 제거됨
- **왜 발생하는가:** 목록을 본 뒤 입장/상호작용 전에 소유자가 공개 상태나 배치를 변경한다.
- **서버 감지:** 입장과 각 쓰기성 상호작용 요청 시 공개 여부와 대상 존재를 다시 확인한다.
- **방어 로직:** 오래된 화면 데이터를 신뢰하지 않고 접근 거절 또는 not found를 반환한다. 타인 데이터 존재 여부를 과도하게 노출하지 않도록 403/404 정책은 신규 API 계약에서 통일한다.
- **사용자 UI:** 방 목록으로 안전하게 복귀하고 내 데이터나 빈 방으로 덮어쓰지 않는다.

### E. 방문 이벤트 배치 데이터 폭탄
- **왜 발생하는가:** 비정상적으로 큰 좌표 JSON, 과도한 오브젝트 수, 반복 이벤트 payload를 보낸다.
- **서버 감지:** payload 크기, 허용 필드/타입, 오브젝트 상한, 요청 빈도를 검증한다.
- **방어 로직:** 방문자는 배치 payload를 보낼 수 없게 하고, 상호작용 API는 최소 식별자만 받는다. 조회 응답은 pagination/상한과 안전한 직렬화를 적용한다.
- **사용자 UI:** 일반 검증 오류로 안내하며 부분 payload를 영구 상태에 반영하지 않는다.

## DB / API / state 영향
- 신규 ERD에는 방 공개 상태, 방문/상호작용 기록, 보상 멱등성 및 일일 제한을 표현할 구조가 필요하다.
- 방문용 조회 API와 소유자용 편집 API의 권한을 분리한다.
- 방문자는 `INVENTORIES`, 소유권, `PLACED_OBJECTS`, `USER_CATS`, `CAT_MEMORIES`를 수정하지 못한다.
- 구체 테이블명, 컬럼명, 보상 ledger 구조는 신규 ERD 확정 전 `TBD`다.

## retry / duplicate / concurrency / network 변수
- 동일 방문 이벤트 재시도는 같은 결과를 반환한다.
- 여러 기기에서 같은 방문자가 동시에 상호작용해도 제한과 보상은 서버에서 원자 판정한다.
- 소유자의 공개 설정 변경과 방문 입장이 경쟁하면 요청 처리 시점의 서버 상태를 따른다.
- 긴 외부 작업이나 애니메이션 동안 DB lock/transaction을 유지하지 않는다.

## 다음 단계 영향
- 성공: 방문 결과와 최신 보상 상태를 표시하고 계속 둘러보거나 내 하우징으로 복귀한다.
- 접근 취소/권한 없음: 공개 방 목록으로 이동한다.
- 보상 지급 실패: 상호작용 성공과 보상 상태를 구분해 복구하며 임의 재지급하지 않는다.

## 테스트
- 공개 방 정상 입장과 비공개 방 거절
- 타인의 가구 이동/삭제, 고양이 소유권 변경, 기억 쓰기 요청 403
- 쓰다듬기 버튼 매크로 연타와 동일 요청 재시도
- 두 기기 동시 상호작용과 일일 제한 경계
- 보상 commit 후 응답 유실/앱 크래시
- 입장 직전 공개→비공개 변경
- 제거된 고양이/가구를 오래된 화면에서 호출
- 과대 payload와 과도한 오브젝트 조회
