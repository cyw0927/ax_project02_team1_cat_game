# 08. 재접속 복원 및 다음 흐름 연결

## 목적
브라우저 새로고침, 재접속, 다른 기기 접속 후에도 마지막으로 서버에 성공 저장된 하우징 상태를 기준으로 화면을 재구성한다.

## 정상 흐름
1. 사용자가 하우징에 다시 진입한다.
2. 서버에서 최신 wallpaper/floor, PLACED_OBJECTS, INVENTORIES, USER_CATS를 재조회한다.
3. 클라이언트 로컬 상태를 초기화하고 서버 확정 상태로 다시 렌더링한다.
4. asset 매핑을 적용해 가구/고양이를 표시한다.
5. 사용자는 계속 편집하거나 홈/상점/가챠로 이동한다.

## 발생 가능한 변수
### A. 이전 세션에서 저장 실패한 위치가 로컬에 남아 있음
- 해결: 재접속 시 서버 상태가 권위값이다. 로컬 미저장 좌표를 자동으로 서버 상태 위에 덮지 않는다.

### B. 상점 구매 직후 하우징 진입
- 해결: INVENTORIES 최신 상태를 읽어 새 가구를 표시한다.

### C. 가챠 직후 하우징 진입
- 해결: USER_CATS를 재조회해 새 고양이를 반영한다. 결과 화면의 임시 데이터만 믿지 않는다.

### D. 다른 기기에서 가구를 이동/삭제
- 재접속 시 현재 서버 상태로 갱신한다.

### E. asset 버전이 오래됨
- 데이터는 존재하지만 이미지가 없을 수 있다.
- fallback을 사용하고 서버 소유 상태를 임의 변경하지 않는다.

### F. 일부 API만 성공
- 예: PLACED_OBJECTS는 조회됐지만 USER_CATS 실패.
- 해결: 부분 성공/부분 실패를 구분한다. 고양이 조회 실패 때문에 가구 데이터를 빈 값으로 덮지 않는다.

## 상점과의 연결
`재화 획득 → 상점 → 가구 구매 → INVENTORIES → 하우징 재조회 → 배치`

## 가챠와의 연결
`재화 획득 → 가챠 → USER_CATS 반영 → 하우징 재조회 → 고양이 표시`

## 홈과의 연결
하우징은 누적 자산의 표시 공간이며 홈에서 직접 진입할 수 있다. 상점/가챠를 반드시 거쳐야만 진입 가능한 구조로 만들지 않는다.

## 장애 문의 시 추적 정보
1. user_id
2. wallpaper/floor item id
3. inventory item/quantity
4. placed_object_id + position_data
5. user_cat_id + cat_id
6. 마지막 성공 저장 여부
7. 각 조회 API 성공/실패
8. 프론트 asset 존재 여부
