# 07. 저장 실패·동시성·복구

## 목적
하우징 편집 중 네트워크 단절, 응답 유실, 여러 기기 동시 수정이 발생해도 서버의 마지막 성공 상태를 기준으로 복구할 수 있게 한다.

## 정상 흐름
1. 사용자가 배치/이동/벽지 변경 등 편집 동작을 수행한다.
2. 클라이언트는 저장 요청을 서버에 보낸다.
3. 서버는 짧은 트랜잭션으로 해당 변경만 저장한다.
4. 성공 응답을 받은 뒤 UI를 확정 상태로 표시한다.
5. 다음 편집은 최신 서버 상태를 기준으로 이어간다.

## 발생 가능한 변수
### A. 저장 요청 전 네트워크 단절
- 서버 상태는 변경되지 않는다.
- UI는 미저장 변경임을 표시하거나 이전 확정 상태로 되돌린다.

### B. commit 성공 후 응답 유실
- 서버에는 변경이 남았지만 사용자는 실패로 볼 수 있다.
- 해결: 같은 요청을 무조건 재실행하기보다 객체/하우징 상태를 재조회해 실제 저장 여부를 확인한다.

### C. 두 기기에서 같은 object를 동시에 수정
- MVP 후보: last-write-wins.
- 위험: 앞선 변경이 사용자에게 설명 없이 사라질 수 있다.
- 필요 시 version/updated_at 기반 optimistic concurrency를 도입한다.
- 최종 충돌 정책은 TBD.

### D. 한 요청이 오래 걸리는 동안 DB lock 유지
- 금지: 사용자의 드래그/프론트 애니메이션 동안 transaction을 열어두지 않는다.
- 서버 저장 transaction은 필요한 DB write만 짧게 수행한다.

### E. 여러 object를 한꺼번에 저장
- 전체 원자 저장이 필요한지, object별 독립 저장이 필요한지는 UI UX와 함께 결정한다.
- 하나 실패했다고 관계없는 object까지 장시간 lock하지 않는다.

### F. 서버 재시작
- 이미 commit된 DB 상태는 유지된다.
- 메모리에만 있던 임시 화면 위치는 유실될 수 있으므로 서버 확정 상태와 구분한다.

## DB/API 영향
- PLACED_OBJECTS create/update/delete
- USERS wallpaper/floor update
- 필요 시 optimistic concurrency용 updated_at/version 검토

## UI
- `저장 중`, `저장 완료`, `저장 실패` 상태를 구분한다.
- 응답 유실 가능성이 있으므로 실패 화면에서 실제 서버 상태 재조회 경로를 제공한다.
