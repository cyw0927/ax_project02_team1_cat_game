# 03. 가구 배치·이동·삭제

## 목적
보유 가구를 하우징에 배치하고, 기존 배치 객체를 이동하거나 회수하는 편집 흐름을 안전하게 처리한다.

## 정상 흐름
1. 사용자가 인벤토리에서 가구를 선택한다.
2. 클라이언트에서 임시 위치를 지정한다.
3. 서버에 배치 요청을 보낸다.
4. 서버는 사용자 소유권, item 존재 여부, 보유 수량, 현재 배치 수량, position_data 형식을 검증한다.
5. 유효하면 PLACED_OBJECTS를 생성한다.
6. 이동은 placed_object_id의 사용자 소유권 확인 후 position_data를 갱신한다.
7. 배치 해제는 PLACED_OBJECTS만 삭제하며 INVENTORIES의 보유 수량 자체는 없애지 않는다.

## 발생 가능한 변수
### A. 보유하지 않은 item_id 직접 전송
- 원인: 클라이언트 조작, 오래된 화면 상태.
- 해결: 서버가 INVENTORIES를 다시 확인하고 거절한다.

### B. quantity=1인데 두 탭에서 동시에 배치
- 원인: 두 요청이 동시에 배치 가능으로 판단.
- 위험: 보유 수보다 많이 배치될 수 있다.
- 해결: 다중 배치 제한이 확정된다면 짧은 트랜잭션에서 현재 배치 수와 보유량을 함께 검증해야 한다. 구체 제약은 최종 스키마에 맞춰 결정한다.

### C. 방 밖 좌표 또는 비정상 position_data
- 원인: 화면 좌표 계산 오류, 직접 API 호출.
- 해결: Pydantic schema로 타입/허용 필드를 검증하고 최소 좌표 범위를 확인한다.
- TBD: 고급 가구 충돌/겹침 판정 수준.

### D. 다른 사용자의 placed_object_id 수정
- 해결: 모든 이동/삭제 요청에서 소유자 검증. 실패 시 403 또는 존재를 숨기기 위한 404 정책 중 팀 기준에 맞춘다.

### E. 두 기기에서 같은 가구 이동
- 결과: 마지막 요청이 이전 위치를 덮을 수 있다.
- MVP 후보: last-write-wins.
- 필요 시 updated_at/version을 이용한 optimistic concurrency 검토.

### F. 삭제 버튼 연타 또는 응답 유실
- 두 번째 요청에서 이미 없는 object일 수 있다.
- commit 후 응답이 끊기면 재조회로 실제 상태를 확인한다.

## DB/API 영향
- INVENTORIES: 보유권 검증
- PLACED_OBJECTS: create/update/delete
- 긴 프론트 드래그 동안 DB lock을 유지하지 않는다.

## UI
- 저장 중 상태를 명확히 표시한다.
- 저장 실패 시 성공한 것처럼 확정하지 않는다.
- 배치 해제와 아이템 소멸/판매를 같은 동작처럼 표현하지 않는다.
