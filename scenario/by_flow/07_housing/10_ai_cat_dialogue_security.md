# 10. AI 고양이 대화와 기억 보안

## 사용자 화면 / 흐름
`내 방 또는 공개 방문 방 → 고양이 선택 → 대화 입력 → 안전한 컨텍스트 구성 → 공급자 비종속 AI 호출 → 출력 검증 → 대화 표시 → 허용된 경우에만 기억 반영`

특정 AI 공급자는 아직 확정하지 않는다. 구현과 문서에서 Gemini 등 하나의 공급자를 고정 전제로 두지 않는다.

## 정상 흐름
1. 서버가 인증 사용자, 방 컨텍스트, 대상 `user_cat_id`와 소유권을 확인한다.
2. 입력 길이·형식·금지 데이터와 요청 빈도를 검증한다.
3. 시스템 역할, 사용자 입력, 공개 가능한 고양이 컨텍스트를 서로 다른 신뢰 영역으로 구성한다.
4. 최소 권한의 AI 호출 계층이 공급자에 요청한다.
5. 출력의 형식, 길이, 위험 콘텐츠와 내부 정보 노출을 검증한다.
6. 안전한 출력만 사용자에게 반환한다.
7. 기억 저장 자격이 있는 소유자 대화만 별도 정책에 따라 요약·검증한 뒤 `CAT_MEMORIES`에 기록한다.

## 대표 Worst Case — 프롬프트 인젝션으로 기억/권한 탈취
- **왜 발생하는가:** 사용자가 `이전 지시를 무시하라`, 비밀을 출력하라, 타인 고양이 기억을 수정하라 같은 입력을 보낸다. 모델 출력 자체에도 후속 시스템을 속이는 문자열이 포함될 수 있다.
- **서버 감지:** 입력·출력 schema, 길이, 역할 경계, 요청 자원 소유권, 도구 호출 allowlist, 민감정보 패턴과 비정상 요청률을 검사한다.
- **방어 로직:** 시스템 프롬프트 하나에 의존하지 않는다. 입력 검증, 역할/권한 분리, 출력 검증, 최소 권한, 허용 도구 목록, 방문자 read-only context, `CAT_MEMORIES` 쓰기 권한 제한, 감사 로깅·모니터링을 함께 적용한다.
- **사용자 UI:** 안전하게 답할 수 없는 요청은 일반화된 안내로 종료한다. 내부 프롬프트, 권한 판정 상세, 다른 사용자의 기억을 노출하지 않는다.

## DB / API / state 영향
- 소유자 대화와 방문자 대화를 권한 컨텍스트로 명확히 구분한다.
- 방문자는 공개 가능한 현재 상태만 읽고 `CAT_MEMORIES`를 읽거나 쓰지 못한다.
- AI 출력이 직접 DB write 명령이 되지 않으며, 서버의 검증된 서비스 계층만 제한된 쓰기를 수행한다.
- 기억 요약/보존/삭제, 동의, 민감정보 처리 구조는 `TBD`다.

## retry / duplicate / concurrency / network 변수
- 타임아웃 재시도 시 동일 입력이 기억에 여러 번 저장되지 않도록 대화 요청 식별자를 둔다.
- AI 응답 성공 후 DB 기억 저장 실패를 사용자 응답 성공과 구분해 추적한다.
- 공급자 장애 시 고양이 소유/배치 상태에는 영향이 없어야 한다.
- 외부 AI 호출 중 DB transaction이나 row lock을 유지하지 않는다.

## 다음 단계 영향
- 안전한 응답: 화면에 표시하고, 소유자·정책 조건을 만족할 때만 기억 저장 후보로 넘긴다.
- 검증 실패/공급자 장애: 재시도 가능 상태를 표시하되 임의 응답이나 기억을 만들지 않는다.
- 방문자 대화: 세션성 화면 상태로만 처리하고 영구 기억 변경으로 이어지지 않는다.

## 테스트
- 직접/간접 프롬프트 인젝션
- 타인 기억 조회·수정 유도
- 모델 출력의 도구 호출/명령 위조
- 과대 입력, 고빈도 요청, 민감정보 포함 입력
- 응답 timeout 후 재시도와 중복 기억 방지
- 공급자 장애, 출력 schema 오류, 로그 민감정보 마스킹
- 방문자 read-only context와 403 권한 검증
