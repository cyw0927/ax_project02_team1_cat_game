# 05. 고양이 표시 및 상호작용

## 목적
USER_CATS에 등록된 고양이를 하우징에 표시하고, 화면 이동/클릭/대화 등 상호작용을 서버 영구 상태와 구분해 처리한다.

## 정상 흐름
1. USER_CATS + CATS를 기준으로 보유 고양이를 로드한다.
2. cat_id에 대응하는 프론트 asset을 선택한다.
3. 하우징에 고양이를 표시한다.
4. 사용자가 고양이를 선택하거나 바닥을 클릭하면 현재 선택 고양이의 화면상 이동 목표를 변경한다.
5. 자동 산책/idle 애니메이션은 사용자 명령보다 낮은 우선순위로 실행한다.
6. 대화/기억 기능을 사용할 경우 user_cat_id 기준으로 서버 기능을 호출한다.

## 발생 가능한 변수
### A. asset 없는 cat_id
- 원인: 백엔드 고양이 데이터와 프론트 asset 배포 시점 차이.
- 해결: 명시적 fallback asset 또는 오류 안내. DB 소유 상태를 삭제하지 않는다.

### B. 여러 고양이가 같은 위치로 이동
- 원인: 동일 클릭 목표, 자동 산책 충돌.
- 해결: 프론트 이동 로직에서 최소 간격/회피를 적용한다. 이 순간 이동을 매 프레임 DB에 저장하지 않는다.

### C. 클릭 이동과 자동 산책이 충돌
- 해결: 수동 명령을 우선하고 도착 후 충분한 idle 시간을 둔 뒤 자동 산책을 재개한다.

### D. starter가 화면에 없음
- 원인: USER_CATS 미생성 또는 UUID 없는 DEMO 모드.
- 해결: UUID 없는 prototype은 기본 주황 고양이를 즉시 표시하고, 실제 사용자 모드에서는 starter 보장 API/서비스 결과를 사용한다.

### E. SIT/SLEEP/STUDY 같은 행동 asset 없음
- 해결: 실제 asset이 존재하지 않는 행동을 구현 완료로 표시하지 않는다. 현재 walk/idle 범위와 향후 확장을 구분한다.

### F. CAT_MEMORIES 저장 시점 불명확
- AI 대화 요약 주기/보존 기간은 TBD. 화면 클릭마다 memory를 생성하지 않는다.

## DB/API 영향
- USER_CATS / CATS: 소유 고양이
- CAT_MEMORIES: 실제 AI 대화/기억 기능 사용 시
- 화면상 실시간 좌표는 기본적으로 클라이언트 상태이며 서버 영구 배치 규칙과 구분한다.

## UI
- 현재 선택 고양이를 식별 가능하게 표시.
- asset fallback이더라도 소유 고양이가 사라진 것처럼 보이지 않게 한다.
