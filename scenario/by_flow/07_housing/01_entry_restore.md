# 01. 하우징 진입 및 상태 복원

## 목적
사용자가 홈에서 하우징으로 진입할 때 서버에 저장된 마지막 성공 상태를 기준으로 방을 복원한다. 빈 방, 조회 실패, 일부 asset 누락을 서로 다른 상태로 구분하는 것이 핵심이다.

## 정상 흐름
1. 사용자가 홈에서 하우징을 선택한다.
2. 서버에서 현재 사용자 식별자를 기준으로 하우징 관련 상태를 조회한다.
3. 현재 벽지/바닥, PLACED_OBJECTS, 보유 아이템 요약, USER_CATS를 순차 또는 병렬로 조회한다.
4. 클라이언트는 서버 응답을 기준으로 배경, 가구, 고양이를 렌더링한다.
5. 모든 필수 조회가 끝나면 편집 가능한 상태로 전환한다.

## 발생 가능한 변수
### A. 신규 사용자라 배치 데이터가 0개
- 원인: 아직 상점 구매/가구 배치를 하지 않음.
- 해결: 오류가 아니라 정상적인 빈 하우징 상태로 처리한다.
- UI: 기본 방 배경과 starter 고양이 보장 상태를 보여준다.

### B. 하우징 조회 API 실패
- 원인: DB 장애, 네트워크 단절, 서버 오류.
- 위험: 실패를 빈 방으로 오인하면 화면에서 잘못된 상태를 저장할 수 있다.
- 해결: `조회 실패` 상태를 별도로 유지하고 저장/배치 버튼을 잠시 비활성화한다.
- UI: `하우징 정보를 불러오지 못했습니다. 다시 시도해주세요.`

### C. 일부 가구 item master 누락
- 원인: 운영 중 item 비활성화/삭제, 데이터 마이그레이션 오류.
- 해결: 전체 하우징 렌더링을 막지 않고 해당 object만 fallback 또는 누락 표시한다. 데이터는 클라이언트에서 임의 삭제하지 않는다.

### D. USER_CATS는 있는데 cat master 또는 asset이 없음
- 원인: DB/프론트 asset 버전 불일치.
- 해결: 서버 데이터는 유지하고 프론트에서 명시적 fallback을 사용한다.

### E. 다른 기기에서 이미 하우징 변경
- 원인: 여러 탭/기기 동시 사용.
- 해결: 진입 시 항상 서버 최신 상태를 읽는다. 이전 탭의 로컬 상태를 권위값으로 사용하지 않는다.

## DB/API 영향
- USERS.wallpaper_item_id / floor_item_id
- PLACED_OBJECTS
- INVENTORIES
- USER_CATS + CATS
