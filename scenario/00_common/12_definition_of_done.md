# 기능 완료 기준 (Definition of Done)

코드가 실행된다는 이유만으로 기능을 완료 처리하지 않는다. 아래 항목을 만족해야 '이 시나리오는 구현이 끝났다'고 볼 수 있다.

## 1. 시나리오가 확정되어 있는가

- 사용자가 무엇을 하는지 설명할 수 있다.
- 성공 흐름을 설명할 수 있다.
- 대표 실패 흐름을 설명할 수 있다.
- 아직 미정인 규칙을 코드에 임의로 넣지 않았다.

## 2. API 계약이 정해져 있는가

- Method
- URL
- Request
- 성공 Response
- 실패 Response
- HTTP status

를 팀원이 보고 이해할 수 있다.

## 3. 백엔드 검증이 있는가

프론트가 보내는 값을 무조건 믿지 않는다.

예:
- user 존재
- task/item/room 존재
- 활성 상태
- 소유권
- 권한
- 잔액
- 현재 상태
- 만료시간

해당 기능에 필요한 검사를 서버에서도 수행한다.

## 4. DB 변경이 안전한가

- transaction 범위가 정해져 있다.
- 중간 실패 시 rollback된다.
- 필요한 UNIQUE/FK가 있다.
- 재화 변경 시 race condition을 검토했다.
- 여러 상태 판정 시 필요한 lock을 검토했다.

## 5. 정상 테스트 통과

대표 Happy Path가 실제로 성공한다.

API 응답뿐 아니라 필요한 경우 DB row도 확인한다.

## 6. 예외 테스트 통과

해당 기능의 대표적인 잘못된 요청을 테스트한다.

예:

```text
없는 대상
권한 없음
잔액 부족
중복 요청
상태 불일치
만료
```

## 7. 동시성 테스트가 필요한 기능인가

필요하다면 실제 동시 요청을 검증한다.

대상 예:
- 상점
- 가챠
- 출석
- 방 입장
- 최초 정답 보상
- Docker 동시 실행 제한

단순 조회 API에는 억지로 동시성 테스트를 만들 필요가 없다.

## 8. 보안상 불필요한 정보가 노출되지 않는가

- `test_cases` 비노출
- password/hash 비노출
- 서버 traceback 비노출
- DB 접속 정보 비노출
- 다른 사용자 데이터 무단 변경 방지

## 9. 기존 기능을 깨뜨리지 않았는가

새 기능을 추가한 뒤 기존 API가 실행되는지 확인한다.

공통 model, migration, auth 변경은 특히 다른 도메인에 미치는 영향을 확인한다.

## 10. Swagger에서 이해 가능한가

`/docs`에서 endpoint가 보이고 Request 형식을 확인할 수 있어야 한다.

가능하면 팀원이 Swagger만 보고도 최소 수동 테스트를 할 수 있게 한다.

## 11. 테스트 코드/기록이 필요한가

반복해서 깨지면 위험한 핵심 로직은 `tests/`에 남긴다.

모든 간단한 조회 API까지 무리하게 자동 테스트를 늘리는 것보다 경제/동시성/채점/상태 전이 같은 핵심을 우선한다.

## 12. Git 작업이 정리되었는가

- 기능 단위 commit
- 불필요한 임시 파일 없음
- `.env`, 비밀번호 등 비밀값 commit 안 함
- PR 설명에 무엇을 만들고 어떻게 검증했는지 적음
- 다른 팀원 review 후 merge

## 완료 체크 예시

```text
[ ] 시나리오 확정
[ ] API 계약 확정
[ ] 구현
[ ] 정상 테스트
[ ] 예외 테스트
[ ] 동시성 테스트(필요 시)
[ ] DB 확인
[ ] Swagger 확인
[ ] 불필요 파일 정리
[ ] PR/Review
```

이 체크를 통과하면 다음 기능으로 넘어간다.
