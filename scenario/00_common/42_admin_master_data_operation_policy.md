# 관리자·마스터데이터 운영 정책

이 문서는 일반 사용자가 직접 만들거나 수정하면 안 되는 **문제, 아이템, 고양이, 랭킹 그룹 같은 마스터데이터**를 누가 어떻게 관리할지 정리한다.

핵심 원칙:

```text
게임 플레이 데이터
≠
마스터데이터
```

마스터데이터는 여러 사용자에게 공통으로 영향을 주므로 일반 사용자 쓰기 API와 분리한다.

---

## 1. 마스터데이터 후보

현재 ERD 기준:

```text
CONCEPTS
TASKS
ITEMS
CATS
RANKING_GROUPS(운영 방식에 따라)
```

이 데이터는 잘못 수정하면 전체 사용자에게 영향을 준다.

---

## 2. 일반 사용자 데이터와 차이

예:

```text
USER_CATS
INVENTORIES
TASK_ATTEMPTS
ROOM_PARTICIPANTS
```

은 사용자 플레이 결과다.

반면:

```text
CATS
ITEMS
TASKS
```

는 게임 규칙과 콘텐츠의 기준이다.

---

## 3. 문제(TASKS) 관리

관리 기능이 생긴다면 최소:

- 문제 등록
- 문제 수정
- 활성/비활성
- test_cases 수정
- difficulty/concept 연결

이 필요할 수 있다.

특히 `test_cases`는 채점 정답 기준이므로 일반 사용자에게 노출하거나 수정 권한을 주면 안 된다.

---

## 4. 문제 삭제

TASK_ATTEMPTS, ROOM_TASKS, RANK_CHALLENGE_TASKS가 TASKS를 참조할 수 있으므로 물리 삭제는 주의한다.

MVP에서는:

```text
is_active=false
```

로 신규 출제를 막는 방식이 더 안전하다.

과거 기록은 남긴다.

---

## 5. 아이템(ITEMS) 관리

관리자 후보 기능:

- 상품 등록
- category 설정
- name 수정
- price 변경
- 판매 중단

현재 ITEMS에는 `is_active` 컬럼이 없다.

상점 판매 중단 기능이 필요하면 스키마 확장 여부를 검토한다.

이미 INVENTORIES에서 참조되는 item을 함부로 삭제하지 않는다.

---

## 6. 고양이(CATS) 관리

관리자 후보 기능:

- 고양이 마스터 등록
- name/persona/rarity 수정
- 가챠 후보 포함 여부 관리

현재 CATS에는 `is_active`가 없다.

가챠 풀에서 제외하더라도 기존 USER_CATS 소유 기록은 유지되어야 한다.

---

## 7. 랭킹 그룹

RANKING_GROUPS에는 `owner_user_id`가 있으므로 두 방식이 가능하다.

A. 운영자가 만드는 공식 그룹
B. 사용자가 만드는 소규모 그룹

현재 ERD는 owner 개념이 있으므로 B도 가능하지만 실제 UX/권한 정책은 팀에서 확정한다.

그룹 수정/삭제 시 기존 RANKING_PARTICIPANTS와 RANK_CHALLENGES 영향도 확인해야 한다.

---

## 8. 관리자 인증

USERS.role을 사용할 수 있다.

예시 개념:

```text
role=user
role=admin
```

정확한 문자열은 팀에서 확정한다.

관리자 API는:

```text
JWT 인증
→ role 확인
→ 권한 없으면 403
```

형태가 기본이다.

프론트에서 관리자 메뉴를 숨기는 것만으로 보안을 끝내지 않는다.

---

## 9. 가격/확률/보상 변경

가격과 보상은 게임 경제 전체에 영향을 준다.

따라서 운영자가 변경할 수 있게 만들더라도:

- 누가 바꿨는지
- 무엇을 바꿨는지
- 언제 바꿨는지

추적 필요성을 검토한다.

현재 별도 audit 테이블은 없으므로 MVP에서는 Git/설정 변경 기록으로 관리하고, 실제 운영 서비스 수준에서는 감사 이력을 확장할 수 있다.

---

## 10. 가챠 확률 저장 위치

현재 ERD에는 별도 가챠 확률 테이블이 없다.

후보:

A. 서버 설정/코드
B. CATS.rarity 기반 서버 규칙
C. 별도 테이블 확장

어떤 방식을 쓸지 확정되지 않았다.

확률을 관리자 화면에서 실시간 수정해야 하는 요구가 없다면 MVP는 설정 기반이 더 단순할 수 있다.

---

## 11. Seed와 운영 마스터데이터

개발 seed의 예시 가격/문제/고양이와 실제 기획 확정값을 혼동하지 않는다.

```text
개발 seed
= API 테스트를 위한 데이터

운영 master
= 실제 게임 규칙 데이터
```

환경에 따라 분리한다.

---

## 12. 변경 영향 확인

마스터데이터를 수정하기 전에 질문한다.

```text
이 데이터를 이미 누가 참조하고 있는가?
과거 기록이 깨지지 않는가?
현재 진행 중 room/challenge에 영향이 있는가?
프론트 캐시가 있다면 갱신되는가?
```

예를 들어 배틀 시작 후 TASK의 test_cases를 수정하면 진행 중 게임의 공정성에 영향을 줄 수 있다.

진행 중 콘텐츠의 기준을 고정할 필요가 있는지는 별도 정책으로 검토한다.

---

## 13. 관리자 API 우선순위

MVP에서 관리자 웹 화면까지 반드시 만들 필요는 없다.

우선순위 예:

```text
1. seed/DB로 마스터데이터 준비
2. 일반 사용자 기능 완성
3. 필요할 경우 최소 관리자 API
4. 관리자 UI는 이후
```

팀 프로젝트 범위에 맞춰 조절한다.

---

## 14. 테스트

- 일반 user가 관리자 endpoint 호출 → 거절
- admin 정상 등록/수정
- inactive TASK가 일반 목록에서 제외
- 참조 중인 TASK/ITEM/CAT 물리 삭제 방지
- 가격 변경 뒤 새 구매에는 새 가격 적용
- 기존 Inventory/UserCat 기록 유지
- test_cases가 일반 Response에 노출되지 않음

---

# 결론

관리자 기능의 목적은 CRUD 화면을 많이 만드는 것이 아니다.

```text
여러 사용자에게 공통 영향을 주는 기준 데이터
→ 일반 플레이 데이터와 분리
→ 권한을 제한
→ 과거 참조를 깨뜨리지 않게 변경
```

하는 것이 핵심이다.

MVP에서는 필요한 최소 운영 방식만 만들고, 관리자 UI 자체는 핵심 게임 기능보다 후순위로 둘 수 있다.
