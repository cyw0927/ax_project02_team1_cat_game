# 시간·타임존 정책

이 문서는 출석, 승급전, 배틀, 채점 기록처럼 **시간이 기능 결과를 바꾸는 곳에서 어떤 시간을 기준으로 판단할지** 정리한다.

시간 정책을 정하지 않으면 같은 기능도 서버 환경에 따라 결과가 달라질 수 있다.

예:

```text
한국에서는 8월 28일 00:05
서버는 UTC라서 아직 8월 27일 15:05
```

이 상태에서 `date.today()`만 사용하면 출석 날짜가 의도와 다를 수 있다.

---

## 1. 기본 원칙

- DB에 저장하는 datetime은 가능하면 UTC 기준으로 다룬다.
- 사용자가 보는 날짜/시간은 서비스 기준 타임존으로 변환한다.
- 출석처럼 `오늘`이라는 개념이 필요한 규칙은 서비스 타임존을 명시한다.
- 클라이언트가 보내는 현재 시간을 신뢰하지 않는다.
- 만료 여부는 서버 시간이 판단한다.

---

## 2. 출석

출석은 `check_in_date` 자체가 하루 1회 UNIQUE 기준이므로 타임존 선택이 매우 중요하다.

추천 MVP:

```text
서비스 기준 타임존 = Asia/Seoul (KST)
```

처리 예:

```text
서버 now(UTC)
→ Asia/Seoul로 변환
→ 날짜 부분 추출
→ check_in_date 결정
```

프론트가 `2026-08-28`을 보내서 서버가 그대로 믿는 구조는 피한다.

---

## 3. 승급전

`started_at`, `expires_at`은 절대 시각으로 비교한다.

```text
server_now >= expires_at
→ TIMEOUT
```

비교는 timezone-aware datetime으로 통일하는 편이 안전하다.

프론트 카운트다운은 표시용일 뿐 최종 TIMEOUT 판정은 서버가 한다.

---

## 4. TASK_ATTEMPTS

`attempted_at`은 학습 이력 정렬과 분석에 사용한다.

추천:

```text
UTC 저장
→ 화면에서 KST 변환
```

채점 완료시간이 필요하면 현재 ERD에 별도 컬럼이 없으므로 향후 `completed_at` 추가 여부를 검토할 수 있다.

---

## 5. 배틀

현재 ERD에는 방 생성시간/시작시간/종료시간 컬럼이 없다.

배틀 기록·제한시간·재접속 기능이 중요해지면 다음과 같은 컬럼이 필요할 수 있다.

```text
created_at
started_at
finished_at
```

다만 현재 문서 단계에서는 필요성을 기록만 하고 임의로 스키마를 바꾸지 않는다.

---

## 6. 일일 보상 초기화

향후 다음 기능들이 하루 단위 제한을 가질 수 있다.

```text
출석
학습 일일 보상 제한
배틀 보상 제한
랭킹 일일보상
무료 가챠
```

이 경우 모두 같은 서비스 날짜 기준을 써야 한다.

예:

```text
KST 00:00:00
→ 새 일자 시작
```

기능마다 서로 다른 기준을 쓰면 사용자가 어떤 보상은 초기화되고 어떤 보상은 안 되는 현상이 생긴다.

---

## 7. 클라이언트 시간 조작 방지

다음은 신뢰하지 않는다.

```json
{
  "today": "2026-08-30",
  "current_time": "..."
}
```

시간에 따른 권한/보상/만료 판정은 서버가 가진 시간을 기준으로 한다.

---

## 8. 개발/테스트

최소 테스트:

- KST 23:59 출석
- KST 00:00 직후 출석
- 같은 날 두 번 출석
- 승급전 만료 1초 전
- 승급전 만료 시각과 동일
- 승급전 만료 1초 후
- 서버 OS 타임존이 달라도 서비스 날짜가 동일한지

---

# 결론

MVP에서는 다음처럼 단순화하는 것이 이해하기 쉽다.

```text
datetime 저장/비교 = UTC
'오늘' 같은 일자 규칙 = Asia/Seoul
화면 표시 = 필요 시 KST
최종 판정 = 서버
```

정확한 서비스 타임존은 팀에서 확정한 뒤 코드 설정값으로 둔다.
