# 멱등성·중복 요청 정책

이 문서는 사용자가 버튼을 여러 번 누르거나 네트워크 재전송이 발생했을 때 **같은 요청이 두 번 처리되어도 데이터가 망가지지 않게 하는 방법**을 정리한다.

프론트 버튼 비활성화는 좋은 UX지만 최종 방어는 서버와 DB가 담당해야 한다.

---

## 1. 멱등성이란

같은 요청을 여러 번 보내도 최종 결과가 한 번 보낸 것과 같다면 멱등적이라고 볼 수 있다.

예:

```text
가구 위치를 x=3,y=5로 변경
→ 같은 PATCH를 두 번 보내도 최종 위치는 동일
```

반면:

```text
코인 100 지급
```

을 두 번 실행하면 200이 늘기 때문에 별도 방어가 필요하다.

---

## 2. 기능별 중복 위험

### 출석

```text
위험: 같은 날 보상 두 번
방어: UNIQUE(user_id, check_in_date)
```

### 상점

```text
위험: 구매 버튼 연타
의미: 사용자가 정말 2개 구매하려는지, 실수 재전송인지 구분 필요
```

현재 MVP에서는 각 요청을 독립 구매로 처리할 수 있으나 프론트는 처리 중 버튼을 막는다. 잔액은 Atomic Update로 음수 방지.

### 가챠

가챠는 요청 하나가 실제 재화 소비와 결과 생성을 만든다.

네트워크 timeout 후 프론트가 같은 요청을 재시도하면 **두 번 뽑히는 문제**가 생길 수 있다.

운영 수준에서는 `request_id`/idempotency key를 도입할 수 있다.

MVP에서는:
- 버튼 연타 방지
- transaction 보장
- 성공 응답을 받은 뒤에만 재호출 허용
- 동일 HTTP 요청 자동 재시도는 프론트에서 함부로 하지 않음

정도로 시작할 수 있다.

### 최초 정답 보상

같은 문제의 두 attempt가 동시에 PASSED가 될 수 있다.

```text
attempt 자체는 둘 다 기록 가능
보상은 정책에 따라 1회만
```

보상 자격 확인 구간에 DB 동시성 방어 필요.

### 배틀 종료 보상

같은 `finish` 로직이 두 번 실행되면 보상 중복 가능.

현재 ERD에는 지급 완료 기록 구조가 부족하므로 실제 배틀 보상 구현 전에 반드시 해결해야 한다.

### 승급전 성공 보상

`IN_PROGRESS → SUCCESS` 최초 전환에서만 지급하도록 설계하면 중복 방어에 유리하다.

---

## 3. HTTP Method 관점

일반적으로:

```text
GET    조회 → 데이터 변경 없음
PUT    동일 값으로 전체/명확한 상태 설정 → 비교적 멱등적 설계 가능
PATCH  값 설정이면 멱등 가능, +1 증가는 비멱등
POST   생성/행위 실행 → 중복 처리 검토 필요
DELETE 같은 대상 삭제 → 이미 없으면 결과 정의 필요
```

Method 이름만 믿지 말고 실제 비즈니스 효과를 본다.

---

## 4. idempotency key 후보

가챠나 결제처럼 한 요청을 정확히 한 번만 처리해야 하는 기능이 커지면 클라이언트가 UUID를 만든다.

예:

```http
Idempotency-Key: 4fd0...
```

서버는 이미 처리한 key면 기존 결과를 돌려준다.

하지만 현재 19테이블 ERD에는 idempotency 기록용 테이블이 없다. MVP에 꼭 필요한지 먼저 판단한다.

---

## 5. 프론트 규칙

```text
제출 클릭 → PENDING 동안 제출 버튼 비활성화
구매 클릭 → 응답 전 구매 버튼 잠금
가챠 클릭 → 결과 확정 전 재클릭 금지
Ready 변경 → 응답/이벤트 반영 전 반복 클릭 제한
```

단, 프론트 잠금만으로 보안을 보장하지 않는다.

---

## 6. API별 질문

쓰기 API를 만들 때 반드시 묻는다.

```text
1. 같은 요청이 두 번 오면 둘 다 실행되어야 하는가?
2. 첫 요청은 성공했는데 응답만 유실되면 어떻게 되는가?
3. 중복을 DB UNIQUE로 막을 수 있는가?
4. 상태 전이 조건으로 한 번만 실행되게 할 수 있는가?
5. request_id가 필요한가?
6. 중복 발생 시 200/409 중 무엇을 반환할 것인가?
```

---

## 7. 테스트

- 출석 20~50개 동시 요청 → 1개만 성공
- 같은 가구 이동 PATCH 10회 → 최종 위치 동일
- 같은 승급전 완료 처리 반복 → 보상 1회
- 같은 방 입장 요청 반복 → participant 1개
- 같은 학습 정답 동시 완료 → 보상 정책대로 1회
- 상점 동시 구매 → 잔액 음수 없음

---

# 결론

중복 요청은 `버튼 두 번 누르지 마세요`로 해결하는 문제가 아니다.

```text
UX 방어 = 프론트
비즈니스 방어 = 서버
최종 무결성 = DB
```

세 층을 나눠서 설계한다.
