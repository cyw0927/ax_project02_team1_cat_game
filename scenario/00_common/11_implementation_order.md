# 실제 구현 순서 초안

기능이 많다고 아무 순서로나 만들면 통합 단계에서 다시 고치게 된다. 선행조건이 있는 기능부터 순서를 잡는다.

## 0단계. 공통 규칙 확정

개발 전에 최소한 다음을 결정한다.

```text
TaskAttempt 상태값
보상 정책
test_cases 형식
가챠 가격/확률/중복
배틀 시작/점수/종료
승급전 문제/시간/합격
인증 방식
하우징 좌표 규칙
timezone
```

전부 완벽하게 결정할 필요는 없지만 자신이 구현할 기능의 핵심 규칙은 결정되어 있어야 한다.

---

## 1단계. 학습 상세/API 계약 보완

1. TASKS에 문제 지문을 어떻게 저장할지 결정
2. 필요하면 `title`, `description` 추가
3. 문제 상세 조회
4. `test_cases` 비노출 확인

이 단계는 Docker 전에 문제 데이터 계약을 깨끗하게 만드는 단계다.

---

## 2단계. TaskAttempt 제출 흐름

1. POST attempt
2. 사용자/문제 검증
3. PENDING 저장
4. 202 반환
5. 결과 조회 API 확인

아직 Docker가 없어도 여기까지는 테스트 가능하다.

---

## 3단계. Docker 채점 연결

1. test_cases parser
2. sandbox executor
3. 동시 실행 제한
4. RUNNING 상태
5. PASSED/WRONG/RUNTIME/TIMEOUT/SYSTEM 처리
6. 컨테이너 cleanup
7. polling 연결

이 부분을 먼저 안정화하면 배틀과 승급전도 채점기를 재사용할 수 있다.

---

## 4단계. 학습 보상/숙련도

채점 결과가 안정된 뒤 최초 정답, 힌트, 숙련도 정책을 연결한다.

동시 정답 중복 보상 테스트까지 수행한다.

---

## 5단계. 가챠

상점 Atomic Update 구현 경험을 재사용한다.

```text
비용 차감
→ 추첨
→ UserCat/마일리지
→ transaction
```

가챠 정책이 미정이면 구현 전에 확정한다.

---

## 6단계. 기존 상점·출석·하우징 검증

새로 크게 만드는 것보다 현재 구현이 시나리오와 맞는지 검사한다.

- 상점: 연타/rollback
- 출석: UNIQUE/보상 transaction/timezone
- 하우징: 소유권/배치 수량/position schema

문제가 발견된 것만 수정한다.

---

## 7단계. 배틀 기본 상태 머신

1. 방 생성
2. 방장 자동 참가 정책
3. 입장
4. Ready
5. 시작 조건
6. ROOM_TASKS 확정
7. FINISHED

WebSocket보다 먼저 DB 상태 전이를 확실히 만든다.

---

## 8단계. 배틀 채점/점수/WebSocket

1. 현재 문제 확인
2. sandbox 채점
3. score 갱신
4. WebSocket broadcast
5. 재접속
6. 승자 계산

---

## 9단계. 승급전 완료 흐름

현재 시작/코드 저장 이후 남은 기능을 연결한다.

```text
제출
→ 채점
→ is_passed
→ 전체 조건 확인
→ SUCCESS/FAILED/TIMEOUT
→ rank score 반영
```

`expires_at`은 서버 기준으로 검사한다.

---

## 10단계. 인증

인증은 모든 user_id API에 영향을 주므로 너무 일찍 넣으면 초반 디버깅이 복잡해질 수 있고, 너무 늦으면 API를 많이 고쳐야 한다.

추천은 핵심 도메인 API 형태가 안정된 시점에 JWT를 붙이고 다음을 일괄 수정하는 것이다.

```text
body/path user_id
→ current_user.id
```

단, 팀 일정상 인증 담당자가 병렬로 개발하는 것은 가능하다. API 적용 시점만 조율한다.

---

## 11단계. 통합 테스트

마지막에는 기능 하나씩이 아니라 실제 사용자 루프로 테스트한다.

예:

```text
회원가입/로그인
→ 문제 풀이
→ 채점
→ 보상 획득
→ 상점 구매
→ 하우징 배치
```

또는:

```text
방 생성
→ 2명 참가
→ Ready
→ 시작
→ 정답 제출
→ 실시간 점수
→ 종료
```

---

## 가장 중요한 구현 원칙

한 번에 전체 코드를 만들지 않는다.

```text
시나리오 1개 확정
→ 작은 구현
→ 검증
→ 다음 시나리오
```

단, 문서 작성은 지금처럼 관련 시나리오를 미리 넓게 정리해두고 실제 구현만 작은 단위로 진행한다.
