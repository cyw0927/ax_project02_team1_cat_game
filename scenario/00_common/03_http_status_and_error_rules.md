# HTTP 상태코드와 오류 응답 기준

이 문서는 같은 종류의 실패가 API마다 제각각 다른 상태코드를 쓰는 문제를 줄이기 위한 초안이다.

## 기본 기준

### 200 OK
조회나 동기 처리 성공.

예:
- 문제 상세 조회
- 랭킹 조회
- 하우스 조회

### 201 Created
새 리소스를 만들어 처리가 끝난 경우.

예:
- 방 생성
- 회원가입

### 202 Accepted
작업 접수는 끝났지만 뒤에서 계속 처리되는 경우.

예:
- 코드 제출 후 비동기 채점

### 204 No Content
삭제 성공처럼 본문이 필요 없는 경우에 사용할 수 있다. 다만 프론트가 갱신 데이터를 필요로 하면 200 응답이 더 편할 수 있다.

### 400 Bad Request
형식은 맞지만 비즈니스적으로 요청 자체가 잘못된 경우에 사용할 수 있다.

### 401 Unauthorized
로그인이 필요하거나 토큰이 유효하지 않은 경우.

### 403 Forbidden
로그인은 되어 있지만 권한이 없는 경우.

예:
- 일반 참가자가 방장 전용 시작 API 호출
- 다른 사람의 하우징 객체 수정 시도

### 404 Not Found
대상이 존재하지 않거나 일반 사용자에게 존재 여부를 구분해 보여줄 필요가 없는 경우.

예:
- 존재하지 않는 task
- 비활성 문제를 사용자 관점에서 숨길 경우

### 409 Conflict
현재 서버 상태와 요청이 충돌하는 경우.

예:
- 잔액 부족
- 이미 출석함
- 이미 참가 중
- 방 정원 초과
- 진행 중인 승급전이 이미 존재

### 422 Unprocessable Entity
FastAPI/Pydantic의 입력 검증 실패에 주로 사용.

### 500 Internal Server Error
예상하지 못한 서버 내부 오류. 사용자에게 DB/스택트레이스 원문을 노출하지 않는다.

### 503 Service Unavailable
Docker 채점 인프라 등 외부/내부 의존 서비스가 일시적으로 사용할 수 없을 때 검토할 수 있다.

## 오류 Response 초안

MVP에서 통일하고 싶다면 다음 정도가 단순하다.

```json
{
  "detail": "Insufficient balance"
}
```

조금 더 구조화하려면:

```json
{
  "error": {
    "code": "INSUFFICIENT_BALANCE",
    "message": "재화가 부족합니다."
  }
}
```

두 번째 방식은 프론트가 `message` 문자열에 의존하지 않고 `code`로 화면을 분기할 수 있다는 장점이 있다. 다만 MVP에서 모든 API를 한꺼번에 바꿀 필요는 없고 팀이 선택해야 한다.

## 중요한 원칙

- 사용자가 잘못한 오류와 서버 장애를 구분한다.
- 오답은 HTTP 실패가 아니라 '채점 작업은 성공했지만 결과가 오답'일 수 있다. 따라서 attempt 조회는 200이면서 `status=WRONG_ANSWER`가 자연스럽다.
- Docker 장애를 `WRONG_ANSWER`로 처리하지 않는다.
- 내부 SQL 오류, 파일 경로, 환경변수 값은 응답에 포함하지 않는다.
- 같은 실패는 가능한 한 같은 상태코드와 에러 코드를 사용한다.
