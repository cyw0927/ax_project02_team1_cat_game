# API 계약 공통 기준

API는 프론트와 백엔드가 서로 약속하는 데이터 계약이다. 화면을 먼저 보고 필요한 데이터만 주고받는 것을 원칙으로 한다.

## 1. Request는 최소한으로

프론트가 이미 보내지 않아도 되는 값은 보내지 않는다.

예를 들어 인증 도입 후 상점 구매는:

```json
{
  "item_id": 5
}
```

정도로 충분하다. `user_id`는 JWT에서 서버가 추출하는 방향이 안전하다.

## 2. 서버가 계산해야 하는 값을 프론트가 보내지 않기

다음 값은 프론트가 보내는 값을 믿으면 안 된다.

- 상품 가격
- 구매 후 잔액
- 정답 여부
- 보상량
- 배틀 최종 점수
- 승급전 성공 여부
- 출석 streak

이 값들은 서버가 DB와 비즈니스 규칙을 기준으로 직접 계산한다.

## 3. Response에는 화면 갱신에 필요한 값을 포함

예를 들어 상점 구매 성공 후 프론트는 잔액과 수량을 바로 갱신해야 한다.

```json
{
  "item_id": 5,
  "item_name": "캣타워",
  "quantity": 2,
  "current_balance": 800
}
```

성공 직후 다시 여러 API를 호출하지 않아도 화면이 갱신되게 하는 것이 좋다.

## 4. 내부 데이터는 노출하지 않기

문제 조회에서 `test_cases`, 정답 코드, 내부 채점 명령 등을 보내지 않는다.

서버 로그 경로, Docker 내부 정보, SQL 오류 원문도 사용자 응답에 그대로 노출하지 않는다.

## 5. ID 위치 기준

- 특정 리소스 하나 조회: Path parameter
  - `GET /tasks/{task_id}`
- 필터/검색: Query parameter
  - `GET /tasks?difficulty=basic`
- 생성/수정 데이터: JSON Body
  - `POST /attempts`

## 6. 비동기 작업

채점처럼 요청을 받았지만 최종 처리가 끝나지 않은 기능은 `202 Accepted`와 작업 ID를 반환한다.

```json
{
  "attempt_id": "uuid",
  "status": "PENDING"
}
```

프론트는 이후 결과 조회 API를 호출한다.

## 7. 상태값은 문자열을 제멋대로 만들지 않기

한 번 확정한 상태값은 문서, DB, 백엔드, 프론트 모두 같은 철자를 사용한다.

예:

```text
WAITING
IN_PROGRESS
FINISHED
```

`INPROGRESS`, `PLAYING`, `STARTED`처럼 같은 뜻의 다른 문자열을 섞지 않는다.

## 8. 날짜/시간

DB에는 timezone-aware 시간을 저장하는 방향을 우선 검토한다. 화면에서 한국시간 등으로 보여주는 것은 프론트 표시 단계에서 처리할 수 있다.

단, 출석 날짜처럼 '하루'의 경계가 비즈니스 규칙인 경우 어떤 timezone을 기준으로 할지 별도 확정해야 한다.

## 9. 리스트 응답

MVP에서는 단순 배열도 가능하지만 데이터가 많아질 기능은 향후 다음 구조를 고려할 수 있다.

```json
{
  "items": [],
  "total": 0
}
```

현재 규모에서는 불필요한 pagination을 억지로 넣지 않는다.

## 10. 확정 전 원칙

API 이름과 Request/Response 예시는 초안일 수 있다. 프론트와 백엔드가 합의한 뒤 계약으로 고정하고, 그 뒤에는 변경 시 양쪽을 같이 수정한다.
