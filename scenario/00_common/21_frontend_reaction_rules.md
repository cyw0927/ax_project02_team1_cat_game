# 프론트 화면 반응 규칙

이 문서는 같은 백엔드 결과라도 프론트에서 어떻게 보여줄지 통일하기 위한 기준이다.

백엔드가 정확한 응답을 보내도 화면 반응이 제각각이면 사용자 경험이 이상해진다. 특히 코드 제출, 상점, 가챠, 배틀, 승급전처럼 기다림이나 실패가 있는 기능은 화면 상태를 미리 정해두는 것이 좋다.

---

# 1. 버튼 클릭 직후

사용자가 서버 변경이 발생하는 버튼을 누르면 가능하면 즉시 중복 클릭을 막는다.

예:

```text
제출
구매
가챠
방 입장
Ready
게임 시작
승급전 시작
출석
```

추천 흐름:

```text
버튼 클릭
→ 버튼 비활성화
→ 로딩 표시
→ 응답 도착
→ 성공/실패 처리
→ 필요한 경우 다시 활성화
```

단, 이것은 UX 방어일 뿐이다.

```text
버튼 비활성화
≠ 백엔드 동시성 방어
```

API 직접 호출은 막지 못하므로 DB 방어는 별도로 필요하다.

---

# 2. 문제 제출 화면

## 제출 직후

```text
제출 버튼 잠금
'채점 접수 중...' 표시
```

202를 받으면:

```text
attempt_id 저장
'채점 중...' 표시
polling 시작
```

## PENDING

```text
채점 대기 중...
```

너무 오래 걸릴 경우:

```text
채점이 지연되고 있습니다.
잠시만 기다려 주세요.
```

같은 중간 메시지를 둘 수 있다.

## PASSED

```text
정답입니다!
보상 표시(실제 지급된 경우)
다음 문제 버튼 활성화
```

코드는 그대로 보이게 해도 된다.

## WRONG_ANSWER

```text
정답이 아닙니다.
코드 내용 유지
제출 버튼 다시 활성화
```

오답이라고 코드 편집기를 초기화하면 사용자가 수정하기 어렵다.

## RUNTIME_ERROR

```text
코드 실행 중 오류가 발생했습니다.
오류 핵심 메시지 표시
코드 유지
```

## TIMEOUT

```text
실행 시간이 초과되었습니다.
반복문 또는 종료 조건을 확인하세요.
```

## SYSTEM_ERROR

```text
채점 서버에 문제가 발생했습니다.
작성한 코드는 유지합니다.
잠시 후 다시 시도해주세요.
```

사용자 잘못처럼 보이게 하면 안 된다.

---

# 3. 상점 화면

## 구매 클릭

```text
구매 버튼 비활성화
로딩
```

## 성공

```text
구매 완료 토스트
상단 잔액 즉시 갱신
보유 quantity 갱신
```

서버가 돌려준 `current_balance`를 사용하면 프론트가 별도 계산할 필요가 없다.

## 잔액 부족

```text
'재화가 부족합니다'
구매 모달 유지 또는 닫기 정책 통일
버튼 다시 활성화
```

프론트가 자체 계산한 잔액보다 서버 응답을 최종 기준으로 본다.

---

# 4. 가챠 화면

가챠는 연출이 있기 때문에 **서버 성공이 확인되기 전에 결과 연출을 시작하지 않는 편**이 안전하다.

추천:

```text
가챠 클릭
→ 버튼 잠금
→ 서버 요청
→ 서버가 비용 차감 + 결과 저장 성공
→ 결과 Response
→ 그다음 연출 시작
```

재화 부족이면 연출 없이 즉시 경고한다.

서버 오류면 비용이 rollback되었는지 백엔드가 보장해야 하며 프론트는:

```text
가챠 처리에 실패했습니다.
재화는 차감되지 않았습니다.
```

같이 안내할 수 있다.

정확한 문구는 실제 transaction 보장이 확정된 뒤 사용한다.

---

# 5. 배틀 방 목록/입장

## 방 목록

방 상태에 따라 버튼을 다르게 보여준다.

```text
WAITING → 입장 가능
IN_PROGRESS → 입장 불가 또는 관전 정책 미정
FINISHED → 결과 조회 또는 숨김
```

## 입장 클릭

```text
입장 버튼 잠금
서버 요청
```

성공:

```text
대기방 화면 이동
```

방이 가득 찼다면:

```text
'방이 가득 찼습니다'
방 목록 인원수 다시 갱신
```

이미 시작됐다면:

```text
'이미 시작된 방입니다'
목록 갱신
```

---

# 6. Ready와 게임 시작

Ready 변경 성공 후에는 현재 사용자의 아이콘을 즉시 갱신한다.

다른 참가자의 Ready 변화는 WebSocket으로 반영한다.

```text
영우 ✅
민수 ✅
지수 ⏳
```

방장은 시작 조건이 충족될 때만 시작 버튼을 활성화할 수 있다.

그러나 프론트 버튼 활성 여부만 믿으면 안 되고 백엔드가 시작 조건을 다시 검사한다.

---

# 7. 배틀 진행 중

WebSocket 이벤트는 화면 실시간 반영용이다.

예:

```text
score_update
participant_ready
battle_started
battle_finished
participant_reconnected
```

점수 이벤트를 받을 때 프론트가 기존 점수에 `+100`을 직접 더하기보다 **서버가 보내준 최종 current_score를 화면에 넣는 방식**이 안전하다.

왜냐하면 이벤트 누락/중복으로 클라이언트 계산이 어긋날 수 있기 때문이다.

---

# 8. 승급전 화면

## 시작

서버가 challenge 생성에 성공한 뒤 제한시간 화면을 시작한다.

프론트 타이머는 사용자에게 보여주는 용도다.

최종 만료 판정은 항상 서버의 `expires_at`을 기준으로 한다.

## 자동 저장

코드 저장 실패가 발생해도 사용자가 작성 중인 코드 자체는 브라우저 메모리에 유지한다.

저장 실패 표시:

```text
임시 저장 실패
네트워크 연결을 확인하세요.
```

## TIMEOUT

서버에서 TIMEOUT 응답을 받으면:

```text
코드 편집기 입력 잠금
제출 버튼 비활성화
시간 초과 결과 표시
```

클라이언트 타이머가 0이 되기 전에 서버에서 이미 만료 판정이 날 수도 있으므로 서버 응답을 우선한다.

---

# 9. 로그인/인증

## 401

토큰 만료/미인증.

Refresh Token을 사용한다면 재발급을 시도하고, 실패하면 로그인 화면으로 이동한다.

Refresh 정책이 없다면 바로 로그인 화면으로 보낸다.

## 403

로그인은 되어 있으므로 로그인 화면으로 보내기보다:

```text
이 기능을 사용할 권한이 없습니다.
```

를 보여주는 것이 자연스럽다.

---

# 10. 하우징

## 배치

가구를 드래그하는 순간부터 DB를 계속 업데이트하기보다 사용자가 위치를 확정했을 때 저장하는 방식이 단순하다.

```text
가구 선택
→ 화면에서 미리보기 이동
→ 위치 확정
→ 서버 저장
→ 성공 후 고정
```

저장 실패 시:

```text
이전 위치로 되돌리기
또는
배치 취소
```

정책을 통일한다.

## 다른 사용자 하우스

읽기 전용임을 UI에서도 명확히 한다.

편집/삭제 버튼을 숨긴다.

백엔드도 다른 사용자의 object 변경을 거부해야 한다.

# 11. 출석

출석 성공:

```text
출석 완료
연속 N일
획득 보상
```

이미 출석:

```text
오늘은 이미 출석했습니다.
```

중복 요청이 발생해도 화면에서 보상이 두 번 올라가는 애니메이션을 보여주지 않도록 서버 성공 응답 기준으로 표시한다.

---

# 12. 공통 로딩 원칙

짧은 요청:

```text
버튼 spinner
```

조금 오래 걸리는 요청:

```text
상태 문구 + spinner
```

비동기 채점처럼 오래 걸릴 수 있는 요청:

```text
접수 완료
→ 별도 상태 조회
```

사용자가 무엇을 기다리는지 알 수 있어야 한다.

---

# 13. 공통 오류 원칙

사용자에게 그대로 보여주지 않을 것:

```text
Python 서버 traceback
SQL 문
DB 접속주소
Docker 내부 경로
password hash
```

사용자에게 보여줄 것:

```text
무엇이 실패했는지
사용자가 무엇을 하면 되는지
작성 중 데이터가 유지되는지
재시도가 가능한지
```

특히 학습게임에서는 오류 메시지가 벌점처럼 느껴지기보다 다음 행동을 알려주는 방향이 좋다.
