이 문서는 `A-01_task_detail_view.md` 다음 단계다. 초보자가 읽어도 흐름을 따라갈 수 있도록 **사용자 행동 → 프론트 → 백엔드 → DB → Docker/동시성 → 응답 → 테스트** 순서로 적는다.

# A-02. 코드 정상 제출

## 무엇을 해결하나
사용자가 코드를 작성하고 `제출` 버튼을 눌렀을 때, 서버가 코드를 바로 Docker에서 끝까지 실행시키며 HTTP 요청을 붙잡는 대신 **채점 작업을 먼저 DB에 등록하고 빠르게 응답**하는 흐름이다.

## 추천 흐름
```text
사용자 제출 클릭
→ 프론트 제출 버튼 비활성화
→ POST /attempts
→ 백엔드 사용자/문제 확인
→ TASK_ATTEMPTS INSERT(status=PENDING)
→ COMMIT
→ 202 Accepted + attempt_id 반환
→ 프론트는 '채점 중' 표시
```

## Request 초안
인증 전 임시 구조라면:
```json
{
  "user_id": "uuid",
  "task_id": "uuid",
  "submitted_code": "def add(a, b):\n    return a + b",
  "used_hint": false
}
```

JWT 도입 후에는 `user_id`를 body에서 제거하고 토큰에서 사용자 ID를 가져오는 방향이 안전하다.

## 백엔드 검사
1. 사용자가 존재하는가?
2. task가 존재하는가?
3. `is_active=true`인가?
4. 코드가 빈 문자열인지 등 최소 입력 검증이 필요한가?
5. 통과하면 attempt를 만든다.

## DB 변경
`TASK_ATTEMPTS`에 새 행을 만든다.
```text
status = PENDING
is_correct = false(현재 ERD 기준)
used_hint = 요청값
attempted_at = 서버 시간
```

`PENDING`인데 `is_correct=false`인 것은 의미가 조금 어색하지만 현재 컬럼이 boolean이므로 status로 상태를 구분한다. 향후 nullable 여부를 별도 논의할 수 있다.

## 성공 Response
```http
202 Accepted
```
```json
{
  "attempt_id": "uuid",
  "status": "PENDING"
}
```

## 왜 202인가
`200 OK`는 보통 요청 처리가 끝났다는 인상이 강하다. 여기서는 채점이 아직 안 끝났고 서버가 작업을 접수한 상태라서 `202 Accepted`가 자연스럽다.

## 동시성
이 단계에서 Docker를 바로 여러 개 띄우지 않는다. attempt 등록은 일반 INSERT이며, 실제 Docker 수 제한은 A-03/A-04에서 담당한다.

## 테스트
- 정상 사용자 + 정상 task + 코드 → 202
- 없는 user → 404
- 없는 task → 404
- 비활성 task → 404
- attempt row가 실제 PENDING인지 DB 확인

# A-03. 채점 대기(PENDING)

## 무엇을 해결하나
30명이 동시에 제출해도 컨테이너 30개를 동시에 만들지 않고, DB에 작업을 쌓아둔 뒤 실행 가능한 순서가 오기를 기다리는 문제다.

## 기본 개념
```text
HTTP 요청을 많이 받을 수 있는 것
≠
Docker 컨테이너를 무제한 띄워도 되는 것
```

FastAPI가 요청을 빠르게 받아도 Docker는 CPU/메모리를 실제로 사용하므로 별도 제한이 필요하다.

## 추천 흐름
```text
attempt=PENDING
→ BackgroundTasks에 채점 함수 등록
→ 채점 함수가 동시 실행 슬롯을 기다림
→ 슬롯 확보
→ RUNNING 변경
→ Docker 실행
```

## 동시 실행 수
요구사항은 **3~5개 수준으로 제한**하는 것이다. 정확한 숫자는 설정값으로 두는 편이 좋다. 현재 프로젝트가 3을 사용한다면 MVP 기본값으로 운용할 수 있지만 기획 규칙으로 영구 고정할 필요는 없다.

## 중요한 제한
`threading.BoundedSemaphore(3)` 같은 방식은 **한 Python 프로세스 안에서만** 3개를 보장한다. Uvicorn worker를 여러 개 실행하면 서버 전체 개수는 더 많아질 수 있다.

MVP에서는 단일 worker + semaphore 방식이 단순하다. 운영 규모가 커지면 Redis/Celery 같은 외부 큐를 검토한다.

## 프론트
PENDING이면 사용자가 오류라고 오해하지 않도록:
```text
채점 대기 중...
```
표시하고 제출 버튼을 잠시 막는다.

## 테스트
동시에 여러 attempt를 만들어 실제 실행 중 컨테이너 수가 설정값을 넘지 않는지 확인한다.

# A-04. 정답 처리(PASSED)

## 무엇을 해결하나
Docker에서 모든 테스트를 통과한 경우 정답 기록, 보상, 숙련도를 어떻게 반영할지 결정한다.

## 처리 순서 추천
```text
Docker 테스트 모두 통과
→ attempt 결과를 정답으로 판정
→ 최초 정답인지 확인
→ 최초라면 보상 정책 적용
→ 필요하면 숙련도 갱신
→ TASK_ATTEMPTS 최종 상태 저장
→ COMMIT
```

## 최초 정답이 중요한 이유
재제출이 무제한이면 같은 정답 코드를 계속 제출해서 코인을 무한 획득할 수 있다.

```text
첫 PASSED → 보상 가능
두 번째 PASSED → 기록은 남기되 보상 없음
```

정확한 보상량은 기획 확정이 필요하다.

## 동시 중복 정답 문제
같은 사용자가 같은 task를 거의 동시에 두 번 제출해 둘 다 정답이 될 수 있다. 두 worker가 동시에 `이전 정답 없음`을 확인하면 보상이 두 번 지급될 위험이 있다.

해결책 후보:
1. 보상 확정 구간에서 사용자 row를 짧게 `FOR UPDATE`로 잠그고 과거 PASSED를 재확인
2. 최초 보상 이력을 별도 UNIQUE 구조로 관리

현재 ERD를 유지하려면 1번이 구현 부담이 작다. 다만 정확한 구현은 팀 승인 후 확정한다.

## DB
- `TASK_ATTEMPTS`
- `USERS.balance` (보상 시)
- `USER_PROFICIENCY` (숙련도 반영 시)

## 테스트
- 첫 정답
- 같은 문제 재정답
- 동시에 두 정답 완료
- 힌트 사용 정답

# A-05. 오답 처리(WRONG_ANSWER)

## 무엇을 해결하나
코드는 정상 실행됐지만 테스트 예상값과 실제값이 다른 경우다.

## 예
서버 테스트:
```text
add(1, 2) expected 3
```
사용자 결과:
```text
2
```

이 경우 Docker 자체는 성공적으로 실행됐다. 따라서 서버 장애나 런타임 오류와 구분해야 한다.

## 추천 처리
```text
실행 성공
→ 테스트 비교 실패
→ status=WRONG_ANSWER
→ is_correct=false
→ 보상 없음
→ attempt 저장
```

## 프론트
- `정답이 아닙니다` 표시
- 사용자가 작성한 코드는 유지
- 다시 제출 가능
- 힌트 버튼 정책에 따라 노출

## 왜 기록을 남기나
오답도 학습 이력이다. 몇 번 틀렸는지는 숙련도/추천 문제를 개선할 때 사용할 수 있고, 나중에 디버깅할 때도 유용하다.

## 테스트
- 첫 테스트만 실패
- 마지막 테스트만 실패
- 여러 테스트 실패
- 오답 뒤 재제출 성공

# A-06. 실행 오류(RUNTIME_ERROR)

## 무엇을 해결하나
사용자 코드가 실행 도중 Python 오류를 발생시키는 상황이다.

예:
```python
print(not_defined_variable)
```

## 구분 이유
오답과 실행 오류는 사용자에게 해결 방법이 다르다.
- 오답: 로직을 고쳐야 함
- 런타임 오류: 오류 메시지를 읽고 코드 자체를 고쳐야 함

## 추천 처리
```text
Docker 실행
→ Python 비정상 종료
→ stderr 확인
→ status=RUNTIME_ERROR
→ is_correct=false
```

## 응답 메시지
사용자에게 도움이 되는 오류 핵심은 보여주되 서버 내부 경로, Docker 설정 등 불필요한 내부 정보는 그대로 노출하지 않는 편이 안전하다.

현재 ERD에는 오류 메시지를 저장할 컬럼이 없다. 결과 메시지를 나중에도 조회하려면 `TASK_ATTEMPTS.result_message` 같은 nullable 컬럼 추가를 검토해야 한다.

## 테스트
- SyntaxError
- NameError
- TypeError
- ZeroDivisionError

---

# A-07. 시간 초과(TIMEOUT)

## 무엇을 해결하나
무한 루프나 지나치게 오래 걸리는 코드 때문에 컨테이너가 계속 살아있는 문제를 막는다.

예:
```python
while True:
    pass
```

## 처리
```text
Docker 실행
→ 서버가 제한 시간만 기다림
→ 제한 초과
→ 컨테이너 강제 종료
→ status=TIMEOUT
→ cleanup
```

## 중요
메모리 128MB, CPU 0.5와 별도로 **실행 시간 제한**이 필요하다. 정확한 초 단위 값은 아직 팀이 확정해야 한다.

## 프론트
```text
실행 시간이 초과되었습니다.
반복문이나 종료 조건을 확인해 주세요.
```

## 테스트
- 무한루프
- sleep 등으로 장시간 대기
- 정상 코드는 제한시간 안에 성공
- TIMEOUT 후 컨테이너가 삭제되었는지 확인

# A-08. 채점 시스템 오류(SYSTEM_ERROR)

## 무엇을 해결하나
사용자 코드가 아니라 서버/Docker 쪽 문제로 채점이 실패한 상황이다.

예:
- Docker Engine 연결 실패
- 채점 이미지 없음
- 컨테이너 생성 실패
- 서버 내부 예외

## 왜 분리하나
이 상황을 WRONG_ANSWER로 처리하면 사용자는 자신의 코드를 계속 고치게 된다. 사용자 잘못과 인프라 장애는 반드시 구분하는 편이 좋다.

## 처리
```text
채점 인프라 오류 발생
→ status=SYSTEM_ERROR
→ 보상/숙련도 변경 없음
→ 오류 로그는 서버 측 기록
→ 사용자에게 재시도 안내
```

## PENDING 고착 문제
BackgroundTasks는 서버 프로세스가 죽으면 작업을 잃을 수 있다. 그래서 오래된 PENDING을 어떻게 처리할지도 결정해야 한다.

MVP 후보:
- 일정 시간 이상 PENDING이면 SYSTEM_ERROR로 정리
- 사용자가 다시 제출하도록 안내

## 테스트
Docker를 일부러 사용할 수 없는 환경으로 만들어 SYSTEM_ERROR가 오답과 구분되는지 본다.

# A-09. 재제출

## 무엇을 해결하나
오답/오류 후 코드를 고쳐 다시 제출하는 흐름이다.

## 추천 원칙
기존 attempt row를 덮어쓰지 않고 **새 TASK_ATTEMPTS row를 하나 더 만든다.**

```text
1차 WRONG_ANSWER
2차 RUNTIME_ERROR
3차 PASSED
```

이력이 전부 남아야 학습 과정이 보인다.

## 프론트
기존 코드 내용을 유지한 채 수정 → 제출 → 새 attempt_id를 받는다.

## 중복 클릭
현재 attempt가 PENDING/RUNNING일 때 프론트 버튼을 비활성화하는 것은 좋은 UX다. 하지만 악의적 직접 API 호출까지 완전히 막는 규칙을 둘지는 기획 선택이다. 재제출 자체를 제한하지 않는다면 서버는 새 attempt 생성을 허용할 수 있다.

## 테스트
- 오답 후 재제출
- 런타임 오류 후 재제출
- 여러 번 제출한 뒤 시도 이력 순서 확인

# A-10. 중복 보상 방어

## 무엇을 해결하나
정답 재제출, 동시 제출, 요청 재전송 때문에 같은 문제의 최초 정답 보상이 여러 번 지급되는 것을 막는다.

## 위험한 구현
```text
SELECT 과거 정답 확인
→ 없음
→ Python에서 balance + reward 계산
→ UPDATE
```
두 worker가 동시에 들어오면 둘 다 `없음`을 보고 보상을 지급할 수 있다.

## 추천 설계 방향
현재 19테이블 ERD를 최대한 유지한다면 보상 확정 순간만 짧게 직렬화한다.

개념 흐름:
```text
정답 채점 완료
→ 보상 확정 트랜잭션 시작
→ 사용자/관련 기준 row 잠금 검토
→ 이 attempt 이전의 PASSED 존재 재확인
→ 없을 때만 DB 연산으로 balance 증가
→ attempt PASSED 확정
→ COMMIT
```

정확히 어떤 row를 잠글지는 구현 시 다시 검증해야 한다. 장기적으로는 `REWARD_HISTORY` 같은 별도 테이블 + UNIQUE가 가장 명확하지만 현재 20개 미만 제약 때문에 테이블 추가는 기획 판단이 필요하다.

## 반드시 테스트할 것
- 같은 코드를 순차 10회 정답 제출
- 동일 문제 정답 2건 동시 완료
- 힌트 사용 여부가 다른 정답 동시 완료
- 첫 정답만 보상이 증가했는지 balance 확인

# A 영역 전체에서 아직 확정해야 할 것

1. `TASKS.title`, `TASKS.description` 추가 여부
2. `TASKS.test_cases` JSON 저장 형식
3. 상태값 최종 목록
4. Docker 실행 제한 시간
5. 출력 최대 크기
6. 동시 컨테이너 정확한 기본값(3~5 중 선택)
7. 최초 정답 보상량
8. 힌트 사용 시 보상 정책
9. 숙련도 증가 공식
10. 오류 메시지를 DB에 저장할 컬럼 추가 여부
11. 오래된 PENDING 복구/정리 정책

이 항목은 코드에 임의의 숫자나 규칙을 넣기 전에 팀이 확정해야 한다.
