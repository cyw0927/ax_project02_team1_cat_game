# C-01 ~ C-10. 실시간 배틀 상세 시나리오

이 문서는 배틀 방 생성, 입장, 준비, 시작, 문제 제출, 점수 반영, 종료까지의 흐름을 초보자도 따라갈 수 있게 정리한다.

> 최소 인원, Ready 조건, 정답 점수, 감점, 속도 보너스, 동점 처리, 보상은 아직 확정하지 않는다.

# C-01. 배틀 방 목록 조회

## 목적
사용자가 배틀 메뉴에 들어왔을 때 참가 가능한 방을 보여준다.

## 흐름
```text
배틀 메뉴 클릭
→ 프론트가 방 목록 API 요청
→ 백엔드가 ROOMS 조회
→ 필요하면 ROOM_PARTICIPANTS 수를 함께 계산
→ 제목/상태/현재 인원/최대 인원 반환
→ 프론트가 목록 표시
```

## DB
- `ROOMS`
- 필요 시 `ROOM_PARTICIPANTS`

## 변경
없다. 조회만 한다.

## Lock
필요 없다. 방 목록 조회는 상태를 읽기만 한다.

## 테스트
- WAITING 방
- IN_PROGRESS 방
- FINISHED 방을 화면에서 어떻게 표시할지
- 빈 방 목록

# C-02. 배틀 방 생성

## 목적
사용자가 새 배틀 방의 방장이 되는 흐름이다.

## 기본 Request 후보
```json
{
  "title": "반복문 연습방",
  "max_participants": 4
}
```

인증 전에는 host_user_id를 받을 수 있지만 JWT 이후에는 로그인 사용자에서 host를 결정하는 편이 안전하다.

## 백엔드 검사
1. 사용자 존재/인증 확인
2. 제목 길이 등 validation
3. max_participants 허용 범위 확인
4. `ROOMS` 생성

## DB
```text
ROOMS
status = WAITING
host_user_id = 현재 사용자
```

## 중요 미정
방 생성과 동시에 방장을 `ROOM_PARTICIPANTS`에도 넣을지 정해야 한다.

### 추천
방장은 실제 배틀 참가자이기도 하므로 **방 생성 시 자동 참가자 등록**이 자연스럽다. 이 경우 ROOMS 생성과 ROOM_PARTICIPANTS INSERT를 같은 transaction으로 묶는다.

## 테스트
- 정상 생성
- 잘못된 최대 인원
- 방장이 참가자 목록에 자동 포함되는 정책 여부

# C-03. 배틀 방 정상 입장

## 목적
정원이 있는 방에 여러 사용자가 동시에 들어올 때 정원을 넘지 않도록 안전하게 처리한다.

## 왜 FOR UPDATE가 필요한가
단순히 숫자 하나를 줄이는 문제가 아니라 다음 여러 조건을 함께 읽어야 한다.

```text
방이 WAITING인가?
이미 참가했나?
현재 몇 명인가?
max_participants보다 적나?
```

그래서 방 row를 잠근 뒤 조건을 확인하는 방식이 적합하다.

## 처리 순서
```text
BEGIN
→ ROOMS SELECT ... FOR UPDATE
→ 방 존재/WAITING 확인
→ 이미 참가 여부 확인
→ 현재 참가자 COUNT
→ 정원 확인
→ ROOM_PARTICIPANTS INSERT
→ COMMIT
```

## 실패
- 방 없음 → 404
- 이미 시작됨 → 409
- 이미 참가 중 → 409
- 정원 가득 참 → 409

## DB 제약
`ROOM_PARTICIPANTS(room_id, user_id)` UNIQUE를 두면 중복 참가를 DB에서도 막을 수 있다.

## 테스트
현재 3/4인 방에 두 요청을 동시에 보내 한 명만 성공하는지 확인한다.

---

# C-04. 마지막 한 자리 동시 입장 경쟁

## 상황
4명 정원이고 현재 3명이다. A와 B가 거의 같은 순간 입장한다.

## Lock이 없으면
```text
A: 현재 3명 확인
B: 현재 3명 확인
A: INSERT
B: INSERT
→ 5명
```

## FOR UPDATE 적용
```text
A가 ROOMS row lock
→ 3명 확인
→ A INSERT
→ COMMIT
→ lock 해제

B가 그 다음 lock 획득
→ 4명 확인
→ 정원 초과라서 실패
```

## 초보자 핵심
`FOR UPDATE`는 '방 전체를 영원히 잠그는 것'이 아니라 **짧은 transaction 동안 다른 입장 판단을 줄 세우는 것**이다.

## 테스트
2개 이상의 동시 요청을 실제로 보내 최종 participant 수가 max를 넘지 않는지 확인한다.

# C-05. Ready 상태 변경

## 목적
참가자가 게임 시작 준비가 됐다는 상태를 저장한다.

## 흐름
```text
사용자 Ready 클릭
→ 서버가 해당 방 참가자인지 확인
→ 방이 WAITING인지 확인
→ ROOM_PARTICIPANTS.is_ready = true
→ COMMIT
→ 다른 참가자 화면에 상태 반영
```

## 해제
UI가 Ready 취소를 지원한다면 `true/false` 토글 API로 만들 수 있다.

## DB
`ROOM_PARTICIPANTS`

## Lock
단순히 본인의 boolean을 바꾸는 작업이라 일반 UPDATE로 충분하다. 방 시작과 동시에 Ready 변경이 경쟁할 때는 시작 로직 쪽에서 방 상태를 잠그고 최종 조건을 재검사하는 것이 중요하다.

## 실시간 반영
대기방 사용자에게 WebSocket으로 ready_update 이벤트를 보내거나 짧은 polling을 사용할 수 있다. 배틀은 어차피 WebSocket을 사용할 가능성이 높아 WebSocket 재사용이 자연스럽다.

# C-06. 방장 게임 시작

## 목적
방장이 시작 버튼을 눌렀을 때 실제 게임을 시작해도 되는지 최종 검증한다.

## 서버가 확인할 것
1. 요청자가 host인가?
2. 방이 WAITING인가?
3. 최소 참가 인원을 만족했는가?
4. Ready 조건을 만족했는가?
5. ROOM_TASKS가 준비되어 있는가?

## 추천 처리
여러 조건을 동시에 보므로 방 row를 `FOR UPDATE`로 잠그고 최종 상태를 확인한 뒤 `IN_PROGRESS`로 변경하는 방식이 안전하다.

```text
BEGIN
→ room lock
→ host 확인
→ 인원 COUNT
→ Ready 확인
→ 문제 확인
→ status=IN_PROGRESS
→ COMMIT
→ start event broadcast
```

## 실패
- 방장 아님 → 403
- 인원 부족 → 409
- 준비 부족 → 409
- 이미 시작 → 409

## 미정
최소 인원과 방장 Ready 여부를 팀이 정해야 한다.

# C-07. 일반 참가자의 게임 시작 요청

## 목적
프론트 버튼을 숨겼다고 서버 권한 검사를 생략하지 않는다는 것을 명확히 한다.

## 상황
일반 참가자가 API를 직접 호출한다.

## 처리
```text
ROOMS.host_user_id
vs
현재 로그인 user_id 비교
→ 다르면 403 Forbidden
```

## 이유
프론트에서 버튼이 없더라도 API 요청은 개발자 도구나 스크립트로 만들 수 있다.

## DB 변경
없음.

## 테스트
- host → 성공 가능
- participant → 403
- 방에 참가하지도 않은 user → 403/404 정책 확인

# C-08. 배틀 문제 정답 및 점수 증가

## 목적
배틀 도중 사용자가 문제를 풀었을 때 채점 결과를 실시간 점수에 연결한다.

## 흐름
```text
현재 ROOM_TASK 문제 제출
→ 사용자가 해당 방 participant인지 확인
→ 방이 IN_PROGRESS인지 확인
→ 제출한 task가 현재 방 문제인지 확인
→ sandbox 채점
→ 정답
→ current_score 증가
→ score_update WebSocket broadcast
```

## DB
- `ROOMS`
- `ROOM_PARTICIPANTS`
- `ROOM_TASKS`
- `TASKS`

## 점수 증가
정답 점수는 아직 미정이다. 점수 값을 프론트가 보내면 안 되고 서버가 규칙을 적용해야 한다.

## 중복 정답 문제
같은 문제를 여러 번 맞혀 점수를 반복 획득할 수 있는지 현재 ERD만으로는 명확하지 않다. `TASK_ATTEMPTS`를 배틀과 공용으로 쓸지, 현재 문제 통과 상태를 어디에서 판단할지 추가 설계가 필요하다.

MVP에서는 `한 참가자에게 같은 ROOM_TASK의 점수는 한 번만` 같은 정책이 필요하다면 그 사실을 저장할 수단부터 확인해야 한다.

## 테스트
- 정답 1회
- 같은 문제 정답 재제출
- 다른 방 task 제출 조작
- 게임 종료 후 제출

# C-09. 배틀 문제 오답

## 목적
오답을 점수와 진행에 어떻게 반영할지 결정한다.

## 공통 처리
```text
sandbox 정상 실행
→ 테스트 실패
→ 오답 응답
```

## 기획 선택지
1. 오답 감점 없음 + 재도전 허용
2. 오답 감점 있음
3. 문제당 1회 제출만 허용
4. 제한 시간 내 무제한 재도전

### 추천 MVP
초보 학습 게임이라는 성격을 고려하면 **오답 감점 없음 + 필요 시 재도전**이 단순하고 부담이 적다. 다만 배틀 밸런스는 기획 승인 후 확정한다.

## 실시간 공개 범위
다른 사용자에게 `누가 틀렸는지`까지 보여줄지, 점수 변화만 보여줄지도 UX 결정 사항이다.

## 테스트
오답 시 점수와 다음 문제 상태가 기획 규칙대로 유지되는지 확인한다.

# C-10. 배틀 종료와 승자 결정

## 목적
게임 종료 시 더 이상 점수가 변하지 않게 하고 최종 결과를 계산한다.

## 종료 조건 후보
- 모든 문제 종료
- 제한 시간 종료
- 방장 종료
- 서버가 정의한 게임 완료 조건

정확한 조건은 기획 확정이 필요하다.

## 처리
```text
종료 조건 만족
→ room lock/상태 최종 확인
→ ROOMS.status=FINISHED
→ 최종 score 조회
→ 개인전/팀전 승자 계산
→ 결과 event broadcast
```

## 개인전
`ROOM_PARTICIPANTS.current_score` 최고값을 비교한다.

## 팀전
```text
GROUP BY team_name
SUM(current_score)
```
방식으로 팀 총점을 계산할 수 있다.

## 미정
- 동점 공동 우승인지 추가 문제인지
- 중도 이탈자의 점수 유지 여부
- 종료 후 보상 지급 여부
- 방 데이터 보존 기간

## 테스트
- 개인전 정상 종료
- 팀전 합산
- 동점
- 동시에 종료 요청
- FINISHED 이후 점수 변경 거부
