# B-01 ~ B-10. 가챠 상세 시나리오

이 문서는 가챠 기능을 구현하기 전에 화면 흐름, DB 처리, 재화 차감, 중복 처리, 실패 복구를 초보자도 이해할 수 있게 정리한 문서다.

> 가챠 가격, 희귀도 확률, 중복 보상, 천장 수치는 아직 확정하지 않는다. 와이어프레임의 숫자는 참고값일 뿐이다.

---

# B-01. 가챠 화면 진입

## 목적
사용자가 가챠 메뉴를 열었을 때 현재 뽑을 수 있는 고양이 정보와 자신의 재화 상태를 보여준다.

## 흐름
```text
가챠 메뉴 클릭
→ 프론트가 가챠 화면용 데이터 요청
→ 백엔드가 CATS 조회
→ 사용자 balance/mileage 조회
→ 가챠 화면 표시
```

## DB
- `CATS`: 고양이 이름, 희귀도, 페르소나 등
- `USERS`: balance, mileage

## DB 변경
없다. 조회만 한다.

## 주의
희귀도별 실제 확률을 프론트에서 결정하게 두면 안 된다. 확률 정책은 서버가 기준을 가지고 있어야 한다. 프론트는 설명용 확률을 표시할 수 있지만 실제 추첨은 백엔드가 한다.

## 테스트
- 정상 사용자
- 고양이 데이터가 하나도 없는 경우
- balance가 0인 경우에도 화면 자체는 열리는지

# B-02. 가챠 요청 단위 정상 처리

## 목적
사용자가 1회 뽑기 버튼을 눌렀을 때 재화를 정확히 한 번 차감하고 결과 고양이를 저장한다.

## 추천 흐름
```text
사용자 1회 뽑기 클릭
→ 프론트 버튼 비활성화 + 로딩
→ POST /gacha/pulls 같은 API 요청
→ 백엔드 비용 정책 확인
→ USERS balance Atomic Update
→ 성공했을 때만 추첨
→ CATS 후보 중 결과 결정
→ USER_CATS 저장
→ COMMIT
→ 결과 + 남은 balance 반환
```

## 재화 차감
Python에서 `balance - price`를 계산한 뒤 저장하지 않는다.

개념 SQL:
```sql
UPDATE users
SET balance = balance - :price
WHERE id = :user_id
  AND balance >= :price;
```

영향받은 행이 0이면 재화 부족이다.

## 왜 Atomic Update인가
사용자가 버튼을 연타하거나 API를 동시에 호출해도 DB가 각 요청에서 현재 잔액 조건을 다시 확인하기 때문에 재화 복사를 막을 수 있다.

## Transaction
재화 차감과 `USER_CATS` 저장은 같은 transaction에 묶는다. 결과 저장이 실패하면 차감도 rollback되어야 한다.

## 테스트
- 잔액 충분
- 딱 가격만큼 보유
- 잔액 부족
- 동시에 여러 번 요청

# B-03. 다회 뽑기가 채택될 경우의 처리

## 목적
10회 또는 10+1 같은 다회 뽑기를 한 요청으로 안전하게 처리한다.

## 흐름
```text
다회 뽑기 클릭
→ 총 비용 확인
→ balance를 한 번 Atomic Update
→ 정해진 횟수만큼 서버에서 추첨
→ 결과들을 저장
→ 전부 성공하면 COMMIT
→ 결과 리스트 반환
```

## 중요한 이유
다회 뽑기를 프론트가 1회 API를 10번 호출하는 방식으로 구현하면 중간 실패, 네트워크 끊김, 부분 결제 같은 상태가 복잡해진다.

따라서 하나의 다회 뽑기 요청에서 서버가 전체를 처리하는 편이 이해하기 쉽다.

## Response 예시 형태
```json
{
  "results": [
    {"cat_id": 1, "rarity": "..."},
    {"cat_id": 4, "rarity": "..."}
  ],
  "current_balance": 1234
}
```

정확한 횟수와 보장 규칙은 기획 확정 후 넣는다.

## 테스트
- 전체 결과 수 확인
- 차감 금액이 정확한지
- 중간 저장 실패 시 전체 rollback

---

# B-04. 재화 부족

## 상황
사용자가 가격보다 적은 balance를 가지고 있다.

## 처리
Atomic Update 결과가 0행이면:
```text
재화 차감 실패
→ 추첨하지 않음
→ USER_CATS 저장하지 않음
→ 409 또는 정책상 오류 응답
```

## 프론트
```text
재화가 부족합니다.
```
표시하고 뽑기 애니메이션은 시작하지 않는다.

## 왜 추첨부터 하면 안 되나
먼저 결과를 뽑은 뒤 결제 실패를 확인하면 서버 로그나 재시도 과정이 복잡해진다. 결제가 가능한지 확정한 다음 결과를 생성하는 흐름이 단순하다.

## 테스트
- balance=0
- 가격보다 1 부족
- 충분한 잔액으로 바꾼 뒤 성공

---

# B-05. 뽑기 버튼 연타

## 상황
사용자가 0.01초 간격으로 3~10회 요청을 보낸다.

## 프론트 방어
버튼을 첫 클릭 즉시 비활성화한다.

하지만 이것은 UX 방어일 뿐이다. 사용자는 개발자 도구나 스크립트로 API를 직접 여러 번 호출할 수 있다.

## 백엔드 방어
각 요청마다 Atomic Update를 실행한다.

예를 들어 1회 가격이 X이고 사용자가 정확히 X만 보유했다면 여러 요청이 와도 한 요청만 잔액 조건을 통과한다.

## 추가 고려
가챠 요청 자체에 idempotency key를 도입할 수도 있지만 MVP에서는 필수라고 보기는 어렵다. 네트워크 재전송까지 엄격하게 한 번만 처리해야 한다면 이후 검토한다.

## 테스트
동시에 여러 HTTP 요청을 보내 실제 성공 횟수와 balance를 확인한다.

# B-06. 일반 고양이 획득

## 목적
추첨 결과로 특정 `CATS.id`가 결정되었을 때 사용자 소유 데이터로 연결한다.

## 흐름
```text
서버 추첨
→ cat_id 결정
→ CATS가 실제 존재하는지 기준 데이터 확인
→ USER_CATS INSERT
→ COMMIT
→ 획득 결과 반환
```

## DB 관계
`CATS`는 고양이 종류의 마스터 데이터이고 `USER_CATS`는 사용자가 그 고양이를 획득했다는 소유 관계다.

쉽게 말하면:
```text
CATS = 도감
USER_CATS = 내 도감에 실제로 들어온 고양이
```

## 테스트
- 저장된 cat_id가 CATS에 존재하는지
- 다른 사용자의 소유 데이터와 섞이지 않는지

---

# B-07. 고희귀도 고양이 획득

## 목적
희귀도에 따라 추첨 확률과 프론트 연출은 달라질 수 있지만 DB 저장 방식은 일반 획득과 동일하게 유지한다.

## 서버 역할
서버가 정해진 확률표를 기준으로 rarity 또는 cat 후보를 결정한다.

프론트가 `나는 SSR 뽑았음` 같은 값을 보내면 안 된다. 결과는 서버가 만들어야 한다.

## 추천 방식
확률표는 코드 상수 또는 설정 데이터 중 하나로 관리할 수 있다. MVP에서는 단순 설정으로 시작할 수 있지만 운영 중 확률 변경이 잦다면 별도 관리 구조가 필요하다.

## 주의
현재 `CATS.rarity`는 문자열이다. 허용 가능한 값 목록을 코드/기획에서 통일하지 않으면 `SSR`, `ssr`, `Ssr`처럼 데이터가 깨질 수 있다.

## 테스트
- 허용하지 않는 rarity 데이터가 섞였을 때
- 특정 rarity 후보가 0마리일 때 서버 처리

---

# B-08. 중복 고양이 처리

## 상황
사용자가 이미 가지고 있는 동일 `cat_id`를 다시 뽑았다.

## 아직 결정해야 할 선택지
### 선택 1. 중복도 별도 USER_CATS row로 보관
같은 종류 고양이를 여러 마리 소유할 수 있다.

장점: 단순 INSERT
단점: 실제 게임에서 중복 개체를 어떻게 사용할지 추가 UI가 필요

### 선택 2. 중복이면 mileage로 변환
새 USER_CATS는 만들지 않고 `USERS.mileage`를 증가시킨다.

장점: 수집형 게임에서 중복 보상이 명확
단점: `(user_id, cat_id)` UNIQUE 같은 소유권 정책을 추가로 고려해야 함

### 현재 판단
어느 선택지도 기본안으로 추천·확정하지 않는다. `USERS.mileage` 컬럼이 있다는 사실만으로 중복 전환 정책을 도출할 수 없으며, 중복 보유 방식과 mileage 역할이 함께 승인된 뒤 구현한다.

## 동시성
같은 사용자의 동시 뽑기에서 같은 cat이 나올 수 있으므로 중복 전환 정책을 쓰면 DB UNIQUE와 transaction 설계를 같이 검토해야 한다.

## 테스트
- 이미 보유한 cat 재획득
- 동시 요청에서 같은 cat 두 번 당첨

---

# B-09. 처리 도중 서버 오류

## 상황
재화는 차감했는데 `USER_CATS` 저장 중 DB 오류가 발생했다.

## 잘못된 결과
```text
돈은 없어짐
고양이는 없음
```
이 상태가 생기면 안 된다.

## 해결
```text
BEGIN
→ balance Atomic Update
→ 추첨
→ USER_CATS INSERT
→ 오류 발생
→ ROLLBACK
```

따라서 balance도 원래 상태로 돌아간다.

## 프론트
성공 응답을 받기 전까지는 실제 획득으로 확정하지 않는다. 실패하면 `뽑기에 실패했습니다. 재화는 차감되지 않았습니다`처럼 안내할 수 있다.

## 테스트
의도적으로 저장 단계에서 오류를 발생시켜 balance가 원복되는지 확인한다.

# B-10. 천장(Pity) 시스템

## 목적
일정 횟수 동안 높은 희귀도가 나오지 않았을 때 보장 보상을 제공할지 결정한다.

## 현재 ERD 문제
현재 19개 테이블/컬럼에는 사용자별 누적 뽑기 횟수나 마지막 고희귀도 이후 횟수를 저장할 장소가 없다.

따라서 천장을 도입한다면 최소한 다음 중 하나가 필요하다.

### 방법 1. USERS 컬럼 추가
예:
```text
gacha_pity_count
```
테이블 수는 그대로 19개라 MVP에 단순하다.

### 방법 2. 별도 가챠 이력 테이블
감사/통계에는 좋지만 20개 미만 제약과 충돌할 가능성이 있다.

## 추천
천장이 필수가 아니라면 MVP에서 제외하는 것이 가장 단순하다. 필수라면 `USERS`에 카운터를 추가하는 안이 현재 제약에 가장 잘 맞는다.

## 반드시 결정할 것
- 천장 존재 여부
- 몇 회인지
- 어떤 희귀도를 보장하는지
- 높은 희귀도가 나오면 카운터를 0으로 초기화하는지
- 다회 뽑기 안에서 천장이 도달했을 때 처리 순서

# B 영역에서 팀이 확정해야 할 항목

1. 1회 가격
2. 다회 가격과 실제 뽑기 횟수(10회/10+1 등)
3. 희귀도 이름
4. 희귀도별 확률
5. 다회 뽑기 보장 규칙
6. 동일 고양이 중복 보유 허용 여부
7. 중복 시 mileage 지급 여부와 양
8. 천장 시스템 여부
9. 천장 카운터 저장 위치
10. 실제 추첨 결과 감사 로그가 필요한지

이 값들이 확정되기 전에는 코드에 임의 숫자를 넣지 않는다.
