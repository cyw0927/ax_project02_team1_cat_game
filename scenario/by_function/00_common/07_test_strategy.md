# 백엔드 테스트 전략

기능 하나를 만들었으면 '정상 동작'만 확인하고 끝내지 않는다. 최소한 정상, 예외, 동시성, DB 정합성 네 방향으로 본다.

## 1. 정상 테스트

사용자가 의도한 정상 흐름이 끝까지 성공하는지 확인한다.

예:

```text
상점 구매
→ 잔액 충분
→ 200
→ balance 감소
→ inventory 증가
```

## 2. 예외 테스트

대표적인 실패를 일부러 만든다.

예:
- 없는 user
- 없는 item/task/room
- 비활성 문제
- 잔액 부족
- 이미 출석
- 꽉 찬 방
- 권한 없는 시작 요청
- 만료된 승급전

각 예외에서 상태코드와 DB 상태가 예상과 같은지 확인한다.

## 3. 동시성 테스트

버튼 연타가 아니라 실제로 여러 요청이 거의 동시에 서버에 도착하는 상황을 검증한다.

### 상점
동시에 여러 번 구매해도 balance가 음수가 되거나 아이템이 공짜로 늘지 않는지.

### 출석
동시에 여러 요청을 보내도 attendance와 보상이 하나만 생기는지.

### 방 입장
마지막 한 자리를 두 사용자가 동시에 요청했을 때 한 명만 성공하는지.

### 채점
많은 attempt가 와도 동시에 실행되는 Docker 수가 제한을 넘지 않는지.

## 4. Transaction rollback 테스트

중간 단계에서 강제로 오류를 내서 앞 단계 변경도 취소되는지 본다.

예:

```text
상점
balance 차감 성공
→ inventory 저장 실패
→ 전체 rollback
→ balance 원상복구
```

## 5. 보안/권한 테스트

- 다른 user_id를 조작해 다른 사람 데이터를 수정할 수 있는가
- JWT 도입 후 body user_id를 믿고 있지는 않은가
- 방장이 아닌 사용자가 시작/종료할 수 있는가
- 다른 사용자의 하우징 객체를 수정할 수 있는가
- `test_cases`가 문제 조회 Response에 노출되는가

## 6. Docker 테스트

- 정상 코드
- 오답
- Runtime Error
- Timeout
- 메모리 과다 사용
- 네트워크 접근
- 파일 쓰기
- Docker Engine 오류
- 컨테이너 cleanup

## 7. 상태 전이 테스트

상태값이 허용되지 않은 방향으로 바뀌지 않는지 본다.

예:

```text
ROOM
WAITING → IN_PROGRESS → FINISHED
```

FINISHED 방을 다시 WAITING으로 바꾸거나, WAITING을 건너뛰고 이상한 요청으로 상태가 꼬이지 않는지 확인한다.

승급전도:

```text
IN_PROGRESS → SUCCESS / FAILED / TIMEOUT
```

최종 상태가 된 뒤 제출/코드 저장을 막는지 본다.

## 8. DB 확인

API 응답만 보고 끝내지 않는다.

테스트 후 DBeaver/SQL/테스트 코드로 실제 row를 확인한다.

예:
- ATTENDANCES 한 행만 생겼는가
- Inventory quantity가 정확한가
- TaskAttempt 상태가 정확한가
- rollback 후 변경이 남지 않았는가

## 9. Swagger 테스트와 자동 테스트

초기 개발 중에는 `/docs`로 빠르게 기능을 이해하고 수동 검증할 수 있다. 반복해서 깨지면 안 되는 핵심 기능은 `tests/`에 자동 테스트를 남긴다.

우선 자동화 가치가 높은 기능:

1. 상점 Atomic Update
2. 출석 UNIQUE
3. 방 입장 정원 동시성
4. TaskAttempt 생성
5. Docker executor 제한
6. 승급전 만료

## 10. 테스트 기록 방식

기능마다 최소한 다음을 남긴다.

```text
테스트 조건
예상 결과
실제 결과
통과/실패
수정한 내용
```

AI가 작성한 코드도 이 검증을 통과한 뒤에만 PR에 올리는 것을 목표로 한다.
