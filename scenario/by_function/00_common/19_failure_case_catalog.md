# 실패 케이스 카탈로그

이 문서는 기능별로 자주 발생하는 실패 상황을 한눈에 보기 위한 공통 참고표다.

목적은 모든 오류를 같은 `400`으로 처리하는 것이 아니라, **왜 실패했는지 백엔드가 구분하고 프론트가 그에 맞는 화면 반응을 할 수 있게 하는 것**이다.

---

## 1. 공통 오류 분류

| 상황 | 추천 HTTP | 백엔드 의미 | 프론트 반응 예시 |
| --- | --- | --- | --- |
| 요청 형식 자체가 잘못됨 | 400/422 | 값 형식 또는 필수값 문제 | 입력칸 오류 표시 |
| 로그인 안 됨 | 401 | 인증 실패 | 로그인 화면 이동 |
| 권한 없음 | 403 | 인증은 됐지만 허용되지 않음 | 접근 불가 안내 |
| 대상 없음 | 404 | user/task/item/room 등 없음 | 존재하지 않는 대상 안내 |
| 현재 상태와 충돌 | 409 | 중복/잔액/정원/상태 충돌 | 상황별 경고 |
| 서버 내부 문제 | 500 | 사용자 잘못이 아님 | 재시도 안내 |
| 채점 시스템 문제 | 일반 HTTP 성공 + attempt 상태 또는 5xx | 비동기 채점 인프라 문제 | SYSTEM_ERROR 표시 |

FastAPI의 기본 validation 오류는 422가 될 수 있으므로 팀에서 400으로 감쌀지 기본값을 유지할지 통일한다.

# A. 학습·채점 실패 케이스

## A-01 문제 조회

| 실패 | 백엔드 처리 | 화면 |
| --- | --- | --- |
| 존재하지 않는 task_id | 404 | 문제를 찾을 수 없음 |
| 비활성 문제 | 404 추천 | 문제를 열 수 없음 |
| UUID 형식 오류 | 422 또는 400 | 잘못된 접근 |

비활성 문제를 403/409로 자세히 알려주기보다 일반 사용자는 404로 통일하는 편이 단순하다.

## A-02 제출

| 실패 | 처리 |
| --- | --- |
| user 없음 | 404 |
| task 없음 | 404 |
| task 비활성 | 404 |
| submitted_code 비어 있음 | 400/422 후보 |
| DB INSERT 실패 | 500 + rollback |

## A-03~A-08 채점

채점 중 발생하는 실패는 사용자 오답과 시스템 오류를 구분한다.

```text
정상 실행 + 기대값 불일치 → WRONG_ANSWER
Python 실행 오류 → RUNTIME_ERROR
실행 제한시간 초과 → TIMEOUT
Docker/서버 문제 → SYSTEM_ERROR
```

중요한 점은 `SYSTEM_ERROR`를 `WRONG_ANSWER`로 기록하지 않는 것이다.

# B. 가챠 실패 케이스

| 실패 | 서버 검사 | 추천 결과 |
| --- | --- | --- |
| 사용자 없음 | user 존재 | 404 |
| 재화 부족 | Atomic Update 영향 0행 | 409 |
| pull_count 허용 범위 아님 | 입력 검증 | 400/422 |
| 획득 가능한 CATS 없음 | master data 검사 | 500 또는 운영 오류 |
| 결과 저장 중 오류 | transaction rollback | 500 |
| 중복 고양이인데 정책 없음 | 구현 금지, 기획 확정 필요 | 개발 보류 |
| 천장 필요하지만 저장 구조 없음 | 설계 미완성 | 개발 보류 |

가챠는 재화만 빠지고 결과가 저장되지 않는 상황이 가장 위험하므로 비용 차감과 결과 저장은 하나의 transaction으로 묶는다.

# C. 배틀 실패 케이스

## 방 생성

- 제목 길이/정원 범위 오류 → 400/422
- host 사용자 없음 → 404

## 방 입장

| 실패 | 추천 결과 |
| --- | --- |
| 방 없음 | 404 |
| 이미 참가 중 | 409 |
| WAITING 아님 | 409 |
| 정원 초과 | 409 |
| 사용자 없음 | 404 |

정원 판정은 `FOR UPDATE` 안에서 다시 확인한다.

## Ready

- 참가자가 아님 → 403 또는 404 정책 통일
- 방이 이미 시작됨 → 409
- 이미 같은 Ready 상태 → 그대로 성공할지 409로 할지 팀 결정

## 시작

- 방장 아님 → 403
- WAITING 아님 → 409
- 최소 인원 미달 → 409
- Ready 조건 불충족 → 409
- ROOM_TASKS 없음 → 409 또는 500 중 설계 선택

## 진행 중 연결 끊김

WebSocket이 끊겼다는 이유만으로 participant row를 삭제하지 않는다. 재접속 정책을 별도로 둔다.

# D. 승급전 실패 케이스

| 실패 | 처리 |
| --- | --- |
| 그룹 참가자 아님 | 403/404 |
| 이미 진행 중 challenge 있음 | 409 |
| 문제 수 조건 불충족 | 400/서버 생성 방식이면 발생 안 함 |
| 비활성 task 포함 | 409/400 |
| expires_at 이미 지남 | 400 |
| challenge 없음 | 404 |
| challenge 종료 상태에서 코드 저장 | 409 |
| 서버 현재 시간이 expires_at 이후 | TIMEOUT 전환 + 요청 거부 |

최종 구현에서는 제한시간을 클라이언트가 임의로 정하지 못하게 서버가 계산하는 방향이 안전하다.

# E. 인증 실패 케이스

| 실패 | 결과 |
| --- | --- |
| username 중복 | 409 |
| 비밀번호 정책 위반 | 400/422 |
| 로그인 정보 불일치 | 401 |
| access token 없음 | 401 |
| access token 만료 | 401 |
| role 부족 | 403 |
| 다른 사용자 user_id를 body에 넣어 조작 | JWT 도입 후 body user_id 미사용 |

로그인 실패 시 `아이디는 맞고 비밀번호만 틀림`처럼 계정 존재 여부를 너무 자세히 노출하지 않는 편이 안전하다.

# F. 하우징 실패 케이스

| 실패 | 결과 |
| --- | --- |
| item 없음 | 404 |
| 소유하지 않은 item | 409 또는 403 |
| 보유 quantity보다 많이 배치 | 409 |
| wallpaper/floor를 일반 가구로 배치 | 409 |
| 다른 사용자 placed object 수정 | 403/404 |
| position_data 형식 오류 | 400/422 |
| 위치 범위 밖 | 위치 규칙 확정 후 400/409 |

현재 충돌 판정을 프론트에서만 할지 서버에서도 할지 미정이다.

# G. 상점 실패 케이스

| 실패 | 처리 |
| --- | --- |
| item 없음 | 404 |
| 가격이 음수 등 master data 오류 | 서버 운영 오류 |
| 잔액 부족 | 409 |
| Inventory 저장 실패 | 전체 rollback + 500 |
| 연타 | Atomic Update가 허용 가능한 요청만 성공 |

가장 중요한 테스트는 `balance`만 줄고 Inventory가 안 늘어나는 중간 상태가 생기지 않는지 확인하는 것이다.

# H. 출석 실패 케이스

| 실패 | 처리 |
| --- | --- |
| user 없음 | 404 |
| 오늘 이미 출석 | UNIQUE 충돌 → 409 |
| 보상 지급 중 DB 오류 | transaction rollback |

| 자정 직전/직후 요청 | timezone 정책에 따라 서버에서 날짜 판정 |

# 프론트가 실패 후 해야 할 것

모든 실패에서 단순히 `alert(error)`만 띄우지 않는다.

```text
잔액 부족 → 구매/가챠 모달 유지 + 부족 안내
방 가득 참 → 방 목록으로 복귀 또는 갱신
오답 → 코드 유지 + 재제출 가능
RUNTIME_ERROR → 오류 메시지 + 코드 유지
TIMEOUT → 반복문/종료조건 확인 안내
SYSTEM_ERROR → 코드 유지 + 재시도
토큰 만료 → 재인증
승급전 TIMEOUT → 입력 잠금 + 결과 화면
```

실패 시 사용자 입력을 보존할 수 있는 기능은 가능한 한 보존한다. 특히 코드 작성 화면에서 서버 오류 때문에 사용자가 작성한 코드까지 사라지는 UX는 피한다.
