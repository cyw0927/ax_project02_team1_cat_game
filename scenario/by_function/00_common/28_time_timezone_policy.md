# 시간·타임존 정책

이 문서는 출석, 승급전, 배틀, 채점 기록처럼 **시간이 기능 결과를 바꾸는 곳에서 어떤 시간을 기준으로 판단할지** 정리한다.

중요하게 구분한다.

```text
기술 기준으로 확정할 수 있는 것
vs
서비스 운영/기획에서 아직 선택해야 하는 것
```

---

# 1. 기술 기준

다음은 백엔드 공통 설계 기준으로 사용한다.

- datetime 저장/비교는 timezone-aware 값을 사용한다.
- DB의 절대시각 datetime은 가능하면 UTC 기준으로 통일한다.
- 만료 여부는 서버 시간이 판단한다.
- 클라이언트가 보내는 현재 시각/오늘 날짜를 권한·보상 판정에 신뢰하지 않는다.
- `오늘`, `일일 제한`, `자정 초기화`가 필요한 기능은 **하나의 SERVICE_TIMEZONE 설정값**을 공통 사용한다.
- 각 router가 제각각 OS의 `date.today()`를 사용하는 구조를 피한다.

---

# 2. 아직 확정되지 않은 것: SERVICE_TIMEZONE 값

현재 서비스 기준 timezone의 **실제 값은 아직 팀 확정사항**이다.

한국 사용자 중심 프로젝트라면 다음이 가장 이해하기 쉬운 후보다.

```text
Asia/Seoul
```

하지만 이것은 현재 **추천 후보**이지, 비즈니스 확정값으로 취급하지 않는다.

따라서 문서에서:

```text
KST 기준으로 확정
```

이라고 쓰지 않는다.

정확한 값이 확정되면:

```text
APP_TIMEZONE=<확정값>
```

처럼 공통 설정에서 관리한다.

---

# 3. 출석

확정 요구사항:

```text
매일 자정 이후 첫 로그인
→ 자동 출석 1회
→ 100원 지급
```

여기서 `자정`이 어느 timezone의 00:00인지는 아직 미정이다.

최종 처리 구조:

```text
server now
→ SERVICE_TIMEZONE으로 변환
→ 날짜 추출
→ check_in_date 결정
→ UNIQUE(user_id, check_in_date)
```

프론트가 `today` 값을 보내고 서버가 그대로 믿는 구조는 사용하지 않는다.

---

# 4. 승급전

`started_at`, `expires_at`은 절대 시각으로 비교한다.

```text
server_now >= expires_at
→ TIMEOUT
```

프론트 카운트다운은 표시용이고 최종 판정은 서버가 한다.

가능하면 UTC timezone-aware datetime으로 저장/비교한다.

---

# 5. TASK_ATTEMPTS

`attempted_at`은 이력 정렬에 사용한다.

기본 방향:

```text
UTC 저장
→ 화면에서 필요한 timezone으로 변환
```

채점 시작/완료 시각이 실제 운영에 필요해지면 `started_at`, `completed_at` 같은 컬럼을 별도 검토한다. 현재 ERD에 없다는 이유만으로 미리 추가하지 않는다.

---

# 6. 배틀

현재 ROOMS에는 생성/시작/종료 datetime 컬럼이 없다.

배틀 제한시간, 경기 기록, 정확한 재접속 복구에 필요하다고 확정되면 후보:

```text
created_at
started_at
finished_at
```

하지만 배틀 진행 규칙 확정 전 migration을 먼저 만들지는 않는다.

---

# 7. 일일 보상/제한

향후 하루 단위 제한이 생길 수 있는 기능:

```text
출석
학습 일일 보상
배틀 일일보상
랭킹 일일보상
무료 가챠
```

이 기능을 실제 도입하면 모두 같은 `SERVICE_TIMEZONE`을 사용한다.

기능마다 다른 자정 기준을 사용하지 않는다.

---

# 8. 설정 위치

공통 설정 예:

```env
APP_TIMEZONE=<팀에서 확정한 IANA timezone>
```

코드는 해당 설정을 읽어 서비스 날짜 계산 함수를 공통으로 사용한다.

예시 문서에서 `Asia/Seoul`을 사용하더라도 **예시와 확정을 구분**한다.

---

# 9. 테스트

timezone 값이 확정된 뒤 최소 다음을 테스트한다.

- 서비스 기준 23:59:59 첫 로그인
- 서비스 기준 00:00:00 이후 첫 로그인
- 같은 서비스 날짜 재로그인
- 서버 OS timezone과 SERVICE_TIMEZONE이 다른 환경
- 승급전 만료 직전
- 만료시각과 동일
- 만료 직후
- 클라이언트 PC 시간을 임의 변경한 요청

---

# 결론

현재 최종 문서 기준은 다음이다.

```text
절대시각 datetime 저장/비교 → UTC 중심
오늘/자정/일일 규칙 → 하나의 SERVICE_TIMEZONE 사용
SERVICE_TIMEZONE 실제 값 → 아직 팀 결정 필요
Asia/Seoul → 현재 추천 후보, 확정값 아님
최종 판정 → 서버
```

따라서 출석 구현에서 현재 `date.today()`를 그대로 최종안으로 사용하지 않는다.
