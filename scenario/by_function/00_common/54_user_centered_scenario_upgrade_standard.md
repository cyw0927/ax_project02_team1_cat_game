# 사용자 중심 시나리오 보강 표준과 추적 규칙

## 목적

`by_function`의 API·DB·테스트 문서를 기능 목록으로만 읽지 않고 실제 사용자 사고 상황까지 추적하기 위한 공통 표준이다. 모든 A~H 시나리오와 공통 정책 문서에 적용한다.

## 각 시나리오의 최소 질문

1. **사용자 화면/흐름**: 사용자가 무엇을 보고 어떤 행동으로 진입하는가?
2. **정상 흐름**: 서버 권위 상태가 어떤 순서로 변하는가?
3. **대표 Worst Case**: 가장 큰 손실·불공정·데이터 훼손은 무엇인가?
4. **왜 발생하는가**: 더블클릭, 매크로, 오래된 화면, 여러 기기, 시각 경계, 앱 크래시, 외부 작업 실패 중 무엇인가?
5. **서버 감지**: 어떤 인증·권한·상태·시간·unique·영향 row 수로 발견하는가?
6. **방어 로직**: 조건부 원자 UPDATE, unique, 멱등키, 짧은 transaction/lock, 재조회 중 무엇을 쓰는가?
7. **사용자 UI**: 성공·실패·처리 중·결과 확인 중·복구 상태를 어떻게 구분하는가?
8. **DB/API/state 영향**: 어떤 row와 상태 전이가 바뀌며 무엇은 절대 바뀌지 않는가?
9. **retry/duplicate/concurrency/network**: 같은 요청이 다시 오거나 응답만 유실돼도 안전한가?
10. **다음 단계 영향**: 실패나 지연이 후속 보상·랭킹·인벤토리·하우징을 오염시키지 않는가?
11. **테스트**: 정상뿐 아니라 경계·경쟁·부분 실패·복구를 재현하는가?
12. **TBD**: 미확정 숫자·확률·보상·컬럼·정책을 새 사실처럼 쓰지 않았는가?

## 실제 사고 상황 공통 카탈로그

| 사고 상황 | 서버 감지 | 기본 방어 | UI/후속 영향 |
|---|---|---|---|
| 23:59 요청, 00:01 완료 | 서버 시각·이벤트 기준일·수락 시각 | 기준 정책은 `TBD`, 서버 시각으로 판정 | 귀속 날짜를 명시 |
| 마지막 한 자리 동시 입장 | 방 상태·정원·참가 여부 | 해당 ROOM만 짧게 `SELECT FOR UPDATE` | 패자는 정원 마감, 참가 row 없음 |
| 제출·구매·보상 매크로 | request/event 식별자·기존 결과 | UI 잠금 + 서버 멱등/unique/조건부 UPDATE | 애니메이션과 실제 지급 분리 |
| commit 후 응답 유실·앱 크래시 | 기존 결과/거래 row | 기존 결과 반환·최신 상태 재조회 | `결과 확인 중` 후 복구 |
| 만료 직전 제출 | 서버 수락 시각·expires_at·상태 | 인정 시각은 `TBD`, 종료 상태 단방향 전이 | 미수락과 처리 중 만료 구분 |
| 차감 성공 후 inventory/result 실패 | transaction 변경 범위 | 전체 rollback, 외부 작업 중 transaction 금지 | 돈만 빠진 성공 화면 금지 |
| 가챠 애니메이션 중 종료 | 저장 결과·request_id | 결과를 먼저 확정, 연출은 결과만 표시 | 동일 결과 복원 |
| 배치 데이터 폭탄 | payload 크기·필드·수량·좌표 | schema/크기/개수 제한 | 부분 저장 금지 |
| Docker 자원 고갈 | timeout·memory·CPU·output·network | memory/CPU/network/read-only/timeout 격리 | 시스템 오류와 오답 분리 |
| BackgroundTasks 중 재시작 | 오래된 PENDING·작업 식별자 | MVP 단일-worker+semaphore 한계, 필요 시 durable queue | stuck 복구 안내 |

## 트랜잭션과 lock 경계

- 상점은 `balance >= price` 조건부 원자 UPDATE와 INVENTORIES 증가를 하나의 짧은 transaction으로 묶는다.
- 배틀 마지막 자리처럼 복수 조건 동시 판정이 필요한 row에만 짧게 `SELECT FOR UPDATE`를 사용한다.
- Docker, 외부 AI, WebSocket 대기, 애니메이션, 사용자 입력 중 DB lock을 유지하지 않는다.
- `BackgroundTasks`는 durable queue가 아니다. 다중 worker·재시작 복구·작업 유실 방지가 요구되면 별도 큐가 필요하다.

## 미확정 정책 보호선

- 가챠 비용, 단회/다회, 할인, 확률표, 픽업, 천장, 중복/mileage 처리
- 배틀 점수식, 종료 조건, AFK 및 보상
- 승급 문제 개수, 합격 기준, 제출 인정 시각, 보상
- `balance`와 `mileage`의 최종 역할
- 일일 미션 신규 사용자/복습 0개 fallback

선택지는 설명할 수 있지만 승인된 값처럼 쓰지 않는다. 존재하지 않는 컬럼은 현재 ERD의 사실로 쓰지 않고 필요한 구조는 `신규 ERD/마이그레이션 TBD`로 표시한다.

## 공개 방문과 AI 대화 확정선

- 공개 방 방문, 타인 고양이 쓰다듬기·상호작용, 방문 보상은 정식 기능이다.
- 공개 상태, 방문 기록, 보상 멱등성·일일 제한 구조는 신규 ERD에서 지원해야 한다. 횟수와 보상 수치는 `TBD`다.
- 방문자는 타인의 소유권·가구 배치·고양이 영구 상태·`CAT_MEMORIES`를 수정할 수 없고 위조 쓰기는 403 처리한다.
- AI 공급자는 미확정이다. 입력 검증, 역할/권한 분리, 출력 검증, 최소 권한, 기억 쓰기 제한, 방문자 read-only context, 로깅/모니터링의 다층 방어를 적용한다.

## 완료 판정

문서 제목만 표준화해서는 완료가 아니다. 상세 시나리오, API 계약, DB 전후 상태, 테스트 케이스가 같은 사고 상황과 정책 경계를 서로 모순 없이 설명해야 한다.
