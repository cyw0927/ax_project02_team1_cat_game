# 배틀 점수 중복 방지 설계

이 문서는 실시간 배틀에서 같은 사용자가 같은 문제로 점수를 여러 번 얻는 문제를 어떻게 막을지 정리한다.

현재 ERD에는 `ROOM_PARTICIPANTS.current_score`는 있지만, **누가 어떤 ROOM_TASK로 이미 득점했는지** 직접 기록하는 테이블은 없다.

따라서 이 부분은 실제 구현 전에 반드시 구조를 결정해야 한다.

---

## 1. 중복 득점이 왜 생기나

예:

```text
사용자 A가 1번 문제 정답 제출
→ 채점 성공
→ +점수

같은 문제를 다시 제출
→ 또 채점 성공
→ 또 +점수
```

또는 네트워크/버튼 연타로 같은 요청이 거의 동시에 두 번 들어올 수 있다.

---

## 2. 프론트 버튼 잠금만으로 부족

프론트에서 제출 버튼을 잠그는 것은 좋은 UX지만 다음을 막지 못한다.

- API 직접 호출
- 네트워크 재전송
- 두 탭/두 기기
- 거의 동시에 들어온 요청

따라서 서버/DB에서 최종 방어가 필요하다.

---

## 3. 서버가 점수를 계산해야 한다

프론트가 다음처럼 보내면 안 된다.

```json
{
  "score": 100
}
```

권장 흐름:

```text
사용자가 코드 제출
→ 서버가 해당 room/task/participant 확인
→ 서버 채점
→ PASSED이면 서버 규칙으로 점수 계산
→ 중복 득점 여부 확인
→ current_score 증가
```

---

## 4. 현재 ERD의 한계

현재 `ROOM_PARTICIPANTS`에는 총점만 있다.

```text
current_score
```

하지만 다음 정보는 없다.

```text
participant A가 room_task 1을 이미 맞췄는가?
participant A가 room_task 2를 이미 맞췄는가?
```

이 정보 없이 완전한 중복 득점 방어를 하려면 다른 기록을 재활용하거나 스키마 확장이 필요하다.

---

## 5. 가능한 해결책

### 안 A. 별도 배틀 답안/득점 테이블 추가

예시 개념:

```text
BATTLE_ATTEMPTS 또는 ROOM_TASK_RESULTS
room_id
participant_id
room_task_id
is_correct
score_granted
```

그리고:

```text
UNIQUE(participant_id, room_task_id)
```

또는 `first_score_granted` 성격의 UNIQUE를 둔다.

장점:
- 가장 명확함
- 재제출 이력/오답 기록 가능
- 중복 방어 강함

단점:
- 현재 19테이블 ERD 제한을 다시 검토해야 함

### 안 B. 일반 TASK_ATTEMPTS 재활용

현재 TASK_ATTEMPTS는 일반 학습용으로 user_id/task_id는 있지만 room_id가 없다.

그래서 그대로는 특정 배틀의 특정 문제인지 구분하기 어렵다.

컬럼을 추가하는 방법도 있지만 학습 도메인과 배틀 도메인이 강하게 결합될 수 있다.

### 안 C. 메모리에서만 처리

서버 connection/session 메모리에 `already_scored` 집합을 두는 방법.

추천하지 않는다.

서버 재시작/여러 worker에서 상태가 사라지거나 갈라진다.

---

## 6. 추천 방향

기능 요구가 실제로:

```text
배틀에서 문제별 최초 정답만 점수
```

이라면 DB에 그 사실을 남길 수 있는 구조가 가장 안전하다.

다만 새 테이블 추가 여부는 ERD 20개 미만 조건과 함께 팀이 결정해야 한다.

이 문서에서는 임의로 20번째 테이블을 확정하지 않는다.

---

## 7. 동시 요청

두 정답이 동시에 처리되는 경우:

```text
worker 1: 아직 득점 안 함 확인
worker 2: 아직 득점 안 함 확인
```

후 둘 다 점수를 올릴 수 있다.

따라서 단순 `SELECT 후 UPDATE`보다:

- UNIQUE INSERT
- 조건부 UPDATE
- 필요한 row lock

등 DB 수준 원자성이 필요하다.

별도 결과 테이블을 쓴다면 UNIQUE가 가장 이해하기 쉽다.

---

## 8. 오답/재제출 정책과의 관계

정해야 하는 것:

- 오답 후 재제출 가능?
- 정답 후 같은 문제 다시 제출 가능?
- 정답 시간에 따라 점수 차등?
- 팀원이 같은 문제를 각각 맞추면 각자 점수?

이 규칙에 따라 필요한 데이터가 달라진다.

---

## 9. 팀전

`team_name`이 있으므로 팀전에서는 두 가지 점수 모델이 가능하다.

A. 각 참가자 점수 합산
B. 팀 공용 점수 직접 관리

현재 ERD는 참가자 `current_score` 합산 방식과 더 자연스럽다.

다만 최종 규칙은 기획 확정이 필요하다.

---

## 10. WebSocket 반영

점수는:

```text
DB 점수 commit
→ score_changed broadcast
```

순서로 보낸다.

프론트가 이벤트를 놓쳐도 재접속 시 DB snapshot으로 복구한다.

---

## 11. 테스트

- 첫 정답은 1회 득점
- 같은 문제 두 번째 정답은 중복 득점 없음
- 오답 후 정답
- 거의 동시에 같은 문제 정답 2회
- 다른 문제 정답은 정상 추가 득점
- 같은 팀 다른 사용자 정답
- 재접속 후 점수 유지
- FINISHED 방에서 추가 득점 차단

---

# 구현 전 결정사항

```text
[ ] 배틀 답안 이력 저장이 필요한가
[ ] 새 테이블을 허용할 것인가
[ ] 문제별 최초 정답만 점수인가
[ ] 오답 후 재제출 가능한가
[ ] 팀전 점수 계산 방식
[ ] 점수 값/시간 보너스
```

이 항목이 정해지기 전에는 `current_score += 임시숫자` 식으로 핵심 점수 로직을 확정하지 않는다.
