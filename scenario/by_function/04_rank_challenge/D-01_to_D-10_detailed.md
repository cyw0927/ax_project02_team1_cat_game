# D-01 ~ D-10. 승급전 상세 시나리오

이 문서는 랭킹 그룹 내에서 승급전을 시작하고, 문제를 풀고, 코드 자동 저장과 시간 제한을 처리한 뒤 성공/실패를 판정하는 흐름을 정리한다.

> 문제 수, 제한시간, 합격 조건, 성공/실패 점수 변화는 아직 확정하지 않는다.

---

# D-01. 승급전 화면 진입

## 목적
사용자가 랭킹 화면에서 승급전 기능을 열었을 때 도전 가능한지 확인한다.

## 흐름
```text
승급전 버튼 클릭
→ 현재 사용자의 RANKING_PARTICIPANTS 확인
→ 해당 group 존재 확인
→ 진행 중 challenge 여부 확인
→ 도전 가능/이어하기 상태 반환
```

## DB
- `RANKING_GROUPS`
- `RANKING_PARTICIPANTS`
- `RANK_CHALLENGES`

## 화면
진행 중 도전이 있으면 새 시작 버튼보다 `이어하기`를 우선 보여주는 방식이 자연스럽다.

---

# D-02. 승급전 정상 시작

## 목적
하나의 승급 시험 세션과 그 안의 문제 목록을 고정한다.

## 처리 순서
```text
사용자 확인
→ group 참가 여부 확인
→ active challenge 중복 확인
→ 출제할 TASKS 확인
→ RANK_CHALLENGES INSERT
→ RANK_CHALLENGE_TASKS 순서대로 INSERT
→ COMMIT
```

## 시간
`started_at`과 `expires_at`은 서버가 관리해야 한다.

사용자 브라우저가 종료되더라도 제한시간이 계속 흘러야 하므로 `남은 시간 10분` 같은 상대값만 저장하지 않고 **절대 만료 시각 expires_at**을 저장한다.

## 중요
현재 구현처럼 프론트가 `expires_at`을 직접 정해서 보낸다면 사용자가 요청을 조작해 시험 시간을 늘릴 수 있다. 제한시간이 기획상 고정되면 서버가 `now + 제한시간`으로 계산하는 방향이 안전하다.

# D-03. 진행 중 승급전 중복 시작

## 상황
같은 사용자가 이미 IN_PROGRESS인 승급전이 있는데 새 승급전을 또 시작한다.

## 문제
동시에 여러 challenge를 만들면 어떤 시험 결과를 점수에 반영할지 꼬인다.

## 처리
```text
새 시작 요청
→ 현재 사용자/group의 유효한 IN_PROGRESS challenge 확인
→ 있으면 새 INSERT 거부
→ 기존 challenge_id 반환 또는 409
```

## 동시성
두 시작 요청이 정말 동시에 오면 둘 다 `없음`을 보고 INSERT할 수 있다. 엄격히 막으려면 DB UNIQUE로 표현 가능한 구조인지 또는 관련 participant row를 잠그고 확인할지 검토해야 한다.

현재 모델의 '한 사용자당 active challenge 하나'는 조건부 UNIQUE로 단순 표현하기 까다로우므로 transaction 직렬화가 현실적인 후보다.

---

# D-04. 승급전 문제 조회

## 목적
시작 시 고정된 문제를 `task_order` 순서대로 제공한다.

## 흐름
```text
challenge 조회
→ 현재 사용자 소유 challenge인지 확인
→ IN_PROGRESS인지 확인
→ expires_at 검사
→ RANK_CHALLENGE_TASKS order_by task_order
→ TASKS 문제 표시 정보 JOIN
→ test_cases 제외 후 반환
```

## 왜 문제를 시작할 때 고정하나
시험 중간마다 랜덤 문제를 다시 뽑으면 새로고침 후 문제가 바뀔 수 있다. `RANK_CHALLENGE_TASKS`가 시험 시작 당시 문제 목록의 스냅샷 역할을 한다.

## Lock
조회만 하는 경우 필요 없다.

# D-05. 코드 자동 저장

## 목적
네트워크가 끊겨도 작성 중이던 코드를 복구한다.

## 흐름
```text
사용자 코드 작성
→ 일정 주기/문제 이동 시 저장 API
→ challenge가 본인 것인지 확인
→ status=IN_PROGRESS 확인
→ expires_at 이전인지 확인
→ saved_code UPDATE
```

## 프론트 전략
키보드를 누를 때마다 매번 API를 호출하지 말고 2~몇 초 debounce, 문제 이동, 창 이탈 시점 등을 이용하는 방법이 일반적이다. 정확한 주기는 프론트와 협의한다.

## 중요한 방어
시험이 끝난 뒤에는 saved_code를 더 수정할 수 없게 해야 한다.

## 테스트
- 정상 저장
- 다른 사용자 challenge 수정 시도
- TIMEOUT 이후 저장
- 없는 task 저장

---

# D-06. 네트워크 단절 후 이어하기

## 상황
사용자가 문제를 풀다가 인터넷이 끊기거나 브라우저를 닫는다.

## 서버 기준
시험은 종료되지 않는다. `expires_at`은 계속 흐른다.

## 재접속
```text
로그인
→ 진행 중 challenge 조회
→ 서버 현재 시간과 expires_at 비교
```

### 아직 시간 남음
- challenge와 문제 목록 반환
- 각 `saved_code` 반환
- 남은 시간은 서버 만료시각 기준으로 화면 계산

### 이미 만료
- status를 TIMEOUT으로 확정
- 이어하기 불가

## 핵심
사용자의 PC 시계를 신뢰하지 않는다.

---

# D-07. 승급전 문제 제출 및 정답

## 목적
일반 학습과 같은 안전한 sandbox 채점기를 사용하되, 결과 저장 위치는 승급전 문제 상태에 반영한다.

## 흐름
```text
제출 클릭
→ challenge 소유권 확인
→ IN_PROGRESS 확인
→ expires_at 확인
→ 해당 task가 challenge 문제인지 확인
→ Docker 채점
→ 통과
→ RANK_CHALLENGE_TASKS.is_passed=true
```

## 재제출
이미 통과한 문제를 다시 제출할 수 있게 할지 결정해야 한다. 보통 승급전에서는 이미 통과한 문제를 다시 점수화할 이유가 없으므로 제출 차단 또는 결과 유지가 단순하다.

## 저장 코드
최종 제출 코드도 `saved_code`에 반영할 수 있다.

---

# D-08. 제한시간 초과

## 목적
브라우저 타이머 조작과 무관하게 서버가 시험 종료를 판정한다.

## 검사 시점
최소한 다음 요청에서 항상 확인한다.
- 문제 조회
- saved_code 저장
- 문제 제출
- 완료 요청

```text
server_now >= expires_at
→ TIMEOUT
```

## 완전 자동 종료
아무 요청도 안 오는 사용자를 만료 시점 즉시 DB에서 TIMEOUT으로 바꾸려면 별도 scheduler가 필요하다. MVP에서는 다음 접근 시 만료 확정 방식도 가능하다.

## 테스트
- 만료 1초 전 제출
- 만료 직후 제출
- PC 시간을 뒤로 변경

---

# D-09. 승급 성공

## 목적
모든 제출 결과를 기준으로 합격 조건을 판정하고 랭킹 점수에 반영한다.

## 처리
```text
challenge 문제 상태 조회
→ 합격 조건 계산
→ 성공이면 status=SUCCESS
→ RANKING_PARTICIPANTS.current_rank_score 변경
→ COMMIT
```

## 점수 동시성
`current_rank_score`를 Python에서 읽고 +점수를 계산해 덮어쓰기보다 DB 자체 `score = score + :delta` 식으로 변경하는 편이 동시 요청에 안전하다.

## 미정
- 몇 문제를 맞아야 하는지
- 성공 시 몇 점인지
- 실제 '등급'을 score 구간으로 표현할지 별도 값이 필요한지

---

# D-10. 승급 실패

## 상황
시간은 끝나지 않았지만 최종 제출 결과가 합격 기준을 만족하지 못한다.

## 처리
```text
합격 조건 미달
→ RANK_CHALLENGES.status=FAILED
→ 필요 시 score 정책 적용
→ 더 이상 문제 저장/제출 불가
```

## 실패 패널티 선택지
1. 점수 변화 없음
2. 일정 점수 감소
3. 재도전 쿨타임만 적용

### 추천 MVP
학습 동기를 꺾지 않고 구현도 단순하게 하려면 **실패 시 점수 감소 없음**이 무난하다. 단, 기획 승인 전 코드로 확정하지 않는다.

## 테스트
- 일부 문제 통과
- 모두 오답
- FAILED 이후 재제출
- 성공/실패 확정 API 중복 호출
